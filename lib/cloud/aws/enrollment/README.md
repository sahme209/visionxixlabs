# Tenant-owned AWS desktop enrollment (read-only slice)

This slice registers an explicitly selected AWS role identity through a currently accepted paired desktop session. It does not create IAM roles/trust, apply infrastructure, enable the generic Agent, adopt legacy Lead credentials, or prove a full customer deployment journey.

Routes:

- `POST /api/desktop/cloud/aws/enrollment`: `expectedAccountId`, `roleArn`, `region`; returns a ten-minute challenge and external ID. Other input fields, including organization/vault overrides, are rejected.
- `POST /api/desktop/cloud/aws/enrollment/[id]/complete`: `externalId`; verifies broker-only AssumeRole and exact account/role/session identity, then atomically consumes the challenge and persists a tenant/version-bound vault record.
- `GET /api/desktop/cloud/accounts`: paired accepted-member metadata for the new disabled, scoped AWS connections only.
- `GET /api/desktop/cloud/accounts/[id]/inventory`: no query/body overrides. Reads the scoped credential in its stored region, repeats exact STS identity validation, and reads one EC2 DescribeInstances page with MaxResults 5. Returns at most five whitelisted instances, a truncation marker and `complete:false`; no tags, provider continuation token, secrets or whole-account totals.

Management requires current `connections:manage`; reads require current `workspace:read`. API keys cannot authorize these routes. Management rechecks the durable device record (user/org/expiry/revocation) and current accepted membership inside the post-provider Serializable transaction using a fresh clock. Challenge expiry, exact proof/input, account timestamp, prior credential version and one-time consumption are checked before replacement; conflicts roll back consumption and preserve existing configuration. Inventory rechecks authority and the account/ref/region/timestamp/version binding after provider reads, withholding late results from revoked/replaced connections.

New-account creation applies canonical PLAN_REGISTRY cloud-account limits using validated existing billing tier/status semantics. Missing/invalid/legacy trial snapshots use Starter allowance; billing/count storage errors fail unavailable. The tenant-wide count includes disabled accounts and all providers. Prechecks avoid unnecessary STS, while the authoritative count/plan read and insertion share the Serializable consume transaction, so a competing last-slot insertion or plan downgrade cannot silently exceed the allowance. Existing-account revalidation has zero resource delta and skips creation limits even above a downgraded cap; this does not change commercial desktop access policy, activate subscriptions or charge billing.

The canonical CloudAccount is created only after real STS confirmation, with `enabled:false`, `observe_only` and a `cloud-v2:<id>` reference. New vault ciphertext is bound to organization, AWS provider, canonical account ID and version. Existing legacy pointers cannot be adopted by this flow. The generic Agent still expects legacy Lead-backed credential references; it is deliberately not enabled or called here. Inventory uses its own tenant-aware resolver. Connected means last verified role identity, not inventory permission or deployment readiness; denied inventory is reported distinctly.

Provider IO uses only dedicated AWS_CONNECTOR_BROKER credentials, configured live mode and the existing cloud feature gate. Ambient workload keys never substitute for the broker. STS has a shared eight-second abort boundary/max two attempts per SDK client; EC2 has a six-second boundary/max two attempts. Format-only validation, absent broker/live configuration, missing migration tables and incompatible storage cannot produce connected. No existing browser OAuth/callback lifecycle events are synthesized: the real account validation audit is best effort, without secret configuration.

The schema/migration proposal is a separate isolated-test artifact and requires its own reviewed production approval, independent of authentication-only recovery. Until the proposed tables exist, these endpoints fail unavailable before provider IO. No production SQL or cloud calls were executed during implementation; all provider acceptance in tests is simulated. Test coverage composes routes, authorization gates, challenge/transaction decisions, actual scoped encryption, mocked SDK identity/EC2 responses, and DTO compatibility. Mocked service rollback/serialization conflicts prove response and composition behavior, not PostgreSQL SSI. Actual isolated PostgreSQL last-slot races and migration fixtures are separate evidence, not production or provider acceptance.

Remaining milestones: actual separately authorized sandbox role/permission acceptance; reviewed disconnect/revocation management; durable audit/monitoring acceptance; multi-account pagination beyond the bounded metadata list; secure generic Agent snapshot integration; Azure/GCP enrollment; approved immutable deployment artifacts, execution, health validation and rollback. Existing website Lead-token enrollment and credentials remain preserved and isolated.
