# Retain unconfirmed desktop request text

An interrupted or failed transport consumed the original input/queued item, but reloading saved history could remove its only remaining visible text when the service had not persisted it. The desktop now retains a bounded, session-only recovery copy before consuming input or queued work. It uses the existing draft-cache limits (20 conversations, 500,000 total characters), refuses overflow without eviction, and clears a copy only on a confirmed service response or explicit dismissal. Credential/workspace remounts clear private copies; nothing is written to browser storage or sent by restoring text.

The compact recovery panel appears only for an unconfirmed response. Restore requires saved-history review and an empty current draft, preserves newer input, and does not send or retry. Stopped/failed responses retain the existing recovery and queue-pause gates. A different request cannot silently replace an older unconfirmed copy: its input/queued item stays intact until the old copy is restored or dismissed. Dismissing the copy does not claim the previous operation finished or bypass in-flight settlement/history gates. A same-text retry still needs a separate explicit Send after those gates.

Four initial regressions reproduced the missing recovery control. A further regression reproduced silent replacement of older unconfirmed text by different work; the pre-consumption guard fixes it. Seventy-nine focused readiness/draft cases pass, including failed/thrown transports, cancellation, dispatched queued failure, capacity refusal, credential remount, newer-draft preservation, explicit copy dismissal, replacement refusal, and confirmed-response cleanup. The pre-existing abort/settlement test now explicitly dismisses its old copy before starting different work; its no-early-send and stale-response assertions remain intact. Independent source review found no blocker.

These are actual React interactions using fixed client fixtures, not a real paid model or native network-failure acceptance. Exact-source full checks, frontend/native build and compatible-session acceptance are recorded separately. No additional model request, permission, billing behavior or web cockpit design changes are introduced.
