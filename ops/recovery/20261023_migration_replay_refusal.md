# Refuse unsafe migration replay

The production migration workflow previously accepted a failed migration name, marked it rolled back, and immediately ran every pending migration. That can replay the historical Agent migration's broad enablement/tool backfill after the narrow schema-only recovery. Removing that convenience prevents an application release workflow from treating a partial migration as safely reversible.

The supported `npm run db:migrate:deploy` command now first inspects the selected public migration ledger in a read-only, repeatable-read transaction. It refuses missing history, unfinished migrations, unknown applied migrations and changed applied checksums. Independently, the historical `20261013172000_add_workspace_agent_identity` migration must already be completed with its matching source checksum; otherwise it requires manual recovery and cannot pass this gate. Alternate database schemas are refused before connection. Database failures refuse deployment; errors do not disclose connection credentials. Historical SQL and ledger evidence are unchanged.

Eleven focused tests cover the policy and supported workflow/command wiring, query failure, read-only refusal, alternate-schema CLI refusal and shell short-circuit before a subsequent command. Eight owned PostgreSQL cases exercise actual ledger reads and actual CLI success/failure with unchanged evidence. These run alongside the existing 50 Agent, session, coding and approval database cases; all 58 passed and the owned local cluster was removed. No production database, private production backup, provider inference or CI workflow dispatch was used.

This is a refusal preflight, **not an atomic migration fence**: inspection and Prisma deployment use separate connections, so concurrent operators can change history between them. It does not review the contents of ordinary pending migrations, certify schema equivalence, authorize production mutation, or make direct Prisma invocations safe. Production migration concurrency remains serialized by the existing workflow, and operators must still use the separately reviewed, backup-bound recovery procedure. The historical migration-lineage convergence remains unresolved. This branch's workflow safeguards become active in the normal workflow only when that source is adopted there; a web-service deployment does not change the default-branch Actions workflow.
