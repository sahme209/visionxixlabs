# Scheduled Airflow dispatch freshness

The scheduler previously loaded credentials and rules, then triggered a due DAG without rechecking either snapshot. Five regressions reproduced dispatch despite a paused/edited rule, revoked/reconnected connection or failed authority read. Scheduled dispatch now requires the current enabled rule's organization, ID, connection, update time and scheduled occurrence, plus the active connection's exact organization, ID, provider and update time. Invalid/missing version dates refuse before dispatch rather than becoming omitted Prisma predicates.

The provider still receives the existing deterministic occurrence ID. The scheduler now advances the next occurrence only through a conditional update matching the same observed rule. If an owner edits or pauses the rule during dispatch, the accepted run receipt is retained, the newer schedule is preserved, and further processing of that stale rule stops. Two additional regressions reproduced missing-version acceptance and unconditional schedule overwrite before these corrections.

Five actual owned PostgreSQL cases verify unchanged dispatch/advance, pause after rule load, revocation after load, replacement credential version and an owner schedule edit during dispatch with its accepted receipt retained. The fixed provider boundary is synthetic: no external Airflow/cloud service is contacted by these database cases. Existing real local Airflow 3.3.2 engine acceptance remains separate. The portable runner passed all 63 cases (prior 58 plus five new) and removed the owned cluster. Focused Airflow tests passed 130, with three opt-in engine cases skipped in that run. Independent source review found no blocker.

This is a pre-dispatch freshness check, **not atomic provider revocation**. A change can still occur after the final database read and before the remote request. The conditional update protects persisted schedule edits; it does not cancel a provider run already accepted. No schema migration, policy change, permission grant, customer connection save, provider inference, live DAG trigger or production database mutation was performed for these tests. Full hosted/customer automation acceptance remains separate.
