# AWS enrollment storage proposal

Prepared 2026-10-15. No production execution is authorized. This proposal is separate from the pinned authentication-only recovery SQL, its approval, and its unchanged migration checksum.

## Proposed durable boundary

Reuse canonical `CloudAccount`; do not create a competing desktop cloud-account inventory. Its tenant/provider/external-account uniqueness remains. Add a compound id/organization key for scoped references, a one-to-one `CloudAccountCredential` containing server-encrypted configuration, positive version and validation time, and `CloudAccountEnrollmentAttempt` containing tenant/user, expected account/role/region, lower-case SHA-256 external-ID digest, expiry, consumed time, optional existing-account binding and observed credential/account versions. Raw external IDs, provider tokens and plaintext credentials are not stored by this schema.

Composite foreign keys prevent a credential or reconnect challenge from referencing another tenant's account. Credential deletion follows account deletion; reconnect attempts restrict deleting a referenced account (normal disconnect should disable, not delete). No new User/Organization relation is fabricated. Tenant/user membership and capability checks, encryption/authenticated associated-data scope, provider identity verification, secret deletion, expiry, single-use consumption and both version compares remain mandatory at the backend transaction boundary. Database columns alone do not implement those controls. Account `updatedAt` protects a pending challenge against intervening disconnect/replacement; credential version protects overwrite races.

## Migration scope and drift handling

`20261016010000_cloud_account_enrollment` creates missing canonical CloudProvider/AutopilotMode enum types and CloudAccount table, creates the two new storage tables and indexes, and adds scoped uniqueness. An exact existing enum is reused; any incompatible labels or non-enum type are rejected without rewriting the type. Existing CloudAccount columns/nullability, primary key and safe autopilot default are checked. Required unique indexes are verified by actual indexed columns/uniqueness/validity, not their names. Existing accounts are not enabled, modified or assigned credentials. Partial/already-present new tables are rejected for review rather than silently adopted. Entire SQL is transactional with short lock/statement timeouts.

Fresh read-only catalog evidence reportedly found CloudAccount, CloudProvider and AutopilotMode absent on the inspected Neon target; the website binding is still unverified. This is not permission to create them there. The known failed workspace-agent-identity migration and missing Organization source relation remain unchanged. Do not run blanket migrate deploy or mark unrelated history applied to reach this new migration. Its eventual application order, exact target schema, lock effects, backup/restore readiness and migration-history recording need separate reviewed execution approval after login recovery.

### Serializable last-slot experiment

The PostgreSQL 17.11 fixture also uses two independent Prisma clients and Serializable transactions. Both count zero accounts in the same fresh synthetic organization, synchronize at a bounded barrier, and insert different AWS external-account IDs. Exactly one commits; the other receives Prisma `P2034` serialization conflict; final count is one. Distinct IDs ensure that per-account uniqueness cannot substitute for the organization predicate conflict. This validates actual PostgreSQL SSI behavior for the backend's count-and-insert transaction pattern, not its plan resolution, role checks, real AWS verification or end-to-end customer acceptance. The fixture does not retry the losing transaction or increase the cap.
