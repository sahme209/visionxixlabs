## Material gap and chosen milestone

An Airflow deployment approval currently authorizes an execution ID and source DAG run, while its actual destination is read later from mutable environment configuration. A pending action can therefore outlive its original role/region/cluster/service configuration and send an approved restart to the replacement target. The customer approval screen promises exact destination review but renders only the rule name and DAG/run/state. This is missing engineering, independently repairable without access to a customer's Airflow or AWS.

Choose one end-to-end milestone: **server-captured, immutable Airflow service-restart review evidence, displayed and digest-bound in paired approval, with a final current-destination fence before dispatch**. Reuse the existing target snapshot helper, policy/reservation primitives and exact execution claim. Do not extract or copy an approval kernel, add an execution ledger, implement interval correlation, or add a deployment capability. An ECS restart remains a restart of the existing service, not an immutable source/artifact release or verified recovery.

## Frozen server-owned review authority

Define `AirflowRestartReviewV1` for only `actionType: "deploy"`, `requestedOperation: "service_restart"`. Payload includes:

- `schema: "axiom.airflow.restart-review.v1"`, organization ID, execution ID, automation ID and source DAG/run/state.
- Exact **configuration** digest for rule action/repository/ref/source kind/environment/approval requirement/dependency IDs/required source state. Exclude operational fields `lastEvaluatedAt`, `nextScheduledAt` and `updatedAt`: scheduler bookkeeping changes them on each tick and must not invalidate an otherwise unchanged review. Existing claim still fences the currently observed rule revision/enabled state.
- Connection ID, endpoint identity and captured connection revision. No token, credential envelope, DAG conf or task log.
- Target tuple returned by the existing `captureRestartTarget` helper, unchanged. The role ARN is configuration identity, not attested effective AWS permissions or a trusted source artifact.
- Creation time, closed protocol version and digest from the existing canonical hashing primitive. No caller-supplied target/hash, lead ID or best-effort audit entry becomes authoritative.

The scheduler captures this target before producing a restart proposal. In one database transaction it creates the canonical execution and immutable review sidecar. If either fails, neither persists and no success counter/audit claims a usable proposal. Competing ticks rely on the existing unique `(automationId, sourceDagRunId)`; one transaction wins, the other reads the same canonical execution/review and does not create alternate evidence.

Do not recapture or overwrite a target on read, approval or retry. A changed target requires a different future eligible source-run proposal. Historical pending/failed deploy actions without a snapshot cannot be backfilled from current configuration. Existing read-only `none` and pull-request actions retain their current behavior; this does not imply their evidence contract is complete.

A guard validates the canonical parent execution/rule/tenant/source tuple on INSERT and refuses UPDATE/DELETE. Add only the reviewed feature marker/catalog requirements needed to distinguish not installed, ready, drift and unavailable. Do not add scalar fields to existing Prisma models or put this SQL in the automatic migration directory. Proposed SQL belongs under `docs/proposals/airflow-execution-review-v1.sql`; application to production is a separate owner decision.

Readiness uses bounded raw catalog/marker/checksum checks before touching optional table columns. No known feature table/marker means not installed; partial or marked-applied incompatible storage is drift; query failure is unavailable. None permits restart approval or silently downgrades to the old path. Existing ordinary Prisma queries for connections/rules/executions continue to work on old installations without P2022. No pending migration backlog or credential/schema repair is inferred.

The separate strict-correlation proposal should later extend this one canonical execution-review payload/version for frozen dependency evidence rather than introduce a second competing execution evidence authority. ## Claim, final fence and failure/replay semantics

1. Before claim, require authoritative stored review integrity, expected displayed digest and matching current rule/connection/source/target; run existing current approver and dependency freshness checks. No record/hold/provider side effect on refusal. Legacy missing review is a bounded unavailable result; never silently recapture.
2. Claim the exact observed tenant execution/status/attempt and enabled current rule using the existing CAS. Bind the claim to the immutable review digest by re-reading that exact sidecar inside the short transaction. No fourth claim engine or extra operation ledger.
3. Resolve existing repository authorization/source policy and reserve using the **existing stable** `airflow-execution:<executionId>` idempotency key. One execution has one immutable review, so do not rotate keys or release prior unknown-outcome holds to evade conflicts. Reused reservations may only return their existing receipt after review/scope validation; they never cause another dispatch.
4. After claim and reservation, perform a final short database fence: require the same running attempt, enabled/config-matching rule, immutable review, active connection revision, current accepted approver and exact target tuple/revision. Reuse existing capability checks and `captureRestartTarget`/`matchesRestartTarget`. Row locks within this short database transaction may serialize these configuration reads with writing the durable dispatch intent; do not hold a database transaction across GitHub/network IO. A two-client PG regression must exercise a target change at this fence, not merely a pure equality check.
5. Persist the existing dispatch intent only after that fence succeeds, including the immutable review digest for reconciliation linkage. Send **reviewed** target fields, not a newly selected target. Once the provider request may have started, keep existing `needs_reconciliation`/durable-running semantics, retained quota, receipt and no automatic replay. Audit/webhook failures do not fabricate provider failure or free holds.
6. A stale/unavailable final target before intent/provider action is a **confirmed no-write refusal**, not unknown provider outcome. Release only the newly acquired reserved slot, checking release success. Restore the still-bound execution to `pending_approval` with a fixed stale-review error, no scheduled retry and preserved attempt/audit history, using a CAS on the claimed attempt. The old digest remains immutable and cannot execute; rejection remains supported. If release or storage outcome is uncertain, retain the hold/running reconciliation state and report it truthfully. Never claim a released allowance without confirmation.
7. The final check does not lock the remote AWS target or prevent a configuration change after its transaction commits. Describe that residual provider race explicitly; this milestone does not introduce a distributed lock or cryptographic AWS enforcement. Current source branch/tag behavior remains the documented restart workflow contract, not SHA-to-image provenance.
