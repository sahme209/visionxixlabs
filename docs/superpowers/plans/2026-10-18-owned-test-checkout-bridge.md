## Private IPC v1

Use a Unix-domain stream socket in a supervisor-created realpath directory mode0700, with socket mode0600. The supervisor selects the path, checks ownership/type/no symlink, and starts exactly its known worker executable/source. Next receives the path and a cryptographic per-launch channel capability only through its checked server launch binding. The capability is private authentication material, not a Stripe key; never include it in argv, browser output, source, request headers, logs or error details. Establish a protocol-version/runtime/account/org/session challenge handshake before readiness. Missing socket/handshake/marker, substituted path, version drift, stale launch session or wrong capability fails closed.

The trust assumption is the same OS user/supervisor and owned source are trusted. Filesystem permissions exclude other UIDs; this proposal does not claim portable Node SO_PEERCRED verification or protection from a fully compromised same-UID process. Do not use a world-readable /tmp socket, an arbitrary env URL or an HTTP loopback proxy with a bearer capability exposed to the browser.

Frames: four-byte length prefix + UTF8 JSON, strict schema/no unknown fields; max384KiB per frame (enough for base64 of the existing256KiB webhook bound), max16KiB checkout frame, max8KiB response, max8KiB bounded protocol-error response. Close on oversized/truncated/malformed frames before command execution. Raw payload/signature are never logged. Responses use closed enums and explicitly allowed fields; never forward SDK/Prisma errors, raw request/response objects, stack, canonical email/body, secret selectors or protocol capabilities to HTTP/logs. Challenge-authenticated per-launch session, monotonic transport sequence, random request ID and exact command-body digest bind replies; HMAC each frame with the private channel capability or derive separate client/server session keys during handshake. Transport sequence is not Stripe-event or financial ordering. A stale frame/session is rejected before service invocation.

Allowed commands only:

- checkout: actor userId + exact configured organization + clientIntentKey + paid plan + interval; no caller account/price/quantity/email/success URL, canonical request, idempotency key, proof or financial amount. The worker reads current seats/User, derives fixed allowed success/cancel URLs from its launch origin, then calls existing prepare→attempt. Browser input cannot choose a provider operation.
- reconcile: bounded base64 raw webhook bytes + bounded signature. The organization/runtime/account are fixed launch scope, not from body/metadata. Worker calls existing service.reconcile(raw,signature,fixedOrg); the existing adapter verifies local SDK signature before provider retrieval and independently verifies account, intent/proof/contract/collection.
- health/status: non-authoritative launch readiness and, for a currently authorized actor, the existing intent's closed state; no secret, raw canonical request, proof, event payload, payment details or arbitrary SQL/API access. This never turns an unknown intent into success or grants an allowance.

No generic execute/API/mutate/SQL/createPrice/createCustomer/refund/replay-facts command. No command accepts a VerifiedProviderSnapshot, PaidInvoiceEvidence, fake event facts or supplied original proof. Only the unchanged provider/service may produce those. No worker reply can directly write a browser-supplied contract into Next's database.

Concurrency is conservatively one accepted mutating command at a time per worker and a bounded queue of zero: busy returns a closed retryable response before prepare/attempt/reconcile. Browser retries are not automatically enqueued. Ordinary HTTP requests get new transport IDs; duplicate raw webhook delivery must always invoke fresh verification/reconcile, never replay a cached positive IPC response. The existing event receipt/CAS then resolves financial idempotence and fresh-negative projection. Inflight duplicate transport IDs are rejected/observed without invoking twice; transport memory is not a new durable ledger or authority.

## Cancellation, bounded ownership and uncertainty

Browser navigation, canceled HTTP stream or lost IPC response is **not** proof the provider create did not happen and is not the Stripe Checkout cancel action. Once accepted, the supervisor/worker owns the bounded operation even if the browser disappears. Do not simply Promise.race and abandon an SDK request. Existing per-request hard10s/complete-body ownership and webhook aggregate30s stay intact. Checkout has multiple sequential10s reads/create, so do not incorrectly claim a30s total existing bound.

Proposed outer supervisor bounds: checkout90s and reconcile45s, including DB work, with bounded connect/handshake and finite write/backpressure timeouts. Next may return an unavailable/reconciliation result while the still-owned operation finishes within that bound; response cancellation cannot start a second operation or release a purchase fence. On outer deadline or process failure the supervisor destroys the owned channel, terminates the exact owned worker process group, awaits exit/socket cleanup and refuses further commands until explicit fixture restart. OS process termination owns/closes outstanding sockets; the current transport continues to own/destroy its per-request resources during normal abort. No detached unowned request or automatic restart/retry. Synthetic trickle/hang/process-death tests must prove actual child exit and resource cleanup.

Existing durable states provide crash behavior:

- prepare fails before insert: no attempt; any later explicit retry still runs service authority/price checks.
- prepared committed, attempt not claimed: same original intent/key remains; a later explicit same-key request may call existing attempt once. No automatic retry.
- attempted committed, provider response/IPC/local commit uncertain: retain attempted/unknown, return reconciliation_required; never mark unused, release fence, mint new key, retry create or infer proof.
- actual original response stored/session_confirmed but browser URL lost: preserve immutable receipt; do not reconstruct proof, call create again or invent successful URL recovery. Existing service observes/requires reconciliation. A later authentic paid webhook may bind only with that stored proof. No cached reply is independent entitlement authority.
- bound transaction commit/HTTP reply lost: event replay uses existing fresh current verification/CAS, no ledger reset/regrant. Refund/failure/unsupported terms still deprivilege; old positive channel/event replay cannot restore authority.

There is no new Checkout expiry/cancel/replacement policy in this slice. A Stripe-hosted cancel return renders no payment/grant, retains unresolved intent, and does not enable another subscription. Existing durable usage dispatch_unknown/holds/purchases are untouched by IPC disconnect, process TTL or Checkout failure.
