## Chosen source package and alternatives

Build **one inactive executable runtime plus real private intent/claim service** for one restricted non-production ECS rolling-service profile. It uses actual durable current authority/quorum/target/quota state and actual GitHub OIDC verification. Its worker performs bounded native SDK requests and guarded recovery; a separate server observer verifies receipt facts. YAML assets remain outside `.github/workflows`; no public routes, workflow installation/dispatch, catalog/default trust, provider/IAM change or production schema application occurs in this package.

The first profile binds an **already running manually initiated exact GitHub run**. An accepted paired owner/admin selects its run ID as an untrusted identifier; the service independently reads GitHub before admitting it. This avoids adding a dispatcher or pretending a caller-supplied run is authority. The inactive job waits for a server intent before obtaining AWS credentials. A future separately approved API/UI and installed workflow must make this rendezvous customer accessible. A new automatic dispatcher would add uncertain-dispatch/quota semantics and is deliberately deferred. A server-only ECS worker would avoid distributing credentials to GitHub, but would require a separately approved durable execution host and would not establish the requested GitHub-job enforcement.

The deliverable is working internal source and a truthful owned acceptance boundary, not an activated customer release. It cannot be reduced to an empty executor catalog, a gate returning unavailable for every implemented operation, an injected approval-true callback, or relabeling the four-input restart workflow.

## Scope and supported operation

V3 only; `operationId` at most 128 safe characters. One selected environment with tier `dev`, `test` or `stage`; `prod`, promotion, emergency bypass and change-window configurations are unsupported. Deny policies requiring unproved test, CODEOWNERS, PR, ticket, tag or prior-environment facts. Current accepted owner/admin, live paired session, current `deploy:execute` and `connections:manage`, allowed commercial access and current quorum are required. The GitHub actor is audited but is **not** inferred to be the paired Axiom user or a voter.

Same public tenant repository for source and caller workflow. Require `manifest.executor.workflowSha === manifest.repository.sourceSha`; the current receipt matcher binds the executor run's source SHA to that artifact source. A separate reusable runtime job may have another independently pinned SHA. A caller/head commit B cannot be reported as artifact source A. Numeric repository ID, owner ID, exact path/ref/SHA, caller workflow identity, reusable identity and run/attempt must match configured reviewed bytes and independently obtained GitHub state. Missing exact run identity or unsupported split-commit execution is unavailable.

AWS commercial partition `aws` only initially, one account/region, existing enrolled role ARN equal to selected target role, one ECS service with deployment controller `ECS`, scheduling `REPLICA`, Fargate launch mode, `awsvpc`, Linux x86_64, desired count 1–4, one essential container and one associated ALB target group of target type `ip`. No service autoscaling, external writer, blue/green controller, service/task-set mutation, task registration, image push, migration or repository hook is supported. Both pre-existing ACTIVE task revisions must share family/container/port, use exact same-account/region ECR digest URIs and a single-platform OCI/Docker image manifest. Image indexes are unsupported in this first executor profile; no parent-index/child-runtime digest equivalence is invented. The genuine GHCR index proves the separate crypto boundary, not this execution profile.

Initial service state must have exactly one completed PRIMARY deployment at the approved baseline, running=desired, pending=0. Configuration invariants (controller, count, network, task/port, target association and ALB health-check settings) are captured and fenced. Actual IAM/OIDC trust, Fargate pull permissions, network reachability and deployment timing remain external assumptions until separately tested against an authorized account. No source operation modifies them to make acceptance pass.

## Reviewed executable closure

Store an actual worker entrypoint and generated standalone bundle plus caller/reusable YAML assets under `lib/releaseops/ecsReleaseV2/executors/candidate/`, not `.github/workflows`. The worker contains the real protocol, authority client, JWT checks and SDK operations; it is not a script that delegates to an unspecified future executor.

Use no third-party GitHub actions in the candidate job. The only reusable reference is an exact 40-hex commit. Bootstrap verifies exact worker-bundle SHA256 and exact Node executable bytes/version/platform before running; it must refuse an unavailable or different runtime without installing or selecting another one. Bundle the SDK/JWT dependencies from the exact lockfile. Retain a canonical closure containing caller/reusable Git blob identities and content hashes, worker/source/bundle hashes, Node version/binary digest, dependency lock digest and all immutable references. Freeze runtime bytes first, then render the inactive YAML against those actual artifact/commit hashes; unresolved/mutable/self-referential pins fail the acceptance gate. Public immutable artifact distribution is a later deployment prerequisite; do not invent a published URL or claim hosted availability.

A concrete owned runtime candidate observed read-only is Linux x86_64 Node v24.19.0, 125,989,464 bytes, SHA256 `bc17c508ffeed0ec622934f9b7fa72f8e78da65350e63c3eceb56fa688aa5e12`. This is an **owned acceptance pin**, not proof that GitHub's runner has identical bytes. Bootstrap still trusts the GitHub runner host and its transport/hash tools; source hashes do not withstand a compromised host. No untrusted checkout, install, build, repository code, service container or preceding step is allowed in the authenticated job.

`ReviewedExecutorConfig` is a detached server-only deployment configuration: exact caller and reusable identities/bytes/closure digest, fixed authority origin/audience, allowed GitHub environment, trust/review expiry and independently reviewed writer-control assumptions. It has no request-selected flags or production default. A hash checks integrity; source/config review and deployment establish who authorizes it. The actual candidate closure must be independently reviewed before any catalog entry or production use.

## Identity and private authority protocol

Proposed private constructor: `createEcsExecutionAuthority({ repo, reviewedConfig, githubReader, currentProviderReader, clock, random })`. Production readers close over existing scoped token/vault services; HTTP JSON cannot supply facts, readers, roots, authorization callbacks or configuration. No Next route is mounted. An internal `handleExecutorAuthority(Request): Promise<Response>` may be mounted **only by the owned loopback fixture** in this package.

- `bindExecutionIntent(principal, {packetId, runId, runAttempt})`: principal comes from the existing paired resolver, never JSON. Requested IDs are candidates. Load current packet/repository/environment/account/policy; validate current review and independent GitHub/AWS facts; capture complete context before and after remote reads; then in one final Serializable transaction recheck all context/quorum/target/config, reserve one current allowance row, bind the exact run, and acquire the canonical physical-target slot. No provider mutation.
- `redeem(operationId, githubOidcBearer)`: verify signed GitHub identity, independently read the current exact run/attempt and compare to the stored binding; current database/context/config checks precede claim CAS. First success binds worker ownership and generation. Replay returns scoped status, never another write permit or quota row. A different run or rerun attempt is denied.
- `permit(intentId, expectedRevision, phase, githubOidcBearer)`: current quorum, initiator session/capability/commercial access, complete context/config/target and operation lifetime must still match. Independently verify phase preconditions, then append a single write-intent record and advance CAS before returning one short-lived permit. Rollout and recovery each have at most one permit, never a retryable provider token.
- `report` receives bounded worker observations, not trusted receipt evidence. It may record a provisional exact deployment ID/result under the same run/phase/version; it cannot approve, clear uncertainty, release a target hold or mark health proved.
- `reconcile(principal, intentId)` uses a currently authorized paired owner/admin, actual independent GitHub/provider reads and existing receipt matching. It cannot request a mutation. A new authorized reader may reconcile an old initiator's expired session; that does not reauthorize the old worker.

Use the already locked `jose` 4.15.9 only after promoting that exact version to an explicit direct dependency, subject to root review; no installer or version resolution is part of design. Use `jwtVerify` with a locally constructed JWK set from a bounded fixed `https://token.actions.githubusercontent.com/.well-known/jwks` read, not automatic discovery or caller URLs. RS256 only, required `kid`, maximum JWT 16 KiB and JWKS 128 KiB/16 distinct keys, 5-second request, no redirect/compression, no `jku`/`x5u`/unsupported critical headers, and fail closed on refresh failure. No NextAuth decode-only helper is authority.

Require exact issuer `https://token.actions.githubusercontent.com`, exact application audience, exp/iat/nbf integer lifetime at most ten minutes with at most 30-second skew, and exact `repository_id`, `repository`, `repository_owner_id`, `ref`, `sha`, `workflow_ref`, `workflow_sha`, `job_workflow_ref`, `job_workflow_sha`, `run_id`, `run_attempt`, configured environment and reviewed custom subject. Missing reusable claims fail. Cross-run/tenant/attempt/audience tokens never claim an operation. Fresh tokens for the same verified job may renew authenticated reads; phase CAS prevents bearer replay from issuing another mutation permit. Store token/JTI digests and expiry only; never raw JWTs or credentials.

The worker separately obtains an `sts.amazonaws.com` audience GitHub token **after** app claim redemption, checks the same job identity, and calls actual `AssumeRoleWithWebIdentity` for the fixed manifest role with a restrictive session policy and 900-second session. All SDK clients use explicit returned credentials, server-derived public endpoints, no ambient credential/endpoint chain and maxAttempts=1. GetCallerIdentity must match exact account and assumed role before further work. AWS trust must independently require the reviewed numeric repository/custom subject and pinned reusable identity. Default repository/ref trust does not establish that guarantee; missing operator-reviewed customization remains unavailable. The code/config does not create GitHub subject templates, AWS IAM trust, role grants or provider access.

The GitHub platform's token-request URL/bearer environment is a privileged platform capability, not an application URL parameter. The bootstrap must constrain its HTTPS host/path to the reviewed GitHub platform policy and refuse redirects; no prior untrusted step can replace it. Actual GitHub OIDC claim shape and custom-subject formatting remain a live-provider acceptance dependency; synthetic tokens do not establish those settings.

## Fresh context and legacy review packets

A historical unwrapped ReviewFacts packet and an old checkpoint are not execution authority. Before producing a new intent, the real admission path must **freshly revalidate** immutable build/provenance, the reviewed executor bytes and AWS target/task/image facts through existing independent readers, then compare with the packet using the existing matcher. There is no `factsVerified: true` or authorization-true input. Missing exact ECR proof/configuration/reader capability produces unavailable and no intent. The newly completed direct profile remains unchanged.

Store a strict fresh execution context in the new intent rather than silently rewriting the old packet. It includes the complete `ReviewContextV1` fields in d6628e4e: initiator desktop ID/user/org/issuedAt/expiry/revocation; current membership acceptedAt/role/updatedAt; repository ID/provider/owner/name/revision; selected GitHub installation including accountType/repositorySelection with deterministic installedAt/ID tie-break; environment tier/policy/revision; complete enabled branch policies bounded at 100; current policy and voter/decision-set digest; packet/evidence digest; existing target/connection snapshot; trust/download config and actual executor closure/review digests. No ciphertext or heartbeat/device display data is stored. Capture before remote reads, compare after, then reread inside final transaction before create **and replay**. No provider IO occurs inside the transaction.

Production admission therefore requires the real current-context/provider composition seam to be implemented in this package using the already available readers; it must not be an unresolved injected callback. Mapping checked results/context may extend reader results additively, without changing proof semantics. Selected unsupported policy facts remain denied. No source claim of a complete real ECR happy path is possible with the presently available genuine GHCR fixture.

## New durable records and atomicity

Propose three appended models plus source migration text, **not database application**:

| Record | Exact responsibility / constraints |
| --- | --- |
| `EcsReleaseExecutionIntent` | Global ID; organization/environment, packet/checkpoint, operation ID, manifest/evidence/policy/decision/context/executor digests and strict context JSON; initiator user/session; exact numeric caller repository/run/attempt/caller+reusable workflow identities; quotaReservationId; expected target/connection; state, revision, claimedAt, leaseExpiresAt, operationExpiresAt; phase write-intent/result identities; current lease generation. Unique organization+operation and repository+run+attempt; scoped packet FK; no secrets. |
| `EcsReleaseTargetLease` | Primary key is canonical physical target digest (partition/account/region/cluster ARN/service ARN), not role/environment/org. One current intent, generation/revision and state; unique intent. Prevents two cooperating organizations/repos/roles from acquiring the same physical target. Busy responses reveal no foreign IDs. Expiry denies permits but does not free the slot. |
| `EcsReleaseExecutionEvent` | Append-only intent+sequence with closed phase/event kind, safe reason, observed time, bounded sanitized evidence/digests and claim revision. Unique intent+sequence; no JWT, STS keys, raw task definition, environment/secret values or raw provider errors. |

Use existing `DeploymentExecution` for exactly one monthly allowance count, with idempotency key `ecs-v3:<operationId>` and unchanged source attribution. Link it to the intent in the same Serializable transaction. It remains an observation/quota record, not the claim. The first profile retains the allowance once a verified existing run is bound, including denied/failed/unknown attempts; recovery and reconciliation add no count. No clock-based refund or key reuse. New scoped foreign-key indexes may be added where required; do not change historical row interpretation. Keep legacy reservation/release/settlement behavior intact.

Every claim transition is CAS on intent ID/org/revision/state plus lease generation. Serialization failures return unavailable/uncertain and authorize no call. A response lost after a commit is not a negative commit proof. Read status can establish current state, but a previously issued write permit is never minted again. Successful no-op status replay still rechecks current authority before disclosing details. Configuration changes, changed voter revision/role/quorum, target/connection replacement, revoked session, expired trust, exhausted/invalid quota or context mismatch prevent a new permit and require new review/admission as applicable.

## State, uncertainty and recovery

`bound -> claimed -> rollout_intent -> rollout_observed -> rollout_verified -> awaiting_run_finalization -> succeeded` is the ordinary path. `rollout_observed -> recovery_intent -> recovery_observed -> recovery_verified -> awaiting_run_finalization -> failed_recovered` preserves rollout failure. An ambiguous write, lost deployment identity, cancellation during IO, stale authority or failed receipt persistence enters `outcome_unknown`; no automatic replay, replacement claim, target release or time-based cleanup follows. Denied/no-write outcomes are distinct; a slot can close only after authoritative proof no permit was issued or a supported terminal observation. The immutable operation key remains consumed.

Permits expire after 10 seconds; claim ownership requires a current check at least every 30 seconds and has an absolute 600-second operation ceiling, also capped by manifest/config expiry. Each mutation is sent once, with SDK retries disabled. Stale/expired permits, an unexpected revision or a failed authorization check means zero further writes. Cancellation aborts request/body reads and does **not** imply rollback authorization. A timed-out request might already be accepted by ECS.

Recovery requires fresh current authority for the same approved manifest/baseline, current target lease, known exact rollout deployment ID, and independent observation that this owned rollout still controls the service. The service's current PRIMARY task/ID must match the known rollout, and no foreign/concurrent deployment or changed config may be present. Restore only the preapproved baseline ARN; never discover a replacement baseline from whatever happens to be current. A lost UpdateService response without a durably known deployment ID remains unknown, even if the service happens to reference the proposed ARN. Changed/lost identity or revoked votes/session/config forbids recovery; manual separately authorized incident recovery remains outside this package.

An issued permit and STS credentials are not instantly revocable. Current authority is proved at the transaction, not at all future instants. The reviewed worker checks again before IO, but the last-check/write interval still exists. No automatic rollback on cancellation, worker restart or GitHub rerun attempt.

## Actual SDK execution and deployment-owned health

Worker preflight: exact STS identity, baseline service state, both task registration projections/images, ECR manifest existence/media type, target-group association/configuration, run/claim/context and current target generation. Request only ECS UpdateService with exact cluster/service and preapproved taskDefinition; no force-new-deployment, desiredCount/config/network/tag overrides or task registration. Verify the response and then an independent DescribeServices read before retaining the exact new deployment ID. A successful HTTP result alone is not rollout success.

Polling uses DescribeServices, ListTasks(serviceName, RUNNING), DescribeTasks and DescribeTargetHealth. Deny pagination, more than eight task ARNs, duplicate identities and any unknown/error shape. Only tasks whose exact taskDefinitionArn and `startedBy` equal the known owned deployment ID may contribute. Require matching account/region/service group, RUNNING state, the single expected container/image URI and resolved single-platform imageDigest, and an unambiguous awsvpc IP/container-port tuple. ALB target IDs/ports must be exactly those owned tasks; healthy targets from the old deployment never count. Require desired count and minimumHealthyTargets to agree in this first profile.

The target-group health-check protocol/port/path/matcher/threshold/time settings must match a reviewed server configuration and stay unchanged through the operation. This proves **deployment-owned configured ALB health**, not arbitrary application semantics, user journeys, migrations or data rollback. Require consecutive passing samples for the manifest stabilization interval, with any failure/unknown resetting the interval. Restrict timeout to at most 240 seconds, stabilization to at most 60 seconds and timeout >= stabilization+5; poll every five seconds, maximum 49 samples per phase. Recovery performs its own complete stabilization/health interval for the baseline's new recovery deployment ID.

Fixed endpoints only for regional STS/ECS/ECR/ELB; every native SDK request max five seconds, no retry/redirect/compression, pre-Smithy response cap 256 KiB and aggregate provider budget 16 MiB/512 calls for the complete operation. Public errors are fixed closed reasons and raw errors never enter receipts/logs. Reuse the existing streaming bounded handler and add a local ELB endpoint construction branch without weakening the existing AWS read-only adapter. All clients/streams/timers are destroyed on terminal exit.

A separate server-owned scoped broker observer repeats identity/deployment/task/ALB checks; worker reports are provisional input, not `TrustedReceiptEvidence`. Credentials remain inside broker/worker stacks and are never returned through authority responses. A narrowly added broker-owned observation entrypoint may reuse the existing private role assumption, with no generic credential callback. Finalization independently reads the exact GitHub run/attempt and configured workflow SHA/conclusion, constructs existing ExecutionReceipt/TrustedReceiptEvidence and calls the existing matcher. Rollout needs run success; recovery needs original run failure. Run in_progress/unknown or missing independent observations stays unproven and retains the hold. Legacy DeploymentExecution status alone never finalizes this claim.

## External-writer and revocation limitation

ECS UpdateService has **no expected-deployment CAS field**. Database leases and GitHub concurrency coordinate only participating Axiom workers. A fresh DescribeServices check does not exclude an outside mutation immediately afterward. The supported profile therefore requires independently reviewed exclusive-writer controls over the exact service/role and pinned OIDC workflow, recorded in server deployment configuration with a review expiry; no request boolean asserts exclusivity. Actual account-level writer-control/IAM review remains external acceptance, and API observation cannot prove all effective writers absent. Even under the assumption, detected drift halts writes and recovery. The residual last-read/write race must remain explicit in source/docs and no receipt promises exclusion of outside writers or rollback of data/secrets.
