# Axiom Governance Intelligence — incremental MVP design

Status: proposed local implementation; not approved or active. No customer discovery, infrastructure change, paid AI call, migration or deployment is authorized by this document.

## Intent
An organization connects existing GitHub/AWS read access and uploads policies. Axiom explains observed controls and gaps, proposes an evidence-backed baseline, and lets an authorized administrator approve an immutable version. Runtime decisions are deterministic, scoped and independent of model text. Discovery never modifies customer infrastructure or expands its own access.

## Existing architecture and reuse
- `lib/governance/policyEngine.ts` and policyModel already provide typed action rules, deny precedence and autonomy ceilings. Reuse a strict validated subset through the admission adapter. The current evaluator defaults allow on no matching rule, and its `allowed` flag is true for require_approval: neither is an execution receipt. The adapter explicitly requires a supported action, covered scope, compiled rule set and satisfied exact human approvals.
- `lib/releaseops/policyEngine.ts` already evaluates active release rules as pure functions. Its legacy unknown-rule behavior skips rules; the new admission boundary must explicitly deny unknown/uncompiled approved rules, without silently changing legacy release semantics.
- `policyProposalEngine.ts`, `policyProposalResponder.ts` and Prisma PolicyProposal/PolicyRule/PolicyViolation already support proposals, operator decisions and violations. Reuse their inbox and audit conventions. They do not by themselves provide immutable, source-bound policy revisions or universal runtime enforcement; never label those capabilities as present.
- `lib/policy/policyEvaluator.ts` and policyRegistry are a platform safety catalog, not a customer-editable authorization system. Preserve these non-overridable limits.
- Existing ticket/action approval stores implement current authority, exact version binding, independent review, durable claim and audit history. Reuse their approval mechanisms; no parallel self-approval or prompt-based bypass.
- Existing GitHub fixed-read readers and AWS IAM/infrastructure discovery modules are candidate adapters, not proof that a given customer granted access. Use current org-scoped connection verification before each bounded read. Existing AWS denial receipts are not retried.

## Approach
Extend the existing governance area with an evidence-to-proposal pipeline and a common deterministic admission adapter. A separate AI product would duplicate approvals/audit; automatically translating prose into executable rules would hide ambiguity. The recommended approach keeps uncertain extraction advisory until a human maps it to a supported typed rule.

## Contracts and boundaries
1. **Evidence snapshot:** tenant ID, source connection ID/revision, collector version, selected repo/account/region, immutable content hash, observedAt, freshness deadline, completeness, redacted facts and precise source locators. Partial/denied pages are recorded as unknown, never absence. Same bytes from different tenants are separate records. Source code, documents and provider responses are untrusted data, never instructions.
2. **Read-only collection:** GitHub allowlisted GETs for repo identity, protections/rules, workflow source and permissions; AWS explicit SDK list/get/describe commands through an existing verified assumed role; uploaded UTF-8 text/Markdown first. Bounded file sizes/pagination/timeouts and cancellation, no external links/SSRF, executable content, credential retrieval or automatic provider retries. PDF extraction is a later adapter unless an existing bounded parser is verified. No new grant is requested automatically.
3. **Proposed requirement:** exact evidence spans and hashes, interpretation, confidence, known limitations and conflicts. Deterministic known-control extraction first. Optional model assistance is opt-in, redacted, budgeted and cannot create authority. Ambiguous requirements remain unresolved and cannot compile.
4. **Versioned baseline:** immutable revision digest over org, parent revision, typed rules, scopes, source snapshot hashes and compiler version. Reuse existing policy proposals and audit history, with an additive immutable revision storage seam because mutable PolicyRule rows alone cannot prove historic approvals. Proposed schema/retention details must be reviewed before any migration. The immutable record contains revision ID/digest, org and explicit enrollment scopes, parent revision ID, compiler version, evidence hashes, typed rules and creator; activation points to one revision per org/enrollment scope. A human approval binds its exact digest, reviewer authority and decision time. Atomic compare-and-swap activation supersedes the prior active pointer and emits an audit event; concurrent activation refuses on stale parent. Revocation disables the active pointer without deleting historic revisions or approvals. A mutation binds the expected active revision and rechecks it before claim and before write; supersession/revocation makes old plans refuse. PolicyProposal acceptance can produce a draft, but its mutable PolicyRule upsert never activates or authorizes the baseline. Any edit creates a new revision and invalidates earlier approval. Agents cannot approve or widen their own permissions.
5. **Closed typed policy rules:** require independent approval, require verified deployment evidence, allow/deny fixed actions, and restrict repository/environment/resource/actor scopes. Deny overrides allow; conflicts and unsupported rules deny execution in governed scopes. These rules only narrow current provider/workspace rights. No wildcard expansion, dynamic code or natural-language evaluation at runtime.
6. **Admission adapter:** normalize actor, org, action, environment, repo/resource and immutable plan digest; verify active approved revision, source freshness and current authority; intersect provider rights, platform safety, existing executor guards and customer rules. Unknown action/resource, missing policy version/evidence, tenant mismatch, revocation, conflict or evaluator failure denies the governed execution. Reads and recommendations remain separately scoped. No LLM response can change a decision.
7. **Integration:** wire adapter before claim and immediately before mutation in Agent, repository actions, Bot, deployments and integration executors. Roll out surface by surface with explicit coverage receipts. Enrollment is explicit per organization/repository/environment/resource scope. Every mutation in an enrolled scope must enter through a covered executor and the adapter; a missing/unintegrated/unavailable executor refuses there. Coverage registration is validated before enrollment, and unknown routes/actions are denied. Unenrolled scopes preserve existing behavior with clear disclosure; no universal enforcement claim is made. Enrollment and activation require the same exact administrator-reviewed revision. No enforcement flag is enabled by local work.
8. **Drift:** compare versioned snapshots with approved baseline; classify verified drift versus incomplete/denied reads, preserve old evidence, recommend remediation. No infrastructure changes. User-triggered collection first; scheduled discovery only after separate cadence/access/cost review.
9. **Audit:** existing audit stores record discovery, extraction/compiler versions, exact approval/rejection, supersession, bounded exceptions, admission decision and executor outcome. Evidence availability and redaction are explicit. No secret/provider payloads in logs. Retention and deletion need an organization setting and implementation review; do not invent compliance claims.

## MVP workflow
Governance → Sources → select existing GitHub repo/AWS account or upload document → read-only scan → observed controls/gaps/unknowns → proposed baseline diff with source citations → authorized human review → exact approved revision → separately enabled runtime coverage → decisions/drift history. Existing product navigation and approval inbox are reused; no new standalone dashboard.

## Local implementation sequence and acceptance
A. Typed evidence/requirement/baseline/decision contracts and pure compiler/evaluator with tenant isolation, conflict and unknown-action denial tests.
B. Bounded discovery ports and mocked GitHub/AWS/document collectors; proof that mutation commands/requests, external URLs and incomplete-as-absent results are rejected.
C. Immutable revision storage and exact approval composition using existing governance/audit mechanisms; isolated database tests for stale approval, revocation, races and immutable history. No production migration.
D. Connect existing execution admission seams with deny-before-claim tests; preserve existing one-attempt and independent approvals. Verify each listed surface explicitly.
E. Native/web governance views for evidence, source citations, proposal diff and deterministic reasons; read-only local journeys. No live customer reads or effects without separate authorization.

Completion means demonstrated source evidence, review, enforcement and audit across named surfaces, not merely generated prose or a mocked screenshot. Local, database, native and provider evidence stay distinct.

## Remaining external gates
Design approval under the user's validation-first rule; specific permission for any schema activation/deployment; genuine administrator decisions; customer-authorized source scopes; live acceptance. This design grants none of them.
