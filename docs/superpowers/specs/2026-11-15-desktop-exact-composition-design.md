# Desktop Exact composition

The owner rejected the previous desktop preview as the old app with different colors. Their selected reference remains Exact: warm black, deliberate typography, original painted framing, white primary actions, restrained neutral controls and clear page composition. The latest instruction authorizes applying this to the desktop, finishing website and desktop validation, then one green PR/merge and one Vercel deployment, followed by remaining work starting with Governance. It does not establish missing runtime evidence or authorize enabling incomplete Governance.

## Selected implementation direction

Recompose the actual application, keeping its current React/Vite/Tailwind stack and operational behavior. Palette-only changes have already failed owner acceptance. A marketing page inserted into every operational workspace would consume editor space and obscure real states. The chosen implementation uses a distinct application shell and editorial Welcome composition, with the same quieter hierarchy carried into the real workspaces.

These concrete layout choices are implementation decisions within the owner's Exact direction, not claims that they separately approved an unseen screen. Their repeated instruction is to execute, use judgment and show the result; do not add another abstract design questionnaire.

## Composition

- Shell: a 200px navigation rail, 60px toolbar and inset opaque working surface with 12px corners. One brand location. Keep navigation order, eight destinations, drag/no-drag regions, commands, split editor and verified-access details.
- Welcome: replace the narrow vertically centered list with a broad asymmetric introduction. Regular 48–56px heading, readable introduction and a white **Open Agent** action on the left; original painted landscape in a distinct, crisp frame on the right. No duplicate body logo, fake code, activity totals or provider outcomes.
- Below the introduction: three substantial destination cards for saved Bot tasks, release planning and batch operations. Each retains exactly its existing navigation callback. Opening a workspace must never execute work.
- Agent/Bot: a clear conversation/context/composer hierarchy inside the working frame. Preserve history, evidence, recovery and settings controls; no automatic AI request.
- Repositories: editor remains dominant, with a distinct scope toolbar, file navigation and review area. No oversized marketing heading above the editor.
- Releases/Batches/Apps/Docs: shared 32–36px regular page headings, 14–16px descriptions, deliberate section spacing and consistent solid panels. Current selection and real success/warning/error states remain distinct. No status is inferred from styling.
- Settings: its own inset frame, section navigation/search and readable grouped controls. No changes to saving, sign-out, credentials or access.
- Artwork belongs to Welcome/pre-auth framing. Operational canvases stay opaque and quiet. Reuse Axiom's original painted-basin asset; no new asset purchase, dependency, font or icon library.

## Acceptance

Show representative real frontend compositions: Welcome, Agent/editor, Releases, Apps and Settings, in dark/light and short windows. The owner must be able to see a structural difference from the rejected screenshots. Static synthetic captures must remain labelled; they are not an installed-app or real-account test. Do not use fake business data in a real workspace.

Keep every handler, capability check, pending/unknown state and genuine status color. Keyboard targets and focus must remain visible; short windows must scroll; artwork must never reduce text contrast. Respect reduced motion and compact/split editor constraints.

Do not mutate frozen inputs while the approved website pointer review is running. Finish and close that review first. Then implement and validate the desktop changes, update the internal demo/help evidence, independently review the actual diff, and complete the necessary builds/rendering before release selection. The prior desktop build is historical once this redesign changes its inputs.

PR, merge and deployment remain conditional on relevant checks, no bypass, no bulk staging of local recovery/cache inventories, and the actual production release procedure. Governance and other master requirements remain open after this visual release.
