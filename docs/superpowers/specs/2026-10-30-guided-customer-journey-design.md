# Guided customer journey and consistent branding

User direction: connect current features into a clear readiness → independent review → verified outcome → recovery flow. User selected this work while the Mac is locked and asked for no routine design checkpoints. Reuse current product architecture and controls; this is presentation/navigation over existing records, not a new approval or enforcement system. The brainstorming opt-out exception applies to the delegated implementation choices. No new grants, schema, provider operations or deployment are included.

Approach: shared deterministic presentation model and accessible panel, integrated into existing release and exact-action screens. This makes the existing controls easier to follow without introducing a parallel workflow or an aggregate approval authority. A separate wizard would duplicate state and was rejected; a global approval service is larger and changes governance boundaries, so is deferred.

Every saved plan shows its next step, responsible actor, four stage summaries and a precise recovery explanation. Unknown/dispatching outcomes take precedence over readiness and approval; confirmed receipts alone establish completed provider outcomes. Expired unused plans require fresh review, consumed attempts never offer resend, closed Axiom requests never imply deployment success, and PR approval never implies deployment authority. Display errors/stale observations explicitly. Buttons navigate to existing exact controls or load saved observations; the journey itself never writes, approves, executes, retries, or changes authority.

Desktop: release request context retains its existing facts and gets next-step guidance; exact ticket and Teams/Linear actions show the same journey vocabulary alongside their existing controls. Web: authenticated Control overview provides the same four-step entry guidance and existing governed destinations, with no invented progress/status. All routes retain current authentication/membership checks. Unknown/missing evidence stays unverified.

Branding: replacement is a user-supplied white triangular mark with transparent background. Existing purple/cyan node mark is explicitly rejected. Locate and confirm the exact source before substitution; do not invent a replacement from the description. Once identified, one canonical source should feed website navigation/auth/footer/favicon and desktop sidebar/boot/window/Dock/installer icons. Generated platform assets are reproducible derivatives; distinguish monochrome transparent in-product logo from legibility requirements of platform icons. Do not overwrite immutable0.1.21 installers.

Verification: meaningful state-table tests, rendered navigation/owner/recovery tests, stale/uncertain/expired cases, strict type/build checks, final review. Native visual acceptance waits for Mac unlock. Website/app publication remains one later reviewed batch under existing cost/security constraints.
