# Candidate: restriction before Node, authenticated live launch origin

Status: design only; implementation and execution of this changed boundary require validation. No profile, mount, native load or identity is authorized here. Canonical availability stays unavailable. This replaces the failed post-Node VM-classification mechanism, not the original trusted-localhost threat model or same-artifact acceptance gates.

## Why this is the smallest useful pivot

NoWrite installed but retained writable descriptors still worked. Public VM observations cannot safely distinguish retained shared mappings from runtime-private state: known MAP_SHARED file and POSIX shm mappings presented SM_PRIVATE; BASIC_INFO.shared was false for them too. The conservative fix now refuses all maximum-write regions, including ordinary Node runtime regions. More shape exceptions cannot establish capability closure.

Move the fixed restriction into a tiny trusted native bootstrap **before** Node starts. Its exec replaces the bootstrap address space, so no bootstrap writable mapping is intentionally retained. Node startup then occurs under the already-installed restriction; it must not receive inherited write-capable file handles. This hypothesis still needs actual same-artifact evidence: the installed sandbox header does not itself establish exec persistence, Node compatibility, or safe handling of shared mappings opened after restriction.

## Fixed source flow (candidate, not implemented)

1. A reviewed native broker, bootstrap, packaged Node, canonical CJS/reader, verification helper and compiled application/consumer are members of one closed release package on the actual readonly sealed image. Broker validates its own dynamic code against the pinned release requirement and validates the signed closure/readonly root. Signing identity authenticates native code; closure hashes authenticate files, neither substitutes for the other. No mutable workspace fallback, external module, loader path, update path or caller-selected executable exists.
2. Broker accepts only its fixed internal launch operation, not arbitrary argv/env/cwd/FDs or caller manifests. It starts the exact bootstrap with fixed cwd/environment, readonly `/dev/null` fd0 and owned output pipes fd1/2. Close-on-exec-default with an explicit allowlist removes all other inherited descriptors. Native bootstrap is single-threaded and has no caller callbacks, dynamic plugins or app imports. It verifies its actual image/root/Node/CJS closure again and closes any unintended descriptor before installing the restriction; unknown closure or handoff refuses.
3. Bootstrap calls exactly `sandbox_init(kSBXProfileNoWrite, SANDBOX_NAMED, &error)` once, frees its error, and exits on any failure. Only success reaches one fixed `execve` of exact packaged Node and canonical CJS main with fixed clean environment/argv. No shell, fork-without-exec, alternate profile, flags-zero policy, temporary-write exception or retry. Successful exec preserves the PID while replacing address space. Actual sandbox persistence is a qualification question, not inferred from the PID.
4. Node starts under this boundary. Before app imports, the original canonical CJS performs main/worker/cache/loader/closure/readonly-root checks. A small fixed native verifier is the only allowed native load; it does not install a profile or export an initializer/boolean. It can only complete the bounded origin handshake described below. Any error refuses before application import/private lexical state.
5. After both the canonical local checks and the live authenticated origin handshake succeed, only this actual canonical main module may establish its private lexical capability. The same cached module reader is consumed by the exact compiled store/transport. Direct import, worker, duplicate path/module, IPC value, copied helper or new process cannot initialize it. The native helper exports no reusable proof, signing digest, constructor or public identity variant. Private identity still grants no provider authority.

## Live origin authentication: necessary changed trust boundary

A PID, environment nonce, descriptor number, parent JSON, signed manifest or package digest alone is insufficient. Dynamic code signing verifies running native code; it does not verify a Node script or prove sandbox ancestry. The candidate therefore needs a **live** fixed native broker plus its trusted spawn state, not a detached parent receipt.

- Broker creates an owned, short-lived local listening endpoint before launching. The child establishes a **fresh connection after exec**, using a locator only. Locator/nonce values are not authentication. Do not assume inherited socketpair peer metadata identifies its post-exec holder; descriptor forwarding and creation-time identity must be tested.
- Both native endpoints obtain actual peer audit tokens from the socket using the public LOCAL_PEERTOKEN option, then select the running guest with SecCodeCopyGuestWithAttributes(NULL, kSecGuestAttributeAudit, ...) and validate using SecCodeCheckValidity with the pinned exact release requirement. Unsupported token/attribute/value/flags, missing validity or ambiguous identity refuses. Bare UID/PID equality, ad-hoc metadata from the peer and static-path lookup are not substitutes. SecCodeCopyStaticCode explicitly lacks a secure filesystem-origin guarantee and is not the trust anchor.
- Broker additionally binds the connection to its own unreaped launch slot: exact spawned child, current post-exec audit identity/process generation, expected packaged Node dynamic identity, fixed launch operation and original lifetime. An external process running the same signed Node cannot join a slot; a peer-supplied PID cannot create one. Parent exit/reparenting, child exit/exec again, PID reuse, second connection or missing generation evidence refuses.
- Child verifies the broker's running exact native code, not a path string. Broker must be a fixed, reviewed implementation whose only successful slot path executes the restriction-first bootstrap. Authentication of arbitrary signed Axiom GUI code or a generic signed command runner is insufficient. A valid broker may not be pointed at an untrusted package or asked to attest an existing process.
- A fresh two-way challenge binds the current connected endpoints, slot and canonical child check to one startup. It cannot be replayed over another connection. The connection remains live through private initialization and the consumer's authority boundary; disconnect, slot revocation, process change or unverifiable freshness refuses. No serialized transcript is accepted as identity. The original one-attempt authority and provider checks remain separate.

This is a new trust dependency: canonical same-module initialization would rely on a kernel-authenticated **trusted launch origin**, instead of proving restriction installation solely inside the canonical initializer. The original same-module requirement is retained, but its prerequisite mechanism changes. It needs explicit design approval and actual evidence; the current module must not begin accepting broker IPC on this document's authority. If audit-token identity after exec or launch-slot generation cannot be securely bound through supported APIs, this candidate is unavailable, not downgraded to parent JSON/PID.

## First bounded qualification and knockout conditions

Before another full application build, prepare an inspectable bootstrap/broker/verifier source artifact and exact fixture plan for separate approval. First answer whether fixed NoWrite-before-exec actually permits exact packaged Node startup while refusing post-exec filesystem write opens and shared-file/PSHM maximum-write capabilities. No constructor/profile execution occurs merely by preparing it.

After approval, one owned readonly-image qualification must run the actual compiled package and actual same-module consumer. Preserve the previous retained-FD/profile failures as immutable controls. Required evidence:

- Original retained writable FD and substituted regular-file stdout controls are absent/refused after the clean handoff, including deliberately leaked high descriptors; stdin is readonly `/dev/null` and output only owned anonymous pipes.
- Under restriction-first Node, path write/open/truncate/rename/unlink/metadata attempts target only the owned real image backing file and hardlink alias; independent bytes/inode/mode observations remain unchanged. Actual mounted root is readonly; permission bits alone do not pass.
- File MAP_SHARED and PSHM RW or currentRO/maxRW mapping acquisition after restriction, including closing the FD before use, cannot create a backing-write capability. Test actual write/upgrade effects on owned seeded data. If NoWrite permits a dangerous shared mapping or fails across exec, stop: this mechanism fails, no new exception or repeat profile.
- Exact legitimate Node/CJS/compiled consumer succeeds under the same artifact. No toy text-file result, source-only observer, signature-only result or generic sandbox boolean qualifies it.
- Fresh channel and dynamic guest-code identity are exercised with correct broker/child and attacks: arbitrary Node script, separately launched same signed Node, copied broker, wrong release/package, forged locator/PID/JSON, inherited/forwarded endpoint, replay, parent exit, second connection, child re-exec/PID reuse, helper direct call, worker/duplicate module/cache/preload tamper and consumer restart. Unsupported/ambiguous cases refuse rather than skip.
- All original closed-artifact/tamper/link/cache/loader/main-only/duplicate/restart and actual issuer→durable store→sole provider transport gates remain required. Auth/provider ports may be simulated but artifact identity/handoff/restriction must be real and labeled separately. Fleet enrollment, legacy credentials and provider quiescence are still separate incomplete controls.

No blanket network/process-execution denial or hostile-host attestation is added. Trusted host/kernel/reviewed launcher remain trusted and can affect host-owned resources. Deprecated NoWrite availability risk remains; a failure requires an explicitly reviewed stronger enforcement boundary, potentially a different supported isolation architecture, not a field whitelist.

## Installed public SDK basis and limits

- `usr/include/sandbox.h` lines 19–49: current-process named-profile API, flags must SANDBOX_NAMED, already-restricted process errors; deprecated/no longer supported. Lines 70–73 describe NoWrite as prohibiting filesystem writes. No exec-inheritance or backing-mapping guarantee is supplied there.
- `Security.framework/Headers/SecCode.h` lines 135–190: dynamic guest lookup with NULL host starts at kernel root; unsupported/ambiguous attributes error. `kSecGuestAttributeAudit` is declared at line127, but exact value construction and lifecycle/exec behavior must be qualified, not guessed.
- Same header lines 217–238: SecCodeCheckValidity verifies signature/dynamic host validity and supplied requirement and is secure against filesystem-source modification. It validates only sealed components needed for identity, not the entire JS closure.
- Same header lines 66–73: static-code filesystem linkage is not guaranteed secure. Do not substitute it for dynamic identity.
- `usr/include/sys/un.h` lines 88–93 exposes LOCAL_PEERTOKEN as peer audit token. This is an API declaration, not evidence that inheritance/forwarding/exec generations satisfy the candidate protocol.

Only installed headers were read. No new provider reads, native APIs, restrictions, mounts, helper loads or identity initialization were executed for this proposal.
