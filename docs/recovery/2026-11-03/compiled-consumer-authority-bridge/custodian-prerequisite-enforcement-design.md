## Decision and decisive limit

Keep the selected dedicated non-login system custodian and owned anonymous-pipe delivery. Replace the constant `axiom_private_supplier_operational()` only as part of a real system-install qualification and supported runtime resource-check implementation. Do not replace it with a deployment flag, receipt signature, UID/PID test, hash manifest, JSON record, caller assertion or always-false checker with a passing fixture. No supported positive custody predicate has yet been established from the inspected headers alone.

The local public API surface supports obtaining the current security-session attributes, the actual item's containing Keychain, owner/ACL entries, authorization tags and trusted-application objects. It does **not**, in these declarations/comments, specify a public procedure for proving that a trusted-application object authorizes exactly the immutable installed supervisor and no equivalent program, nor complete semantics for arbitrary ACL subjects/partition entries or races with administrative mutation. `SecTrustedApplicationCopyData` returns data; byte equality is not a documented authorization-equivalence proof. `SecACLCopyContents` describes applications allowed **without prompting**, not a complete exclusivity theorem. Therefore a finite OS-read implementation is possible, but claiming its success proves exclusive custody would be unsupported. This is the remaining decisive blocker, not an absent API selection for secret retrieval.

## Exact implementation entry and ordering

The eventual unit modifies `origin_private_resource_supplier.{h,m}` and the startup call in `origin_broker.c`; it must not add a public registration hook or configurable credential endpoint.

1. Introduce a private installation-owned supplier context, created only by fixed native supervisor startup before queues/listener/child launch. It holds retained exact item references and the selected System-Keychain reference; no external constructor or request may create it. Remove the parameterless operational boolean rather than making it a mutable approval bit. Return an explicit unsupported-profile/refusal result while the profile below is unqualified.
2. Startup first disables UI with the already selected `SecKeychainSetUserInteractionAllowed(false)`; missing symbol/error permanently refuses this process. Then inspect `SessionGetInfo(callerSecuritySession, ...)`: require success, an actual session ID, `sessionIsRoot` set and graphic/TTY/remote bits absent for this narrowly selected system profile. These attributes are necessary context checks, not proof of launchd ownership, dedicated principal or custody. No session creation, UI fallback, unlock or retry.
3. Resolve the exact provisioned file-based System Keychain using an explicitly qualified fixed locator; retain its reference and constrain all fixed selectors with `kSecMatchSearchList` containing only that reference. `SecKeychainOpen` is a candidate locator, not an invocation approved here. Its real-path/file provenance and replacement behavior must be qualified before choosing a production pathname. Do not rely on default search order or accept the first same-named item in another keychain.
4. Obtain references, not secret data, for each exact service/account selector; require exactly one matching generic-password item per selector in that scope. Use bounded `kSecMatchLimitAll`/`kSecReturnRef`, reject zero/multiple/wrong-type results and bound the result count. `SecKeychainItemCopyKeychain` and `SecKeychainGetPath` check actual containing keychain and expected fixed location; matching path alone is not file identity. Retain those exact item refs for subsequent data reads, rather than repeating name-based discovery.
5. For each actual item call `SecKeychainItemCopyAccess`, `SecAccessCopyOwnerAndACL`, `SecACLCopyAuthorizations`, and `SecACLCopyContents` on every entry. Require success and bounded, correctly typed outputs; inspect all entries, not only decrypt/read. The approved profile must enumerate exact permitted owner type/owner, authorizations, application subjects and prompt selector interpretation. Reject unknown owner/subject/tag/partition/prompt semantics, null or unrecognized application lists, unsupported ACL formats, extra authorization paths and any failure to establish full policy equivalence. Never interpret unreadable/unknown as restrictive. The header does not supply a safe complete equivalence algorithm, so this stage currently returns **unsupported**, not “qualified.”
6. Only a profile with real independently qualified OS enforcement may create the usable private context. It is scoped to that native process and retained item refs, not serializable or persisted as authority. Each delivery rechecks current context/session/item ACL/resource provenance under the qualified mutation/race model; reads the data of those retained refs through a qualified fixed-item operation; rechecks after read; then applies the existing cancellation/deadline/root/session checks before framing/writing. No bytes reach Node after any unknown or changed result. ACL rechecks alone cannot eliminate mutation races; an actual exclusive writer policy is a prerequisite.

`SecItemCopyMatching` with `kSecMatchItemList` is documented to restrict returned items to the specified reference list. Selecting its exact data query for retained generic-password references requires supported-version qualification. No fallback to a fresh unscoped name query. The present three-query `fetch` is therefore insufficient as the implementation of this proposed checked-reference flow.

These APIs are declared locally; file-based SecKeychain/SecAccess/SecACL/SecTrustedApplication APIs are deprecated on macOS and unavailable on the listed mobile platforms. Declaration presence is not supported-version operational qualification.

## Real installation/operator qualification required before a positive path

The qualification is an external action and trusted administrative decision, not a file the broker accepts as authority. Approval of this source design does not authorize it. An operator must separately approve a bounded owned deployment first, preferably entirely synthetic credentials and an isolated synthetic datasource. No production resource or legacy changes are implicit.

The operator must establish an actual system launch configuration under the dedicated non-login principal, a fixed immutable supervisor/package/Node launch tree, protected executable/configuration/parent directories, and no untrusted route to modify launch arguments, environment, executable contents, descendants or resource policy. Root/host administrators remain explicitly trusted; protection against a hostile host administrator is not claimed. Merely signing a receipt or supplying a launchd label does not establish these controls. The current per-user arrangement does not qualify.

The operator/platform review must supply and qualify the exact file-based item owner/ACL/partition/prompt semantics for the supported macOS versions, including how runtime inspection proves equivalence to the provisioned policy. Establish that only the installed custodian can perform the relevant secret read, that no unbound process or alternate same-signed executable gains equivalent access, and that untrusted users cannot alter ACL/owner/keychain or replace its backing resource. If the public APIs cannot inspect the complete enforced policy, the supported profile requires an explicitly documented trusted installer/admin guarantee for that uninspectable part and a real protected installation boundary, with runtime checks limited to claims they can actually establish. A caller-provided “qualified” receipt is never an authority input. If neither complete inspection nor that qualified installation boundary is feasible, this platform profile remains unsupported and the constant gate is not removed.

Separately establish compatible DB credentials/rows, the existing deployment-wide vault key and session key, exclusive resource writers, removal of equivalent DB rights/keys/fallbacks from every unbound/legacy tier sharing those resources, and preserved tokens/unknown-history/drain semantics. Synthetic qualification can establish a deployment mechanism only; it cannot establish production withdrawal. Actual provisioning and exclusive legacy withdrawal remain external gates.

The code entry is the actual installed supervisor's private startup path plus OS-enforced access to the retained resources. Qualification records identify the approved installation/profile and its limits for human review; the program does not deserialize them into a positive capability. Positive startup requires actual supported context/resource checks within the qualified installed boundary. Until the operator supplies the missing complete ACL interpretation/enforcement boundary, an implementation claiming a positive path would invent semantics. Do not implement that claim.
