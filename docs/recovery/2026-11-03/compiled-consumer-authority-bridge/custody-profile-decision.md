# Proposed C custody profile: explicit resource and cutover decisions

**Internal source-only decision specification, not implementation/operational approval.** Builds on `3125ba1c` and inventory `0be6a38c` (W01–W15,32 hashed sources). No SQL, grant, service, credential, code, test or provider action is prescribed or performed. Original same-compiled-consumer, actual runtime/fleet/legacy/coverage and unknown-history requirements are unchanged.

## Recommended minimum complete model

For the **new customer-controlled profile**, choose an unbound web/presentation/worker tier with **no database credentials at all**, no App signing material, no connection-decryption key/fallback and no reusable provider token. A protected authority/effect tier owns the privileged resources and runs the actual fixed compiled direct-merge coordinator/store/credential/transport graph. The web is an authenticated data-only client, not an authority writer or credential broker. This is a **new deployment profile**, not a claim that the current hosted Next application already works with its DB/environment removed.

That authority tier must mediate the complete control-plane inputs needed by the effect: session issuance/revocation, accepted membership/role management, exact plan/requester/reviewer history, provider approvals, policy/baseline/evidence/source heads, installation revisions, claim/drain/exposure leases and outcomes. Trusted identity/admin decisions remain real independently authenticated decisions; locating them behind a service does not make the agent a reviewer. A protected effect service with untrusted web writes to its authority tables would not meet this model.

No “inert contract phase” counts as completion. The target is exclusive **real** custody plus the actual compiled-consumer path. Local simulated contracts may be useful validation evidence after approval, but do not establish any resource isolation, native launch, credential withdrawal or production readiness.

## Why this default rather than shared-table RLS

| Choice | Enforcement shape | Benefit | Cost / unresolved prerequisites |
|---|---|---|---|
| **Recommended: no DB credentials in unbound tier** | Only trusted authority/effect processes can reach the authority DB using their private credentials. Web/workers use exact authenticated APIs and bounded read models. Provider keys and tokens also never enter unbound processes. | Makes global `lib/db.ts`/factory imports nonauthoritative there because the real resource is absent. Avoids trying to secure every authority row through a broad web database login. | Broad existing Next routes assume DB access. A complete new-profile API/read-model and control-plane migration is required, including auth/session/role/invite/admin/background paths. Existing platform cannot be called compatible until that migration is qualified. |
| Alternative: restricted web DB principal with per-kind/row/event enforcement | Database policy denies all privileged workflow kinds/authority tables and identity/policy mutations to web; narrowly delegated independent authorities persist exact decisions. | May preserve more existing read-heavy routes. | Shared `DurableAgentWorkflow` plus events, indirect authority facts, owner/admin bypass and dynamic/operational writers make it a larger policy-proof surface. Source inventory is not complete enough to assert safe grants. Requires reviewed DB policy/schema/role/backup migration and real acceptance. No production SQL selected here. |

The recommendation narrows access by moving ownership, not by granting a stronger same-UID process a JS factory token. It does not change current deployment roles automatically. If required product functions cannot be migrated without leaving authority credentials in general web, this profile stays unsupported rather than quietly falling back to the alternative.

## Exact custody and interfaces

- **Identity and role authority (W01–W02):** authenticated pairing/session and membership/invitation/admin endpoints terminate at a trusted authority component. It owns session/role writes and allows tightly authenticated containment revocation. Current `desktopSessionStore.prisma.ts`, pairing/session routes, seat/invitation mapping and manual role routes must be moved or replaced as exact interfaces, not left on a DB-enabled web route. The issuer independently resolves current actor/session/membership, not a forwarded “already checked” assertion.
- **Plan/review/policy/evidence (W03–W08):** trusted authority persists immutable exact revisions/events and real independent decisions. Data-only APIs separate propose/read/review/activate/revoke. The issuer reads these authoritative records and preserves transaction locks/current-source checks. An active ceiling still does not enroll a baseline or approve an action. A background collector cannot edit an approval or counterfeit current source.
- **Claim/drain/leases (W05,W09–W11):** actual compiled issuer owns claim and consumption transaction, exposure before mint, issued/unknown token accounting, submission intent and outcome. The same protected composition retains the private claim and original freshness through awaits and final handoff. Management APIs cannot reset unknowns or erase older runtime/token blockers.
- **Installation and provider authority (W12–W14):** authenticated install callback/webhook/reconnect semantics move behind trusted authority; general web may forward data but cannot rebind installation ownership. App signing/mint and any relevant decrypt key/fallback remain exclusively in protected custody. Existing scoped token factory and read-policy factory remain private dependencies of the actual compiled graph; no generic token endpoint or credential-return API is introduced. Read-only policy credentials do not silently become write credentials or vice versa.
- **Database integrity (W15):** authority/effect tier has only reviewed necessary rights, but exact split between identity/policy authoring and effect claims is still a design decision. A shared trusted DB owner is not a least-privilege conclusion. Backup/restore/admin access and event/record consistency must retain original history and quiescence. No schema/role implementation is implied.

## Binding actual issuer to custody

The resource custodian must authenticate the **actual owned qualified issuer instance**, including its private native launch/lifetime binding and exact supported package/compiled dispatcher, not just same UID, a code-signature label, supplied PID, module name or JS-ready value. Credentials cannot be delivered to an arbitrary process that happens to satisfy a signing requirement. Custody must either remain inside that exclusively controlled issuer resource process or be exercised through an exact operation-bound private channel whose native owner retains the resource; the latter is not a generic credential export.

Before claim, credential mint/exposure and final synchronous send, the actual compiled graph must obtain fresh native lifetime plus original business authority/session/approval/source/connection/deadline checks. Native process identity does not supply human approval or prove DB claim content. A current native-origin observation alone must continue returning unavailable until the actual bridge and resource ownership are qualified.

The present per-user controller/broker sources and package checks **do not evidence this resource isolation**. Exact supported OS/service principal, resource access mechanism, authenticated channel and fixed recipient are pending platform-design decisions. They must be reconciled with the placement/channel proposal; no privileged service installation, account creation, key migration, permission grant or protected-resource read is approved by this specification.

## Proposed supported placement (cross-review decision)

Use a **dedicated non-login service principal with system placement**, a fixed data-only XPC entry and one owned actual compiled issuer handler. This is the concrete proposed default, **not** the existing per-user SMAppService arrangement and not a service already installed/qualified. The companion [process placement and request-channel proposal](process-placement-and-request-channel.md) (`d214f47f`) supplies exact message/session/transport bounds; this custody specification supplies the resource rights and writer migration. Its proposed `_axiomissuer` principal is new and requires approval; the name is not an existing account or grant. Both documents leave actual compiled-handler-to-custodian authentication and privileged provisioning unresolved, rather than asserting a working platform boundary.

The native owner must retain custody of privileged resources and authenticate the actual owned fixed issuer instance before any access, with fresh lifetime checks at the stated boundaries. Dedicated UID and code-signature checks are necessary proposed restrictions, not by themselves sufficient issuer/resource binding. The current native250ms origin challenge is observation, not a secret grant. There must be no public “get credential” XPC operation: only the fixed compiled graph may exercise the resource through a private native-owned instance channel. Exact DB-driver/key access delivery inside that instance remains part of the reviewed implementation design; an arbitrary signed or same-UID process must not receive it. If the platform cannot enforce that ownership for the actual compiled handler, this profile remains unsupported.

## Cutover and compatibility gates

1. Inventory actual deployment principals/secrets/jobs under separately authorized read access; current source cannot prove where live DB/signing/decrypt credentials exist. Record current tokens/leases/unknowns and older runtime effects without clearing history.
2. Specify exact trusted APIs for every mapped control-plane writer and needed web read. Preserve reviewer identity, session freshness, invitation role behavior, plan/event integrity, current policy/baseline and authenticated revoke-only containment. Do not strand administration or let a fallback regain broad DB rights.
3. Prepare reviewed least-privilege DB/resource/key custody and migration/rollback/backup plans. **Actual** DB grants/schema/service installation/key transfer/provider changes each require specific operational authorization. A code-only design approval cannot perform them.
4. Qualify one fixed compiled direct-merge dispatcher from the same sealed successful package, then original positive/refusal/freshness/claim/credential/unknown matrices. Simulated provider/auth/DB tests remain narrower evidence. Current unqualified issuer seams/default coverage stay refusing.
5. Drain or qualify legacy DB-enabled runtimes and still-valid token exposure under original rules before activation. No live mixed-mode fallback allows an older web process to retain equivalent keys. Rollback to older software must not restore withdrawn effect authority; unsupported rollback refuses rather than reissuing keys automatically.
6. After cutover, presentation failure cannot erase authority history; service outage refuses new effects. Read-only outcome/containment paths have separately reviewed availability. Cancellation after possible submission remains consumed unknown; crash/restart reconciles read-only, never regenerates a send permit or resends.

This first profile does **not** complete master coverage. Deployment, Agent, other apps/tickets, Airflow, native input, workers and legacy callers remain refused until their actual resource paths and original fleet/coverage requirements qualify. The complete architecture goal includes those lanes; it is not reduced to direct merge or to an API contract demo.

## Global signing/decryption configuration fixes the cutover scope

Source inspection adds an important constraint: the current signer is **deployment/platform scoped**, not a separate per-organization resource. `githubConfig.ts:104–114,150–174` prefers the platform credential singleton and falls back to environment App configuration/private key, including DB/decryption failure fallback. `platformGithubAppCredential.ts:1–32` describes the `platform_github_app` singleton and context-bound vault encryption. `githubAppAuth.ts:156–198` resolves that configuration/key and signs App JWTs; its in-process token cache key is installation/repository/permission-profile scoped (`:171`), not an independent organization-specific signing key. The cache narrows token reuse; it does not restrict the holder of the underlying App key from independently minting other installation tokens permitted by that App.

`credentialVault.ts:6–15` derives the same configured key from `CREDENTIAL_ENCRYPTION_KEY` or `STARTER_TOKEN_SECRET`; context binding prevents cross-field/tenant ciphertext substitution but does **not** create separate key custody per profile. A process retaining the shared key and applicable encrypted rows may retain equivalent decrypt authority. Removing only a merge route, clearing one cache entry, or hiding one organization does not remove those resources.

**Concrete default cutover scope:** the new protected profile is process/deployment-wide for every organization/resource sharing that signer, vault key and DB principal. All general web/presentation/worker processes in that new profile have no DB credentials, App signing configuration, platform credential access, vault key/fallback or reusable provider tokens. Every legacy organization/feature using those same resources must move to mediated trusted operations/read facts or explicitly refuse. It is invalid to qualify one organization/profile while the same deployment’s unbound web retains the equivalent signer/decrypt key “for other organizations.” This is not an assertion about all customers or independent deployments: actual key sharing, deployed principals, App installations and secret placement remain unknown without separately authorized operational inventory.

Existing GitHub readers require an explicit compatibility map. Provenance/repository/PR/status/UI readers may call exact **read-fact** APIs on the trusted tier, which privately uses their current least-privilege token scopes and returns bounded authorized observations. Preserve installation/repository/tenant binding, permission profile, source freshness, current session and error/unknown semantics. The current `createReleaseReadOnlyMergePolicyCredential` and `merge_policy_read` path remain private trusted dependencies; they cannot export a token to the unbound tier. A generic “mint read token” API would require a separate reviewed credential-exposure model and is not selected here. A reader with no reviewed fact adapter refuses; it cannot silently restore environment PAT/App-key fallback or invoke the old DB-backed factory.

Before actual cutover, the reviewed compatibility inventory must include platform manifest credential setup/update, App install callbacks/status, live scanners, operating-loop/state builders, native Git/legacy token issuers, and their background/job callers. These are high-signal source consumers, not a claim of exhaustive live reachability. Existing tokens/caches in older processes remain governed exposure/drain blockers until qualified/expired; process replacement alone is not provider revocation. No key rotation, secret transfer, App change, DB grant, migration or service activation is authorized by this design.
