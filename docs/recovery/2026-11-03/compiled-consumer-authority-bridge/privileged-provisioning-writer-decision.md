# A2 decision proposal: installation-owned provisioning writer

Source-only follow-on to `09c662d4`, using only the same local SDK headers. **Requires user design approval.** No implementation, tests, OS calls, resource writes, grant or installation is authorized or performed. Existing `operational()` remains constant zero and custody **UNIMPLEMENTED**.

## Proposed finite unit and changed trust assumption

Select a privileged installation-owned provisioning writer as a candidate way to establish policy by actual OS writes, rather than trying to infer full authorization equivalence from opaque trusted-application data. This introduces a **new trusted writer**. The approving human, privileged installer and host/root administrator are explicitly trusted and outside the attacker model. The native custodian remains the separately reviewed dedicated non-login principal; it is not promoted to root. Unbound apps/workers, caller metadata and other same-signed executables remain untrusted.

The finite unit is one installation transaction for three **new synthetic installation-owned generic-password items** in the fixed file-based System Keychain, a protected installation binding to one immutable custodian launch, and the corresponding private supplier startup/read path. It is not migration of production keys or modification of existing user items. No package manifest or signed policy receipt independently enables access. Real OS acceptance of the installed policy and actual current authorized reads within the protected installation are required.

This is viable only with an explicitly approved trusted installer boundary. Public Security declarations do not independently attest “this process was installed by the approved operator” or “the policy has never changed.” Trust in that administrative boundary must be stated, not simulated through ACL metadata.

## Local API grounding and important limit

The hashed local SDK declares:

- `SecTrustedApplicationCreateFromPath(fixedInstalledCustodianPath, &app)` constructs a trusted-application reference for the selected installed tool. Never pass NULL (self), a caller path or a broad list of signed applications.
- `SecAccessCreate(descriptor, explicitSingleApplicationArray, &access)` creates the **currently designated system default** configuration. Header comments say defaults can change by release and the trusted list controls applications allowed without confirmation. NULL defaults to the creating application. Therefore this call alone is **not** an exclusive-owner/full-policy proof and must not accidentally retain the installer as a general secret reader.
- `SecAccessCreateWithOwnerAndACL(uid, gid, ownerType, explicitACLArray, &error)` accepts explicit ownership and ACLs. `SecACLCreateWithSimpleContents` and `SecACLUpdateAuthorizations` supply creation/update surfaces; the exact full owner/authorization/prompt/partition policy must be fixed and platform-qualified. Do not guess that an empty list denies everything or that a single no-prompt application denies all other access paths.
- `SecItemAdd` accepts `kSecUseKeychain` for the exact target keychain and `kSecAttrAccess` for macOS generic-password items, returning the added reference with `kSecReturnRef`. Success acknowledges an actual addition; it does not certify all exclusivity requirements.
- `SecKeychainItemSetAccess(exactOwnedRef, access)` replaces access on an actual item. It is a potential later reviewed migration mechanism, **excluded from the initial new-item unit**. It must never discover an arbitrary legacy item by name and rewrite it merely because an install request asked.

API declarations are deprecated macOS file-based interfaces, not current-version operational qualification. OS acknowledgment proves the requested operation succeeded, not that a caller's interpretation of default ACLs is correct. Selecting the writer avoids opaque byte comparison, but cannot remove the need to qualify the exact written policy and installation controls.

## Genuine installer-to-custodian binding and epoch

Select an **offline installed launch relationship**, not a public install-ready RPC. The trusted installer installs the immutable custodian and complete fixed launch tree/configuration at administrator-controlled locations and provisions the exact resources before enabling its dedicated system launch. The only administrative actor allowed to change those locations or item policy is the trusted installer/root boundary. Current per-user source and loaded-file checks are insufficient evidence of those deployed protections.

For the initial unit, the trusted installer is the sole resource-policy writer and launches a fresh system instance only after its entire transaction succeeds. Installation epoch means that concrete fresh installed process/resource generation; a stale process is stopped and must not inherit an updated grant. The installed supervisor receives no runtime “qualified=true” message and has no credential-registration endpoint. It must check its real fixed installation/file provenance, current system-session context and dedicated principal, then locate only the exact installation-owned resources and perform actual OS-authorized reads. The installer controls execution and the OS resource policy; an untrusted requester does not authenticate the installer through JSON.

Any protected locator/epoch metadata serves only to select resources and detect mismatch. Root ownership or matching generation text alone does not grant startup. Unknown/missing provenance, multiple matches, unexpected item ownership/ACL shape, unexpected current launch context or denied read refuses. An attacker-created lookalike item cannot qualify merely through matching labels. There is no supported self-contained cryptographic installation attestation asserted here: the authenticity of the relationship derives from the real protected installed launch/resources under the explicitly trusted administrator. If that relationship cannot be established and qualified, the model is rejected for that deployment.

The exact install paths, launch arguments/environment, permissions/owners and replacement/race protections must be part of the reviewed installation manifest before implementation. No manifest supplied by the unbound caller can define them. The custodian's child package/Node and pipe recipient remain subject to the original native owned-instance qualification; resource provisioning does not authenticate an arbitrary signed recipient.

## Transaction and actual enforcement

1. Under a separately approved operator action, stage the fixed immutable program and launch configuration with no enabled service and no production secrets. Select synthetic datasource/key/session values; exclude every production account/service and existing item. Reject preexisting selector collisions, incomplete installations and unknown prior attempts; no automatic repair/delete/reuse. Any proposed discovery query must resolve a supported pre-return allocation/work bound before implementation; rejecting an oversized `kSecMatchLimitAll` result after return supplies no such bound.
2. Build the explicit qualified access policy for the installed custodian and trusted administrative owner. Trusted admin modification rights are acknowledged; untrusted modification/read paths must be excluded by the actual installed policy and protected file/service ownership. Do not rely on `SecAccessCreate` default shape alone.
3. Add each new item with its explicit access object and exact target keychain in the same actual `SecItemAdd` call. Require OS success and correctly typed returned refs; retain exact refs in the provisioning transaction. Do not publish an enabled launch on partial success. On partial failure, report an incomplete installation for separately approved recovery; no automatic key repair or silently accepting a partial generation.
4. Trusted installer completes the protected install binding and enables one fresh dedicated system launch only after all actual writes succeed. The custodian uses the private startup entry and actual item/context checks described in the prerequisite design, disables interaction before reads and reads the retained exact items through OS authorization. Passing a policy receipt cannot substitute for these operations. The OS's current authorization decision enforces the written resource policy; a successful read alone still does not establish exclusivity.
5. At every supply, preserve original cancellation/deadline/lifetime/one-use pipe checks and fail on unexpected current resource/installation changes. The trusted admin must quiesce/revoke the epoch before changes; inspection cannot eliminate a concurrent privileged writer. Administrative mutation during an active epoch is outside the approved operating procedure and cannot be masked by a cached “qualified” bit.

The exact full policy and supported installation provenance implementation are prerequisites for positive startup source. Until those are explicitly approved, no code should replace constant zero with a predicate that pretends the prerequisites exist. A positive owned deployment must use the real APIs and real installed resources, not a fixture returning their expected result.

## Finite acceptance and retained gates

After separate source approval and exact operational authorization, acceptance must demonstrate the real synthetic installation transaction, actual successful fixed-custodian reads and owned pipe delivery; denied reads by unbound user/same-signed alternate programs; refusal for wrong context/duplicate/lookalike/missing/partial resources; no UI; denied untrusted policy/file/service mutation; fresh epoch after installer changes; and unchanged one-use/deadline/unknown outcomes. Tests must exercise the installed OS boundary, not just mock OSStatus or compare ACL dumps. These are future acceptance requirements, not tests authorized or generated now. No blocked original compiled-consumer experiment is renamed or regenerated.

This qualification proves only the scoped synthetic installation mechanism. Historic key copies, production DB/key compatibility, shared deployment signer/vault scope, unbound/legacy withdrawal, provider token exposures, actual compiled consumer/native same-artifact matrix, trusted control-plane writers, fleet/full mutation coverage and Governance enrollment remain separate mandatory gates. Custody comes before initialization keys; no DB-backed initialized consumer is required merely to provision them. Actual governed execution still requires the later original consumer acceptance. No malicious-root protection, exclusive production custody or full Governance is claimed.

**Next action:** user approval or rejection of this new trusted provisioning-writer boundary and bounded new synthetic installation unit, followed by a concrete exact policy/installation specification for approval before code or operational actions. If the operator/root trust boundary is unacceptable, or exact supported owner/ACL policy cannot be qualified, retain the current refusal; the allowed local APIs do not provide an independent attestation substitute.
