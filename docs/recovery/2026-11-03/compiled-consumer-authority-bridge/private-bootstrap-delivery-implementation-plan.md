## Next concrete unit and prerequisite decisions

Implement **one native-owned, once-per-epoch delivery of actual private initialization material into the fixed canonical Node main, followed by construction of its existing private business graph**. Keep native ownership of launch/lifetime/resources and Node ownership of SQL, identity, policy, approvals, claims, decryption, App signing, scoped minting and final transport. No second native business executor.

The existing evidence does not yet support an unconditional resource-delivery implementation. Resolve these exact gates before approving that unit:

1. **Real supplier:** select the actual custody store and its supported native read API/access policy for the dedicated service principal, supplying the real authority PostgreSQL datasource, the actual 32-byte vault key, and the compatible session key bytes. A proposed dedicated-principal Keychain-backed supplier is a decision candidate only: none of the eight approved Apple references specifies its lookup, access control, provisioning or noninteractive availability. No Keychain API is selected from unsupported recollection, and no Keychain access occurs here. Approval must identify exact fixed item identities, principal/access-control enforcement, source of each existing compatible key, provisioning/rotation/revocation ownership, and the bounded read API. If Keychain is not selected, choose a concrete equivalent supplier and its evidence explicitly. A constructor argument, empty buffer, fixture secret, caller-provided provider callback, environment lookup or static compiled secret cannot stand in for it. No supplier implementation or secret injection is approved until that selection is complete.
2. **Recipient and reply route:** retain the reviewed raw-Mach per-message sender candidate, but require a supported, qualified way to deliver the bounded response exclusively to the actual owned canonical Node execution. A request-supplied send-once reply right authenticates a destination right, not its receive-right owner; the sender may nominate another recipient. Audit PID/version/signature checks do not fix that. The approved findings do not establish a public API to inspect that owner or prevent delegation, nor an exclusive bootstrap rendezvous across fixed `execve`. Do not silently approve secret response on the supplied reply right. Decide and substantiate the native-owned response endpoint/custody mechanism, including transfer/inheritance across bootstrap exec and exclusion of other recipients. If the selected mechanism cannot satisfy it, this unit remains unsupported; choose a separately reviewed delivery mechanism instead of implementing a passing stub. No new public reads or native experiments are authorized by this plan.

These are narrow implementation prerequisites, not permission to restart architecture or to treat a sender filter as authority. Approving local code alone cannot supply either proof. The actual owned-recipient binding and original compiled-consumer qualification remain unavailable even after code exists.

## Exact material record and lifetime

Proposed total response cap: 32 KiB including frame, with fixed lengths and no unknown fields. Datasource UTF-8 is at most 8192 bytes (existing private constructor limit); vault key exactly 32 bytes; session-key cap/accepted representation must be reconciled with existing compatible private token codec and selected supplier before code approval. Billing is fixed nonsecret `legacy` or reviewed `public` account/livemode identity, not a caller entitlement. No raw App private key is independently delivered: actual private platform App configuration reads its encrypted singleton through this DB/vault and fails closed. No provider token is in the bootstrap payload.

Actual DB rights, network/TLS configuration, compatible encrypted rows and global key sharing must be operationally established. Neither choosing a new datasource nor sending a new key makes current sessions/rows compatible. The authority client/vault/token codec necessarily retain copies (datasource string/Prisma configuration, copied vault key, crypto inputs); clear staging buffers where supported without claiming V8/Prisma zeroization. No payload/ciphertext/URL/key logging, error serialization or IPC echo. Epoch loss closes new operations and follows existing consumed/unknown/exposure history; wiping staging does not revoke already minted tokens. No reconnect/reissue, restart inheritance or generic credential RPC.
