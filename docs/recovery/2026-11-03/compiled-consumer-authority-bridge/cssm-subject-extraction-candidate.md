## Initial assessment (superseded where noted by the clarification below)

The declarations provide the structural surface for an eventual prompt-free subject candidate: `SecAccessGetOwnerAndACL` returns CSSM owner/entry structures, and `SecAccessCreateFromOwnerAndACL` accepts those structure types. An OS-created simple application ACL can supply its application subject without decoding opaque trusted-application bytes. Copying only that complete application subject into a separately owned entry would avoid intentionally carrying the prompt alternative. This is **structurally plausible, not yet implementation-ready**: the inspected header does not document ownership/freeing/lifetime of the returned pointers, and the supplied public-source findings do not fully specify the exact exported CSSM threshold grammar. Neither omission may be filled by guessing.

The initial proposed preparation unit was a bounded, owned CSSM-tree validator/deep copier and exact-subject selector, independent of all Security calls. Its OS adapter remains withheld until the two specific ABI/lifetime and subject-layout questions below are grounded. Pure-buffer success would prove only memory/shape handling, never OS policy, identity or custody.

## Exact local declarations and representation limits

`SecAccess.h:146` declares `SecAccessCreateFromOwnerAndACL(const CSSM_ACL_OWNER_PROTOTYPE *, uint32, const CSSM_ACL_ENTRY_INFO *, SecAccessRef *)`; line174 declares `SecAccessGetOwnerAndACL(SecAccessRef, CSSM_ACL_OWNER_PROTOTYPE **, uint32 *, CSSM_ACL_ENTRY_INFO **)`. The latter comments say pointers are returned but state no allocation ownership, release operation, validity duration or effect of another call/mutation. No matching free function was found in the inspected SecAccess/SecACL declarations. Holding a CF reference is prudent but is not documented proof that these arrays remain valid. Do not call `free`, `CFRelease` or a guessed CSSM free operation on them; also do not assume they leak safely or remain valid forever.

`cssmtype.h` declares `CSSM_LIST` with type/head/tail and linked `CSSM_LIST_ELEMENT` with next pointer, word ID, element kind and datum/sublist union. It declares the ACL owner subject/delegate; entry subject/delegate, authorization count/pointer, time ranges/tag; and entry handle. `cssmapple.h` declares code-signature and keychain-prompt subject constants, plus a process selector with explicit UID/GID mask fields. These structures allow representation-preserving copying, not inference of arbitrary subject semantics. The existing [Apple findings](apple-acl-source-findings.md) establish that the simple application list includes a prompt alternative. They do not provide enough exact exported list layout to select a branch by numeric position or manufacture a new threshold encoding.

## Proposed future OS-owned builder adapter

All following operations are future, separately approved actions, not calls made now:

1. Create a trusted-application reference for the exact fixed installed supervisor path and an in-memory simple ACL containing exactly that one application. No real resource/item is created. A temporary `SecAccessCreate` builder may contain defaults; those are never installed and must not be copied as the final entry set.
2. Set that explicit simple entry's rights to the selected numeric `CSSM_ACL_AUTHORIZATION_DECRYPT` and `CSSM_ACL_AUTHORIZATION_DB_READ` equivalents only after the CF authorization-to-CSSM mapping has been established. Do not infer that two similarly named constants map automatically. The selected high-level names remain the historical desired read/decrypt rights, not qualified effective rights.
3. Obtain the actual CSSM representation through `SecAccessGetOwnerAndACL`. Require an unambiguous binding between the explicit builder entry and exactly one returned entry; no “first entry” choice, display-description identity assumption or copied defaults. Actual source/API semantics must establish that binding before implementing the adapter.
4. Under a grounded return-buffer lifetime rule, immediately deep-copy the complete bounded representation into an owned arena. Never mutate OS-returned pointers. Select one complete application subject only from the explicitly recognized simple-entry alternative shape; verify exactly one application and the known prompt branch, excluding the entire prompt branch from the output. Unknown shape/extra branch/unknown subject fails. Do not parse/rewrite the code-signature payload; preserve it byte-for-byte as OS-generated opaque datum.
5. Use a separately generated explicit root administrative owner subject only after the public process-owner encoding and its exact semantics are grounded. A builder's default owner is not assumed to be that owner. A potential root-UID owner from an in-memory `SecAccessCreateWithOwnerAndACL(0,0,kSecUseOnlyUID, rightsNames,...)` must be inspected/qualified as a separate owner builder; it must not be confused with the rejected ACL-array transplant.
6. Prepare exactly one owned entry with the selected application subject, explicit qualified rights and no delegation; do not copy builder default entries, handles, dates or permissions without interpreting their required meaning. The semantics of zero/empty validity and entry handles must be established before choosing their final values. Call the lower-level constructor only after those choices are reviewed; keep all owned input buffers alive through it and retain them for the returned object's lifetime unless documented copying semantics permit earlier release. Retaining input alone does not settle OS-returned source-buffer lifetime.

This recipe intentionally stops at semantic unknowns rather than fabricating a subject format or allocator contract. No temporary access object grants privileges by itself. Any future item creation still requires the exact new-synthetic-only transaction, real OS policy enforcement and trusted installation boundary; no SetAccess migration/delete/production data is included.

## Bounded pure-buffer preparation proposal

The proposed reviewable implementation unit, if separately approved, accepts only an **already owned** CSSM graph accompanied by allocation-range metadata from its adapter; it never dereferences arbitrary caller/OS pointers. Fixed limits: 16 ACL entries, nesting depth8, total256 list elements, total64KiB datum bytes and at most16 authorization tags. Reject arithmetic overflow, null/count mismatch, cyclic/shared graphs, pointers outside owned ranges, overlapping allocations, inconsistent head/tail/next, unknown list/element kinds, impossible union use and limits before copying. These limits bound this unit's own work/storage, not OS allocation or search work.

Output is one complete owned selected subject plus an explicit entry/owner envelope, or a refusal. Its arena owns every copied node/datum/tag byte; cleanup uses only its own allocator, wipes when appropriate and never frees OS memory. The selector must require an exact reviewed layout contract for application-vs-prompt branches; no positional heuristic, opaque CFData decoding, unknown-subject admission, default ACL carryover or empty-list deny assumption. Since that contract is not yet grounded, there is no approved positive subject selector now. Synthetic graph validation cannot establish a real code identity, prompt absence in an installed effective ACL or read exclusivity.

## Clarification: concrete one-shot candidate after supplied source detail

This section supersedes the earlier claim that unspecified deallocation/complete exported grammar necessarily blocks all code preparation. The parent supplied further detail from the **already approved** `Access.cpp` and `ACL.cpp` reads: owner output is allocated with the standard allocator and the allocated ACL array is released to the caller without being freed before return; the single-application simple subject has the known threshold-one-of-two application/prompt form. These are supplied public-source observations, not new retrievals or installed-framework attestation. See the [central findings](apple-acl-source-findings.md); no additional source quotation is reproduced here.

A finite candidate can avoid guessing the output deallocator: retain the once-created in-memory policy objects and their returned CSSM allocations until the dedicated provisioning process exits. Inputs/outputs contain policy identity, not secret item values. This changes the profile to **one-shot, process-lifetime policy retention**, with no repeated builder calls, no reused long-lived service, no cleanup callback that guesses allocator ownership and no nonzeroization claim. It does not establish a universal bound on framework allocation; that is not needed for the stated one-shot preparation scope. Fixed call counts and bounded application-owned copies remain explicit. Unexpected results terminate this attempt without retries.

The concrete candidate for separate code-preparation approval is:

1. Build a temporary in-memory access object with `SecAccessCreateFromOwnerAndACL` using an explicit root process owner and **zero entries** (`aclCount=0`, no entry array). This does not mean empty ACL is installed as deny-all: the temporary object never attaches to any Keychain item. Use the declared `CSSM_ACL_PROCESS_SUBJECT_SELECTOR` with current version, `CSSM_ACL_MATCH_UID` only, UID0, GID0, and delegate false, encoded in the exact process-subject list form established by the supplied public source. Root administrative authority remains an explicit trust assumption. No default-producing `SecAccessCreate` builder is needed.
2. Create exactly one fixed installed-path trusted-application reference and exactly one simple ACL on that zero-entry temporary access, then set exactly the selected high-level decrypt/read authorization names. Obtain its actual exported CSSM rights with the returned entry; preserve those numeric rights rather than guessing a name-to-number mapping. Require the expected read/decrypt correspondence at qualification; a mismatch refuses, not grants broader rights.
3. Call `SecAccessGetOwnerAndACL` **once**. Require success, one owner and exactly one returned entry. The explicit zero-entry builder plus one added entry eliminates “which default entry?” guessing. Never copy any extra entry or accept a count mismatch. Retain all returned allocations and the builder for the process lifetime; never mutate or free OS-returned pointers.
4. Validate the source-known exported threshold-one-of-two structure and complete list integrity under the owned-copy limits. Require precisely one OS-created code-signature application subject and one keychain-prompt subject. Identify branches by the actual declared subject type within that exact grammar, not first/last position. Reject nested unknown alternatives, repeated application/prompt subjects, extra elements, malformed thresholds, cycles and count mismatches. The implementation must transcribe the supplied source's concrete list grammar for review; no invented threshold encoding is selected. OS pointers are treated as trusted framework output from that one successful call, not arbitrary caller pointers; count/type/range checks cannot magically prove arbitrary pointers safe. If the actual framework shape differs, refuse without retry.
5. Deep-copy **only the complete application sublist**, preserving every OS-generated code-signature datum byte without decoding/rebuilding it. Set this copied complete subject as the final entry's top-level `TypedSubject`; do not retain its threshold parent or prompt sibling. Preserve the explicit qualified rights, no delegation and source-established validity/tag representation from the single returned entry; do not carry entry handles as authority. Keep a deep copy of the explicit root owner in the owned arena. All app-owned nodes, payloads and rights are bounded and exclusively freed through the app's allocator.
6. Pass that one owner/one-entry CSSM array to `SecAccessCreateFromOwnerAndACL`, not the similarly named CF-array API. Keep the arena, temporary builder, OS outputs and resulting access object alive until process exit. This bypasses unresolved early-free/input-copy timing without asserting that retention proves policy semantics. In this preparation unit no item is added, queried or modified, no access object is installed and no supplier gate is enabled.

The proposed implementation can contain those real in-memory API calls after separate code approval, while actual invocation remains separately authorized. Pure-buffer preparation can implement the exact validator/copier/assembly with the existing fixed bounds and no OS invocation; however, its passing synthetic input cannot establish that the OS builder actually emits the expected shape. The two halves form a finite candidate, not separate substitutes for resource custody.

Mandatory subsequent real qualification remains: actual supported/deprecated API behavior; constructor acceptance of the extracted subject; exact owner/rights/validity behavior; absence of prompt/default authorization alternatives in the effective installed item; alternate-code/Node denial; copied genuine supplier pre-read refusal and pre-main integrity under the complete installed boundary; exact retained resources, native epoch/pipe recipient and unchanged original compiled-consumer/copy/fleet/coverage/history matrices. Opaque signature-subject reuse is not assumed path-exclusive. Any unexpected shape or policy rejection refuses; no fixture-backed positive path, repair, SetAccess migration, production data or blocked test recreation is selected.

**Revised finite disposition:** source-supported enough to propose this one-shot in-memory builder plus bounded CSSM subject extraction/assembly for separate implementation review. It is not operationally qualified and not selected as a working exclusive policy. The remaining questions are concrete constructor/effective-policy and complete-boundary qualification, rather than a demand to discover a universal allocator bound or to implement a speculative free routine. Canonical `operational()` stays false and the business channel unmounted.
