# C role division and private initialization: source-review blueprint

**Design proposal only.** This reconciles the custody and placement/resource-channel documents; it does not approve code, services, grants, provisioning, tests or qualification. In particular it does not resume or describe the blocked security test. The existing Node/Prisma/business-policy graph must remain the actual compiled consumer; a second native SQL/policy engine is not proposed.

## Two distinct owners, not two policy engines

| Component | Owns | Must not do / present qualification |
|---|---|---|
| **Native supervisor / resource provisioner** | Fixed system placement and launch; actual owned child/package/instance/epoch/lifetime; narrowly controlled private bootstrap resource provisioning to that child only. | Does not interpret approval/plan rows, run business SQL, independently decide reviewer rights, or execute a second merge implementation. Audit/PID/UID/signature observations alone do not grant resources. Private recipient/resource binding is still unqualified and needs selected-platform proof and user review. |
| **One protected compiled Node authority process** | Actual private Prisma client; current identity/session/role/policy/plan/approval state; actual claim/drain/credential-exposure transactions; existing context-bound decryption, App JWT/scoped mint and fixed final HTTP transport. | Does not expose its repo/secret/token/credential factory through business APIs. It must run the same emitted compiled coordinator/store/transport from the bound package, not source wrappers or native reimplementation. Current default issuer readers still refuse. |
| **Unbound web / desktop / ordinary workers** | Presentation and exact data-only business requests, with opaque user session material passed to the authority for independent verification. | No DB/App/vault/session-signing resources, no returned issuer capability/token, no legacy resource fallback. Client or transport authentication is not independent approval. |

The logical “privileged tier” is these first two collaborating roles; it is not a claim that the native supervisor must read DB authority itself. Any earlier resource-channel wording that the native custodian independently reads claim/policy/session rows should be read as a **trusted compiled Node authority responsibility**. The native owner supplies fresh instance/resource binding; Node performs original DB locks and current business checks. Neither accepts a caller’s claimed success from the other as a substitute for its own responsibility.

## Exact initialization graph (proposed; no execution performed)

1. Fixed native supervisor verifies the supported package/runtime and creates one owned child for one epoch. No caller-selected entrypoint, command, executable config or loader is accepted. Resource provisioning remains unavailable until that exact child’s selected native instance/recipient binding is proved.
2. The fixed **private bootstrap**, before authority modules can initialize resources, accepts the minimum resource material through the reviewed private instance channel once for that epoch. It has no public “get credentials” method. No material is placed in environment, argv, logs, files or a JS global registry; nothing is returned on the public business channel. Losing/mismatching that epoch permanently refuses rather than reconnecting a generic process.
3. That bootstrap creates one private Node resource context and the actual Prisma client using explicit private constructor configuration. It creates the vault/session-verification/App-config dependencies using private lexical inputs, then privately constructs the existing compiled session resolver, stores, token readers, coordinator and fixed transport. Public data-only handlers capture only that fixed composition; arbitrary requests cannot choose a repo/fetch/key or create a new context.
4. A real operation invokes the same compiled graph. Native lifetime/resource binding is checked before claim, before/after awaited credential acquisition and at final synchronous send; Node independently retains original session/approval/source/policy/connection/deadline checks and transactional claim/lease semantics. A native ready observation never becomes business approval.
5. On disconnect, revocation, epoch loss or crash, preserve original consumed/unknown and outstanding credential history. A restarted process gets no old permit; read-only recovery uses the actual authoritative records. Quiescence/fleet/legacy and all uncovered-profile gates remain unchanged.

This initialization requires real source API changes; the current source **cannot** do it merely by supplying an opaque handle or changing launch configuration.

## Concrete source API requirements before implementation approval

| Current actual API / behavior | Needed private-resource adaptation; no substitute claim |
|---|---|
| `lib/db.ts:3–20` eagerly exports `new PrismaClient()` (or isolated-runtime configuration), with a development global cache. Coordinator accepts an actual repo but other imported helpers reach this global. | A supported-profile private client must be instantiated with the actual explicit datasource configuration inside the fixed authority bootstrap, without `DATABASE_URL` environment fallback or a global resource registry. Existing trusted compiled callers must use that client; importing the old global cannot create an alternate authoritative client. Prisma legitimately needs real connection configuration: a native opaque handle is not currently a Prisma datasource. |
| `credentialVault.ts:6–15,64–74` resolves shared key material from environment/fallback on each scoped decrypt. | Retain the actual AES-GCM/context algorithm but supply the private key through a closed authority-owned vault instance/dependency. Existing global decrypt exports cannot fall back to environment in this profile. Buffer/string/cipher lifetime/copy behavior needs honest review; Node receiving secrets in private memory is necessary for this design and is not a zero-memory-exposure claim. |
| `githubConfig.ts:104–174` and `platformGithubAppCredential.ts:60–87` use global Prisma/platform singleton and environment fallback, then the vault to obtain App key. `githubAppAuth.ts` signs/mints and caches tokens. | Private App configuration reader uses the actual private repo/vault and existing scoped signing/mint logic, with no fallback outside that context. Prefer reading the encrypted platform App row through the private DB/vault rather than redundantly provisioning another raw App key. Exact required bootstrap material depends on that selected custody plan; no generic credential-delivery interface. Scoped token cache is private to this qualified process/epoch and retains exposure accounting. |
| `resolveRequestDesktopSession.ts:6,64,94,126+`, `desktopSession.ts`/store and `desktopToken.ts:26–27` depend on global DB and environment signing secret. | The actual compiled current-session resolver/store and token verification must receive private authoritative dependencies too. Opaque user token is request data, not authority; a forwarded “verified session” DTO is insufficient. Private signing-key custody/compatible existing-token migration must be specified, not silently recovered through `NEXTAUTH_SECRET` in web. |
| `releaseProviderMergeCoordinator.ts:31–38,100–118` accepts configurable ports; `releaseProviderMergeTransport.ts:27–55` accepts credential/current/submission/fetch. | Keep testable factory APIs where appropriate, but the production fixed authority entry privately chooses the sole repo/credential/current/native-lifetime/fetch graph. Exclusive real resources plus closed launch are required; a JS token/factory check alone is not evidence. Actual final HTTP request remains the existing compiled transport. |

**Required material, not placeholders:** a legitimate private Prisma datasource configuration; the key necessary for the selected vault-encrypted platform rows; the actual session verification/signing material or a separately reviewed compatible identity authority; nonsecret fixed App/connection configuration where not loaded through the private DB. The exact platform mechanism that delivers this only to the actual owned qualified Node/bootstrap instance is **not yet proved or implementation-approved**. If the selected mechanism cannot deliver those real APIs’ inputs under the stated constraints, stop and identify that incompatibility; do not claim a native handle makes Prisma/decrypt work.

## Decision and proof gates

- Review the selected native recipient/provisioning semantics using the separately approved public platform documentation; neither same UID/code signature nor the current250ms challenge alone establishes resource custody.
- Approve the exact minimal private bootstrap payload/lifetime and the required source API adaptations above. This is a new authority boundary. No generic module receives resource material and no public caller receives it.
- Approve the process-wide no-resource web cutover and actual DB/key/session migration separately, including all organizations/legacy paths sharing current signer/vault keys, old token exposure and read-fact compatibility. Real grants/provisioning/service/deployment require operational consent beyond local code.
- Independently review the actual emitted compiled graph and its closed resource creation, then qualify it under the original same-consumer/tamper/loader/claim/credential/freshness/unknown matrices. Simulated composition cannot stand in for actual custody. Full master profiles, fleet/legacy/drain and unsupported paths remain blocking.

Until these decisions/proofs exist, this is a reviewable architecture with explicit API gaps, not a working C implementation, qualified issuer, universal coverage or an authorization to enable Governance.
