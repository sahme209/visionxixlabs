# A2 synthetic custodian installation and access-policy specification

**Design specification only.** User approval `call_Nu5fVdY8QbGHZLHdabhskBJr[0]` authorized this specification, not implementation or operation. Supersedes the earlier unbounded collision-discovery candidate for this new-item profile. Parent design chain: `09c662d4`, `992c1a5b`, `10c83879`. Same local SDK only; no external reads, code/test generation, compilation, OS API invocation, Keychain/service/provisioning/grant action or production resources.

## Exact scope and trust boundary

One dedicated non-root custodian, one administrator-installed immutable package generation, three newly added synthetic generic-password items in the file-based System Keychain. Trusted human operator, installation writer and root/host administrators are outside the attacker model. They may change policy and must quiesce the installation first. No claim protects against malicious root, privileged backup readers or old production key copies. Unbound apps, workers, same-signed alternate programs and all runtime requests remain untrusted. The provisioner is a privileged maintenance program, not an agent-accessible service or generic credential API.

The future installer must bind to a human-approved package and a concrete locally allocated installation generation. No unbound caller supplies its executable path, access policy, selectors, UID, resource bytes, launch arguments or generation. A signed receipt or root-owned JSON file alone never qualifies startup. Actual installed program/configuration protection and OS-enforced resource access are part of the assumed trusted boundary and must be qualified in the real synthetic deployment.

## Fixed installed layout and launch

Proposed installation root: `/Library/Application Support/Vision XIX Labs/Axiom Synthetic Custodian/`. Its parent chain and installation root are root-owned, not writable by the dedicated principal or any untrusted group/user; directories mode 0755. Each approved generation occupies a new root-owned `generations/<generation>/` directory; no mutable `current` symlink. Supervisor, fixed Node executable, native addon and complete sealed consumer package are installed within that generation, root-owned with executable files 0755 and ordinary files 0644. Refuse symlinks, unexpected hard links/owners/write permission, substituted mounts or files that cannot be bound to the loaded image. Modes alone are insufficient if ACLs or another mechanism grants write access: qualification must exclude those paths too. No shared user-writable dependency/cache/loader or writable ancestor is allowed.

System launch label: `com.visionxixlabs.axiom.synthetic-custodian.<generation>`. Root-owned `/Library/LaunchDaemons/<label>.plist`, mode 0644, uses an absolute generation-specific Program path and fixed arguments. Dedicated non-login account `_axiomissuer_synthetic` is provisioned only under separate approval; launch UserName is exactly that account, not root. The numeric UID is an installation-resolved identity, not a caller number or authority proof. No GUI/login inheritance, environment credential injection, caller-defined working directory, search-path lookup, dynamic loader option or arbitrary command parameter. Exact environment allowlist must be frozen with the package implementation; unsupported inherited variables refuse. No general writable stdout/stderr destination or secret diagnostics.

The fixed supervisor starts before workers/listener, disables Keychain interaction, verifies current system-session attributes, dedicated principal and actual loaded immutable installation/root provenance, then creates private supplier state. These checks are necessary within the administrative boundary; they do not independently attest launchd origin. Public headers inspected here supply no standalone installation/launch attestation. The installer-to-custodian relationship is the actual trusted system installation and enabled launch with protected dependencies, not an authenticated JSON exchange. If the threat model requires independent proof against that installer/root boundary, this model is unsupported.

A generation is an administrator-allocated fresh fixed identifier, recorded in root-only transaction state. Allocation is serialized by the trusted installer; any existing transaction/directory/launch label is a collision and refuses, including incomplete prior attempts. Exact generation identifier syntax is 32 lowercase hexadecimal digits, allocated independently of runtime requests. Randomness/uniqueness implementation is not selected by the inspected Security headers; the trusted operator must ensure unused generation allocation. No generation is reused after partial failure. A fresh installed process owns that generation; restart does not inherit a native epoch or a consumed delivery capability.

## Rejected candidate access policy: retained for history

Historical intended owner: `(uid=0, gid=0, ownerType=kSecUseOnlyUID)` for each new item; no replacement effective policy is selected. Administrative owner modification authority is deliberately trusted. The local `SecAccess.h` declares these fields/constants but does not fully document every owner override; real supported-version qualification must establish their actual effects. No dedicated-user ownership assumption substitutes for this check.

The rejected candidate intended a final access object with one simple ACL entry:

| Field | Selected value |
|---|---|
| Trusted applications | One `SecTrustedApplicationRef`, constructed from the absolute installed generation-specific supervisor executable path; never NULL/self, installer, directory wildcard, signing-team wildcard or other program. |
| Authorization array | Exactly `kSecACLAuthorizationDecrypt` and `kSecACLAuthorizationKeychainItemRead`; no `Any`, export, modify, delete, ChangeACL, ChangeOwner, partition or implicit default entries are selected. Both selected tags are declared; whether both are necessary/sufficient for this generic-password operation must be qualified. |
| Prompt selector | Numeric zero, selecting none of the declared require-passphrase/unsigned/invalid prompt bits. **Zero is not claimed to mean deny other applications or globally disable UI.** |
| Description | Fixed nonsecret `Axiom synthetic custodian bootstrap`; it is display text, never policy identity. |

**Rejected construction, not implementation-ready:** candidate `15b96dfa` proposed building a simple ACL entry and passing `[explicitEntry]` to `SecAccessCreateWithOwnerAndACL`. The separately approved [Apple source findings](apple-acl-source-findings.md) show that this API consumes authorization-name strings rather than transplanting `SecACLRef` entries. Do not implement that call or treat the header's array description as sufficient construction semantics.

The same findings show that the simple application-list subject includes a prompt alternative even when flags are zero; changing authorizations does not remove it. Therefore the selected simple-ACL recipe is rejected as the mechanism for prompt-free exclusive custody. This is a source-alignment finding about public source, not evidence of an unauthorized read or an attested match to this Mac's framework. The table above records historical intended inputs; it is no longer a selected effective policy.

`SecAccessCreate` defaults and successful OS writes still do not establish exclusivity. The earlier uncertainty is now a concrete construction mismatch plus an unwanted subject alternative in the reviewed public source. No replacement API or effective deny policy is selected by this correction.

Any future separately selected complete boundary must receive platform/operator qualification showing that it excludes every untrusted read and modification route under supported versions and the stated trusted-admin boundary, including another process running as the dedicated principal and same-signed alternate path. Trusted-application path creation is not assumed to be path-exclusive when executable/signature equivalence is considered by the OS. Admission of different programs that can omit mandatory checks rejects the policy. A copied immutable genuine supplier may instead be refused before every read by the full enforced boundary, only under the concrete requirements in the [composed-boundary decision](composed-custodian-boundary-decision.md); this is not current qualification. Do not broaden the trusted set or call source checks custody. A different subject/prompt/owner policy requires a reviewed design amendment; the rejected construction cannot proceed merely after a successful synthetic read. Until this semantic gap is resolved, positive supplier code is not authorized and the gate stays zero.

## New-item transaction and collision handling without match-all

No pre-add Keychain search is selected. For each fixed account `authority-postgres`, `vault-key`, `desktop-session-key`, use service `com.visionxixlabs.axiom.synthetic.bootstrap.<generation>` and the same exact installation-selected file-based System-Keychain reference. New-item data is synthetic only: isolated synthetic PostgreSQL datasource, exactly 32 vault bytes and 32–4096 session bytes. Never read/reuse a historical production value. Credentials still require separately approved generation/input handling before operation.

Perform exactly three serial `SecItemAdd` requests, each carrying generic-password class, exact service/account, `kSecUseKeychain`, a future separately approved effective `kSecAttrAccess` (the historical recipe above is rejected), bounded synthetic value and `kSecReturnPersistentRef` only. Local headers permit persistent references to be stored/passed between processes; their actual returned size is not documented as bounded. The trusted installer must reject an oversized returned locator and stay incomplete, but that does not assert a bound on framework internals. `errSecDuplicateItem` means the item already exists and aborts the generation. All other failures also abort; do not query which item collided, accept existing items, update, SetAccess, delete, retry with changed selectors or automatically roll back items. Three-item atomicity is not asserted. Partial state is recorded for separately approved human recovery and never enabled.

The local `SecItemCopyMatching` comments also permit a numeric match limit greater than one with up to that number of returned items; that would bound returned count, not internal work or uniqueness beyond the selected limit. It is unnecessary for this new-item transaction. This avoids the **unbounded match-all result enumeration** entirely and uses the OS add collision decision instead of a racy “check then create.” It does not claim bounded OS database search work, runtime or allocation: the API comments provide no such hard bound for Add or matching. Initial installation is a trusted offline maintenance operation, with no real-time acceptance claim. An uncertain/blocked Add leaves the generation incomplete and never launches it. Future worker/process timeout containment requires separate implementation approval; a timeout cannot prove the OS write did not occur, so no automatic retry is allowed.

Persist the three exact opaque locators in a fixed-version root-owned mode-0644 locator file at the immutable generation root, containing only those nonsecret references and fixed generation binding; no secret bytes or “qualified” booleans. Keep privileged transaction/recovery state separately in a root-only mode-0600 journal. The non-root custodian reads only the locator file; it is never elevated to read the journal. Both files are protected from untrusted writes. The locators are selectors, **not credentials or authorization capabilities**. Deliver the binding only through the installed fixed startup path, never caller IPC. Locators may disclose item identity and must not be logged publicly.

The custodian resolves each exact persistent reference with `SecItemCopyMatching` using macOS-specific `kSecMatchItemList: [theSinglePersistentCFDataRef]`, constrains the fixed keychain and uses `kSecMatchLimitOne`/`kSecReturnRef`; it does not rediscover by service/account or enumerate matches. It requires the returned actual item type, containing keychain, fixed attributes, owner and known ACL shape, then retains exact item references. Subsequently it reads only those references under actual current OS authorization, with original deadline/cancellation/lifetime checks. This avoids a duplicate-count discovery requirement because installation uses returned item locators and actual Add collision enforcement. The local declarations describe persistent-reference querying and match-one result limit; they do not promise hard bounds on query work/internal memory or unforgeable locators. Locator substitution cannot grant access without actual policy and installation enforcement. Denied/malformed/missing/mismatched references refuse, with no name fallback.

## Epoch, changes and future acceptance

The trusted installer never mutates active-generation program/configuration/item policy. It must quiesce the old supervisor/children and preserve consumed/unknown exposure history before separately approved changes; new generation means new items and fresh process/native epoch. Killing a process cannot prove earlier provider exposure was revoked. No policy record grants a reusable bootstrap capability, and no old locator/process is accepted automatically in a new generation. Runtime metadata checks detect supported changes but are not a complete defense against concurrent trusted-root mutation; trusted administrative serialization is explicit.

Future separately authorized acceptance is finite and must use the actual installed synthetic OS boundary:

| Case | Required observable outcome |
|---|---|
| Exact fixed non-root custodian, complete fresh generation | Three actual authorized reads; owned one-use pipe delivery under existing native lifetime; no UI, secret logs or generic credential endpoint. This is not compiled-consumer qualification. |
| Other user, unsigned or different same-signed program, other process under dedicated UID; copied genuine supervisor outside protected path | Different-code/direct-read and policy-change routes denied by actual OS policy, including interactive alternatives. An immutable copied genuine supplier may instead refuse before any read under the composed-boundary conditions; no copied/unqualified process obtains material. |
| Modify item/ACL/owner/keychain backing file, package, plist, locator, ancestors or launch inputs as untrusted caller | Actual denied mutation; no resulting positive startup. |
| Collision at each of the three Add positions | Generation remains incomplete; no query/enumeration, reuse, delete, SetAccess, automatic retry or enabled launch; prior successes remain explicitly partial. |
| Crash/uncertain Add/oversized or invalid locator | Incomplete, no inference of absence and no automatic write retry; separately reviewed recovery only. |
| Missing item/wrong keychain/substituted locator/unexpected owner/ACL/loaded image/context/UID | Refuse before material delivery; no name fallback, repair or UI. |
| Old process/resource generation after administrative change; interrupted/restarted delivery | No inherited native epoch/delivery capability; original unknown/consumed history preserved and no resend. |
| OS query delay/cancellation after possible partial read/write | No late delivery; uncertain OS writes remain incomplete. Internal framework hard bounds remain unclaimed. |

These are acceptance requirements, not newly generated tests. The originally blocked compiled-consumer experiment must not be recreated or renamed. The initial synthetic deployment proves no production key withdrawal, historic-copy erasure, DB compatibility or real fleet enforcement.
