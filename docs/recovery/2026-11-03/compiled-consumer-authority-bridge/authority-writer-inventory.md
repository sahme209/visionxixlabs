## Concrete custody-design implications

1. A least-privilege proposal must cover both record and event rows, identity/policy facts and all transition writers. A role that can rewrite authority inputs can bypass effect custody even without the provider key; a process with the key can bypass a mere JS approval guard.
2. First separate **trusted authority authoring**, **issuer claim/effect ownership**, **read-only presentation**, and **authenticated containment revocation**. Do not grant general web CRUD to shared workflow storage and call the service exclusive. Exact storage/role enforcement is a pending design choice, not an implemented claim.
3. Inventory actual deployment principals, secret locations, key fallback, background jobs, webhooks, operator scripts and admin/DB-owner powers under explicit read authorization before approving operational migration. No such live inspection occurred here. Source cannot establish removal of a deployed credential or revoke an older runtime.
4. Extend the existing AST candidate catalog with reviewed classifications for this finite map during a later approved implementation, rather than regenerating a whole security catalog now. Dynamic SQL, adapter repositories, model aliases, non-TypeScript tooling and direct operational DB writers are coverage gaps. Search absence is not proof of no writers.
5. The next reviewable C design must select actual enforcement for these rows and define migrations/backup/restore/revocation before implementation authority. Local inert resource composition can test contracts later but cannot stand in for exclusive real custody, original same-compiled-consumer acceptance, fleet/legacy/drain qualification or full master executor coverage.
