# Conservative maximum-write classifier correction

The approved design rejects retained shared maximum-write mappings, including those with closed file descriptors. Actual owned fixtures showed SM_PRIVATE cannot establish that guarantee. This correction removes PRIVATE/COW as sufficient allow authority: every maximum-write mapping now refuses. It does not widen any positive boundary or qualify a usable runtime.

Genuine RED evidence: two recorded shared mapping shapes returned false-allow (exit1); actual owned MAP_SHARED file plus POSIX shm assertions returned exit20. After correction, both regressions exit0. All 33 existing classifier assertions pass with PRIVATE/COW maximum-write expectations corrected. Installed SDK compile uses xcrun clang -std=c11 -Wall -Wextra -Werror -O1, inventory.c linked only with standalone test sources; no initializer/profile code loaded.

One additional bounded own-process comparison queried VM_REGION_BASIC_INFO_64 after checking installed SDK struct/count. Exact returned region/count is checked and returned object-name ports are deallocated. The diagnostic `shared` flag was 0 for known MAP_SHARED file mappings both before and after adding a shared alias, and for POSIX shm, just as for private/COW. Thus this candidate field does not discriminate the required safe boundary in this experiment. No field absence, external_pager, user_tag or named-path value is whitelisted. The first refused baseline mapping changes after the conservative fix, as expected; it is not the earlier baseline guard observation.

Three corrected executables exit0 under 10-second parent bounds; the additional BASIC comparison also exits0. No NoWrite run, addon load, mount, private identity, provider read/write or activation. Canonical availability remains unavailable. A usable runtime still requires a stronger justified capability mechanism and original actual handoff/backing-image/same-artifact gates; these results are not that qualification.
