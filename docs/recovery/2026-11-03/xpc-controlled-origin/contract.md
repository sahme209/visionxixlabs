# Candidate fixed launch origin: XPC messages plus trusted spawn lifetime

**Design only.** The owned resource unit passed its bounded matrix (`protected-resource-result`); it did not run or qualify the actual canonical issuer. Prior retained-FD and blanket-shm failures remain unchanged. This contract adds no runtime code, registration, profile/mount experiment, broker or positive identity. The current main still refuses.

## Concrete supported topology

Choose one signed, fixed native broker advertised as a **per-user LaunchAgent Mach service**, provisionally `com.visionxixlabs.axiom.issuer-origin`. Its plist is inside the signed app's `Contents/Library/LaunchAgents` and uses `BundleProgram` plus one fixed `MachServices` entry. A separate explicit registration action through `SMAppService.agentServiceWithPlistName` / `registerAndReturnError` is necessary; it is not included in design or local-code approval. Requires macOS13+ and signed app, checks status/approval, and an explicit unregister cleanup/update lifecycle. No privileged service flag, LaunchDaemon/admin role, dynamic service-name registration or background-item workaround. Exact registration and rollback are review gates before any test changes user state.

This avoids an unsupported anonymous endpoint transfer across exec. `xpc_connection_create(NULL,...)` creates an anonymous listener, but a portable initial endpoint delivery across this exec is not supplied by the current public contract. Do not serialize an XPC endpoint into argv/env, invent private Mach/XPC calls, or treat inherited channel ownership as the postexec sender. A bundled-XPC alternative may be investigated later if its exact discovery topology is demonstrated; it is not assumed here.

The broker is the reviewed fixed launcher: verifies its own running code, actual readonly closed package/dependencies/native closure, signed release inputs and exact canonical paths, then permits only one fixed child at a time. It cannot attest/adopt an already-running process or accept executable/argv/environment/package roots from a requester. UI authorization to request that fixed local launch is separate from every later provider action.

| `xpc_connection_set_peer_code_signing_requirement(connection, const char *requirement)` | `int`, macOS12+. Set **once per connection before activation**; nonzero/ENOTSUP refuses. | `SecCodeCreateWithXPCMessage(actualReceivedDictionary, kSecCSDefaultFlags, &SecCodeRef)` | Public `OSStatus` declaration selects actual sender using its associated audit token. | `posix_spawn(pid_t *, fixedPath, fixedFileActions, fixedAttrs, fixedArgv, fixedEnv)` | Broker-owned exact child; `POSIX_SPAWN_CLOEXEC_DEFAULT` and explicit readonly stdin/owned pipe output; no pass-through capabilities or shell. PID is internal slot bookkeeping only. |
| `waitid(P_PID, child, &siginfo, WEXITED|WNOHANG|WNOWAIT)` | Public `sys/wait.h`; WNOWAIT leaves child waitable. Observe direct-child exit without consuming/reusing its slot. | native client `getpid()` | Actual SELF kernel PID inside fixed verifier, no JS argument. Compared to the authenticated broker's exact still-owned spawn slot as an additional launch-origin check; **never PID alone**. |

`xpc_connection_get_pid` explicitly warns of recycled IDs and delayed invalidation. It can at most reject an obviously different peer, never establish identity. No public received-message audit-token getter was found in installed xpc headers; this contract does not use one. `audit_token_to_pidversion` exists but does not supply a trusted token or establish exec semantics by itself. No guessed audit-word layout or claimed OS exec-generation token is introduced.

## Startup protocol / source flow

1. Broker holds one locked slot `{ownIncarnation, monotonicallyIncreasingLaunch, directChild, lifecycle, canonicalStartupConsumed=false}`. The incarnation/launch numbers are replay locators, not authority. Its only creation path verifies the actual closed readonly package, starts the fixed restriction-first bootstrap, and records the returned direct child. Fixed bootstrap applies the already reviewed restriction-before-exec path and execs exact packaged Node/CJS; no public request changes those choices.
2. Before app imports, actual canonical CJS verifies main/worker/cache/closed-loader/native/root/argv/environment conditions. It must refuse if the fixed addon is already present in its native module cache: cached empty exports cannot constitute fresh initialization. Only then require the exact manifest-bound addon. Native initializer is no-argument, process-one-shot and exports frozen empty state, no setter/token/boolean/callable initializer.
3. Native initializer creates its own fresh Mach-service connection; sets broker release requirement once; activates and sends one fixed `begin` dictionary with a fresh private native challenge. No caller-supplied socket, received dictionary, PID, reply, locator or callback is accepted. Broker verifies actual message code against the allowed Node release and its own live single slot. It never makes a slot from message contents or issues identity to an arbitrary existing process.
4. Broker observes its unreaped direct child with waitid/WNOWAIT and replies **on that actual reply channel** with the intended child PID, its current live slot/incarnation, an echo of the challenge and a fresh broker challenge. Native helper checks the actual received message's running broker identity, exact schema/deadline/challenge and `getpid()==intendedChild`. Thus a same-signed Node process outside the broker's slot cannot initialize, even if it knows the service/slot locator. The SELF comparison is a prerequisite inside trusted native code, not a `selfMatches:true` JSON field trusted by the broker.
5. Native returns one acknowledgement through its own connection after SELF/local checks, bound to both private challenges/current slot. Broker may permanently consume startup only in that live slot; no provider ability is issued by this acknowledgement. A foreign sender might cause refusal/denial of service if it races the singleton: that must not create any canonical capability, adopt the peer or reopen a consumed slot. Exact forward/race behavior is a first-unit test, not a promised result.
6. Only successful completion in that **fresh actual native constructor** permits the already-verified actual main module to establish private lexical state. Same-module consumer reads remain in that one actual cached canonical CJS module. Native cache/constructor behavior must be demonstrated on exact packaged Node: clearing caches, duplicates, workers, re-require or native-image aliases must either re-enter a refusing one-shot constructor or refuse before private state. Merely requiring cached empty exports is expressly insufficient; if the no-public-initializer topology cannot prove freshness, stop for a specific design revision rather than add a public initialization method.
7. Keep the native connection private/live. Recheck actual received messages against broker code and monotonic challenge/lifetime; invalidation/timeout/broker restart/direct-child exit or unexpected protocol revokes local availability. Broker observes exit before reaping and destroys that slot permanently. It never adopts the old process after restart. A re-exec loses the old JS/native private state; the broker's consumed startup cannot initialize a new main even if the numerical PID remains. This establishes a logical launch-slot lifetime and post-consumption replay fence, **not an OS exec-generation proof**. It cannot distinguish an extra same-signed exec before the first ACK. The proposed security objective is the still-owned, still-restricted **exact verified canonical artifact with one startup authority**: same exact canonical re-exec before any private initialization is not authority replay and need not be rejected merely for its history. This prospectively supersedes the earlier agent-added blanket pre-ACK re-exec rejection **as a design proposal only**; it does not alter any previous result or activate identity. A different artifact/entrypoint and ANY after-ACK re-exec must refuse. Signature/PID do not prove the JS entrypoint: the actual trusted fixed pre-import code must have no extra-exec, untrusted loader or caller-controlled entry path, and current canonical/closure/fresh-native-initialization checks remain necessary. The mechanism cannot attest arbitrary exec history or defend against malicious native code already inside the trusted issuer. If that source-flow prerequisite cannot be established, private initialization refuses.
8. At the actual durable claim/sole-write seam, the real private module must still provide current executing identity and current origin liveness along with all existing exact action/approval/current-access/source checks. A detached startup transcript, stale boolean or periodic observer result is not a synchronous fresh dispatch authority. Exact bounded NAPI/async admission integration must be specified before wiring coverage; provider actions remain unavailable until that same compiled consumer test passes.

## Why forwarding/replay does not become identity (required attacks)

An endpoint/service name is a locator. A forged dictionary lacks an actual associated sender and is rejected by Security APIs; relaying values through a different live connection still authenticates that connection's actual native sender. Both code identity and native SELF==broker-owned-child checks must pass before private canonical state. Forwarded/inherited connection assumptions are not accepted as proof. The helper accepts no public channel/dictionary and holds challenges privately. Broker slot liveness/one-startup state is native-owned; no peer PID, self-claim, message challenge or package receipt constructs it.

Those facts are candidate reasoning, not measured acceptance. Mandatory adversarial cases: external same-signed Node; foreign process with forwarded endpoint/connection/message; wrong broker/release; copied helper/custom main; wrong/changed package; replay/out-of-order/second begin/ACK; stale challenge; child exit during each exchange, broker crash/restart, PID recycle after slot destruction, same exact canonical pre-ACK re-exec under the proposed semantics (never a second private initialization), different-entrypoint pre-ACK re-exec, and ANY post-ACK re-exec; helper and CJS/native cache duplication/worker/cache clearing. If a forwarding path initializes private state in an unspawned process or a cached helper blesses a duplicate canonical module, the design fails and remains unavailable. Under this proposed objective, a pre-ACK same-canonical control may remain eligible only while no prior private initialization exists and every current fixed-source/closure/native gate passes. Record it as prospective accepted-origin semantics, never as proof that the APIs detected its exec history. An altered entrypoint or caller-controlled preinit path remains a failing attack; a PID/signature match cannot excuse it. Preventing arbitrary malicious native code already running in the issuer is outside the original trusted-localhost model; no such protection is claimed.

## Next mechanistic unit — approval scope must be concrete

After design approval, **local implementation/ordinary isolated tests only** can prepare a tiny signed broker and no-profile/no-identity test client using these exact APIs. First unit must prove real per-message requirements/SecCodeCreateWithXPCMessage, native SELF+direct-child slot rejection of an independently started same-runtime peer, one-shot constructor/cache refusal and disconnect revocation. It emits only bounded observations, not an issuer digest, and exercises no provider, mount or restriction. Signing requirements/identifiers and source/binary hashes are fixed for review first; do not use current unsigned/foreign binaries as a structural positive.

The first unit may establish message/SELF/cache primitives and record the proposed pre-ACK semantics; it cannot initialize real private identity or claim arbitrary exec-generation detection. This exact source-flow trust objective, the service-registration dependency and the eventual private NAPI/canonical integration must receive the user's specific local implementation review before code is written. Actual LaunchAgent registration changes user background-service state and needs a separate exact installation/cleanup approval after inspectable artifacts exist. A named listener cannot legally be dynamically added without its advertised launchd service; no implementation may fake that by private bootstrap APIs. If platform provisioning is undesirable, stop to review an alternative supported endpoint bootstrap rather than silently reuse raw UNIX ancestry. Only after the mechanistic unit qualifies should this be combined with the actual readonly package/restriction and the real canonical CJS→compiled durable consumer; all original immutable/tamper/cache/duplicate/restart/action gates remain.
