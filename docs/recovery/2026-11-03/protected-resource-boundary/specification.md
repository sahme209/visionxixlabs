# Revised design: protect executing code and authority resources

Status: **design only**. User delegated the design choice; the selected boundary protects the verified executable package, its backing resources and private execution authority. It does not promise denial of every writable memory object. No runtime implementation, profile experiment, image mount, broker, credentials or identity activation is authorized by this specification. Canonical availability and enrollment remain unavailable.

## Preserve the evidence and original endpoint

The original approved NoWrite experiment installed the restriction but retained file writes/truncation succeeded. The later restriction-before-Node experiment started Node and blocked owned ordinary/shared-file effects, while fresh POSIX shared memory remained writable. Both are failures under their respective reviewed matrices and stay immutable. Neither is now relabeled a passing security result. The later blanket writable-shm requirement is superseded **as a design objective**, not retroactively changed in its results.

The original immutable closed-package/loaded-code consistency/private controlled-launch origin and actual canonical same-module issuer→compiled store→sole transport endpoint remain required. A filesystem hash, parent receipt, environment token, PID, open channel or code-signing digest alone is never executing identity. Current source fixes, source tests and this document do not qualify those controls.

Threat assumptions remain the trusted local host/kernel and reviewed launcher/runtime/application closure. A hostile administrator, arbitrary malicious native code already executing inside the issuer, forged kernel, or compromised signing/build trust is not claimed contained. Trusted code may create ordinary private runtime memory. This is not an extension to hostile-host protection, generic arbitrary-code execution safety, network denial or whole-process tamper resistance.

## Protected resources and rules

| Resource | Required boundary | Refuse / acceptance attack |
| --- | --- | --- |
| Exact Node, canonical CJS/reader, native helpers, full application/dependency/config closure | One closed verified artifact on the actual kernel-readonly image; canonical fixed main/argv/env/cwd, no development/HMR/preload/cache/module-root/executable-config fallback | Missing/extra/changed files; aliases/external symlinks; alternate Node or native helper; mutable config that selects code; replacement before verify/import or during concurrent import |
| Actual image backing file and hardlink/owned aliases | No inherited writable FD or shared backing mapping; revised fixed launcher installs restriction before Node exec; validate effects against actual image, not only inside readonly mounted view | Retained high-number FD, replaced writable stdio, backing-file write/truncate/rename/unlink/metadata, hardlink alias, closed-FD shared-map upgrade. Any modified protected bytes/identity or unexplained authority refuses |
| Executable import/loaded-code provenance | Main-only CJS verifies before application imports; every executable/native load belongs to the sealed manifest and reviewed load behavior, with actual cache/duplicate/restart checks | Caller-selected entrypoint, worker/direct import, duplicate CJS cache/path, external package search, writable code cache, runtime input/shm bytes used as script/module/native source. A post-load hash cannot bless earlier code |
| Private executing capability | Only the actual canonical main module establishes lexical state after qualified local checks and live kernel-authenticated fixed launch origin; exact compiled consumer reads that same module | Serialized proof, public initializer/setter, copied object/module, IPC/JSON/HTTP/env injection, stale/replayed/other-process origin, wrong compiled consumer, restart using old identity |
| Launch-origin channel | Reviewed fixed native broker and trusted spawn slot; fresh post-exec peer identity checked against actual running release code and current process generation/lifetime | Socket possession or numeric PID alone, descriptor forwarding, wrong signed program/release, separately started same Node, process/parent exit, re-exec/PID reuse, second connection/replay/unknown lifetime |
| Fresh isolated POSIX shm or anonymous memory | Permitted **only as non-executable application data**, not an alias of any protected package/backing resource, loader/module/cache/config source, identity source or accepted authority channel | Shm-derived code/config/module specifier, executable memory from untrusted data, shared-memory identity/approval/provider credential/proof, unexplained external peer or protected-resource alias. Unknown use/lineage refuses qualification |

The shm rule is a usage/provenance requirement on the reviewed closed implementation, not a claim that NoWrite denies reading shm, that all shared memory is kernel-isolated from same-UID peers, or that CJS can defend against arbitrary native code. Names/paths, random naming, unlinking, `SM_PRIVATE`, `external_pager=0` and `BASIC_INFO.shared=0` are not proof of safe provenance. Fresh isolated objects must not hold credentials, private capability material or authenticity decisions. If required runtime IPC actually uses shm for authority or loading, qualification stops for a specific design review; it is not silently exempted.

No monkey-patched JS loader, public flag, structural descriptor, synthetic inventory or hash observer establishes that these rules hold. The exact emitted runtime's import/native/config behavior must be closed and verified. If it cannot be, this candidate remains unavailable rather than claiming the trusted closure exists.

## Candidate launch sequence (not implemented/qualified)

Retain the previously reviewed restriction-first candidate: fixed sealed native broker starts exact tiny bootstrap with only readonly stdin/owned pipe output; bootstrap validates closure, closes actual extra FDs, applies the fixed named restriction once and execs exact packaged Node in the same PID. Canonical main performs closed-loader checks, then the fixed native verifier authenticates live broker origin using supported kernel-backed running-peer identity plus trusted launch-slot state. Only then may the same main module establish private lexical state and import the compiled consumer.

The kernel-authenticated channel mechanism is still an unresolved gate: supported audit-token selection/exec-generation semantics must be concrete and tested; neither signature nor peer credentials proves restriction installation. A generic signed launcher or broker assertion about an arbitrary process does not pass. No broker code should be written until the exact mechanism has a reviewed contract. The unused conservative post-Node classifier is not weakened to admit ordinary Node mappings; this candidate changes where capability closure is enforced, rather than inventing a positive VM shape exception.

## Smallest useful next feasibility unit

**Prepare a reviewable artifact before requesting execution**: one actual closed compiled package (using an already accepted exact build if its closure qualifies), real readonly image, exact fixed restriction-first bootstrap, and a test-only canonical main with no identity issuance. Do not rebuild the whole application merely to repeat toy file effects. The first owned unit asks: can the fixed Node package run from this actual readonly image while all allowed owned aliases of its backing resources remain unchanged under the exact process? It does not need a broker or positive identity yet.

The exact future execution proposal must separately bound image creation/attach/detach, paths/hashes, the one restriction run, owned seeds and cleanup. No such execution is approved here. Controls must include unrestricted effects and independent after-state readback; a control that fails cannot support a denial claim.

1. Show actual readonly mount/device and full closure, then start the exact packaged Node/canonical test main. No mutable workspace import or test binary standing in for the package.
2. Attempt bounded owned mutations of image backing file and hardlink, protected package paths, substituted inherited descriptors and currentRO/maxRW shared backing aliases; verify hashes/inodes/modes, not errno alone. Prepare inherited FD/map injection controls before the fixed bootstrap so clean exec must remove them; retain original successes as NoWrite-alone failures.
3. Separately create/use fresh test shm only as data, affirm it stays outside executable/config/identity/credential channels, and attempt deliberate shm/mutable-path loader input via the canonical entrypoint. Canonical validation must refuse before any private state. This proves only those exact input routes, not universal hostile-code containment; application load-surface coverage remains explicit.
4. On any protected mutation, unresolved alias, unclosed executable/config source, missing control or unsupported prerequisite, stop. No fallback profile, metadata allowlist or automatic retry.

Only after this resource feasibility unit succeeds should a separately reviewed live origin implementation and actual same-artifact private issuer→durable claim→sole transport qualification proceed. Existing full acceptance cases remain: canonical cache/main/duplicate/worker/restart, tamper/concurrent import, current exact independently approved action/claim, and failure-before-write. Auth/provider ports may be simulated while actual package/origin/restriction/consumer identity must be real and labeled. Fleet/legacy credentials, provider quiescence and coverage activation remain separate outstanding gates.

## Decision log

This design intentionally changes the later blanket shm prohibition to protected-resource immutability and non-authority/non-loader shm use. It keeps stronger original package/private-capability requirements rather than treating a surviving unrelated shm write as proof of broken code immutability. It supplies **no implementation or run approval**, no positive identity, no automatic activation, and no unsupported security marketing claim.
