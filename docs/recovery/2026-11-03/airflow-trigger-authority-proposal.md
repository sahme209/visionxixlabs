# Airflow manual trigger and scheduled occurrence authority — proposed local implementation

Status: design for validation-first review. No runtime implementation, new role, schema migration, provider call, credential issuance, enrollment or activation. Base source 16d8be17. This is an authority/operation gap, separate from the unqualified canonical issuer and failed native confinement experiment.

## Observed source and compatibility

- `app/api/desktop/airflow/dags/[dagId]/runs/route.ts` POST currently accepts exact request conf with a current paired `deploy:execute` principal. It checks current session again before credential use/write but has no saved trigger plan, independent decision or one-attempt claim. Client generates a timestamp run ID and audit is appended after success.
- `lib/integrations/airflow/automationTick.ts` schedule branch binds rule ID/revision, connection ID/revision, DAG and scheduled time; it sends a deterministic occurrence run ID before advancing the rule. There is no pre-POST occurrence claim. A lost response can leave the same occurrence eligible at a later tick.
- `AirflowAutomationExecution` rows represent actions after a terminal source DAG run. Preserve these rows, approvals, retry policy and history; they are not trigger-operation receipts and must not be relabeled or backfilled.
- `connection.ts` checks current connection and enrollment around credential decryption, host validation and client construction. `airflowClient.ts` then authorizes and POSTs once; an explicit run ID permits a 409 GET reconciliation. Preserve read-only clients, DNS/host restrictions and exact returned DAG/run identity validation.
- Existing execution-policy/revision stores already implement independently reviewed immutable revisions, exact digests, CAS activation, revocation and chained durable events. Reuse these mechanisms and current policy-admin/approver capabilities; introduce no parallel role system. Their current schema supports repository/resource/environment scopes and fixed actions, not DAG/schedule scopes. Do not fabricate repository/environment IDs or map a DAG to deployment authority merely because its name resembles one.

## Proposed authority model

1. Add a reviewed typed scope variant for Airflow: organization, exact connection ID/revision, canonical configured base URL identity and exact DAG ID. Add distinct fixed actions for manual DAG submission and schedule-occurrence submission. Keep existing repository scopes/action meanings unchanged. A later explicit administrator-reviewed repo/environment-to-DAG association is needed before using a deployment baseline for this scope; absent mapping refuses that baseline. No model/provider string or cron secret supplies it.
2. Extend existing policy revision compilation/store/request composition to this typed scope, preserving proposed → independently approved → activated/revoked history and exact parent pointer/CAS. Scope cannot become active until actually supported enforcement coverage/issuer qualification exists. Local tests may exercise simulated authority only.
3. Manual trigger: paired requester prepares one immutable plan binding scope, exact bounded canonical conf and digest, server-generated run ID, request ID, expiry and original requester/session. A different current approver personally reviews that exact plan using existing approval capabilities. Original requester executes separately with current `deploy:execute`; approval alone never dispatches. An exact one-attempt claim precedes reservation and consequential credential access. Repeated request ID returns existing plan, not another run. This deliberately changes today's unsaved direct trigger to reviewed execution and requires design approval.
4. Unattended schedule: a policy administrator proposes an immutable schedule revision binding exact Airflow scope, original rule ID/revision, UTC cron, explicit effective/expiry interval, occurrence identity algorithm version, deterministic conf template (currently only `axiom_automation_id`), named accountable principal and permitted missed-occurrence policy. A distinct approver personally reviews it. Activation and revocation reuse policy revision mechanisms. A cron bearer authenticates invocation only; creator ID, enabled rule, legacy approvalRequired flag and `actionType:none` cannot issue this authority.
5. Define a trusted server-only scheduler authority adapter for the approved revision. It verifies original accountable/approver current membership and required capabilities, active access/entitlement, revision/pointer/revocation, exact rule revision and scope at claim and final intent. It records an actual scheduler principal/lease and its exact artifact identity; it does not invent a desktop session, impersonate the creator, or require a fictional historical session. Expired/unavailable/revoked authority refuses. A named principal's sign-out is not treated as proof all provider credentials expired. This adapter is a new explicit reviewed authority type, not a weakened `createEnrollmentDrainAuthority` user-session path.

## Durable operation and effect protocol

Use existing versioned `DurableAgentWorkflow` and chained event storage with strict new workflow kinds, not new tables. Keep policy revisions separate from trigger operations. Manual operation ID derives server-side from organization/requester/request ID. Scheduled occurrence ID derives from organization, approved schedule revision, exact rule and occurrence time; provider run ID remains deterministic and recorded. Never reinterpret earlier unknown rows or infer safe absence from missing snapshots.

Under org-first transaction, validate exact immutable plan/revision/history and current authority, then CAS prepared → claimed once. Atomically associate the actual claim with one fixed outbound slot profile and exact run/conf/scope digests before token authorization or credential release. A schedule rule edit/pause/reconnect, revised policy or expired occurrence invalidates the old operation; it does not mint a replacement occurrence to evade an unknown claim. No provider I/O under locks.

Immediately before the sole fixed `/dags/{exactDag}/dagRuns` POST, recheck source/authority and consume one durable intent; retain the returned private freshness closure across final awaits and call synchronously at fetch with the same bounded signal. Persist validated exact DAG/run receipt separately from business completion. Accepted queued/running work is not quiescent. Unknown POST/commit acknowledgment remains consumed and blocks redispatch, including a later scheduler tick. GET reconciliation can observe the exact run, never trigger again. Preserve 409 read semantics only for the original one submission, not permission to issue another POST. Any future explicit retry policy requires a separately reviewed boundary and must not reuse this operation.

Credential auth may itself mint a bearer; reserve before that call, preserve unknown issuance and do not infer lifetime or revocation from token strings, HTTP success or session expiry. Real bearer/fleet/effect qualification remains unavailable until separately proven.

## Bounded acceptance before enablement

- Manual: exact independent decision, original requester executes, changed bytes/run/DAG/path/session/current role/connection or expired approval refuses; duplicates and concurrent clicks yield one claim/slot/POST.
- Scheduled: current approved revision/expiry/accountable authority required; cron-only and creator-ID-only refuse. Paused/edited/reconnected rules, revoked approver or policy, unsupported DAG mapping and ambiguous missed occurrence refuse.
- Actual isolated PostgreSQL races: duplicate occurrence, reserve versus drain, final intent versus barrier, claim/slot commit acknowledgment loss and restart; original history unchanged. Simulated external/auth/issuer ports explicitly labeled. No provider I/O while DB locks held.
- Sole transport: canonical unavailable before claim or credential; abort/current-authority loss at each await gives no POST; lost submission/receipt gives unknown and later tick performs no POST; exact-run readback and wrong/malformed identity negatives; no automatic retrigger.
- Regression: DAG/read-only client operations preserved; existing downstream completion approvals, restart reviews and histories unchanged. No activation/coverage claim from fixture success, no live calls or production setting changes.

Implementation is gated on approval of the typed Airflow scope, manual decision separation and scheduler authority model above. No runtime change is implied by retaining this proposal.
