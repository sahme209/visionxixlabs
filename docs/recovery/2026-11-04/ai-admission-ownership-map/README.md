## Coherent migration frontier, not another guard batch

Before implementing a shared migration, specify the existing request/run owner, exact purpose and payload/model/output bound, current workspace policy, actor/billing classification, genuine reservation source and request/phase idempotency, one-use manager/provider consumption, usage linkage, and unknown-outcome retention. Tenant work reuses verified tenant identity; platform/cron diagnostics require a separately selected maintenance owner/policy. A system label or passed `organizationId` cannot mint funding. Image pricing and non-token fees need their own contract.

Migrate admitted entry points first only where a demonstrated contract gap exists; retain their working accounting. Thread an existing or newly reviewed funding capability through shared helper/orchestrator APIs, preserving no-AI fallbacks and truthful availability rather than silently substituting unpaid success. Then inspect all upstream33sites and excluded/dynamic/other-provider transports. New financial authority, availability or policy-freshness boundaries require specific validation-first design approval. This source review authorizes no such runtime change.
