# V19 Windows rename compatibility — proposed, not applied during freeze

Public desktop-v0.1.21 source configuration has productName Axiom Agent, identifier com.visionxixlabs.axiom, no custom Windows installer settings. Its release workflow includes only x86_64-pc-windows-msvc for Windows. Released package-lock fixes CLI and Windows native CLI2.11.1. That exact historical MSI implementation uses the same DNS UUIDv5 formula as current2.12.4; its NSIS template uses the same two product-name registry-key formulas. The proposed GUID is therefore source-derived expected legacy identity, not inspected MSI-binary identity. These reads establish source defaults and architecture, not inspection of the distributed MSI/NSIS binary. Source URLs, byte counts and SHA256 are in PROVENANCE.json.

Pinned Tauri CLI2.12.4 MSI implementation computes DNS UUIDv5 of productName + .exe.app.x64 unless explicitly configured. The historical input yields a3c7da37-1792-51f2-8b3a-8848b1b33f88; the V19 default would differ. Explicit wix.upgradeCode preserves this legacy upgrade identity while product/window/installer display remains V19. Its constant x64 suffix is the actual pinned implementation even when other architectures are built; do not invent new per-architecture GUIDs. Only historical Windowsx64 is evidenced here.

NSIS uses productName for both display and UNINSTKEY/MANUPRODUCTKEY, and finds previous MSI by display name plus unchanged publisher. An explicit MSI GUID cannot fix NSIS. The proposed custom NSIS template is byte-for-byte pinned upstream except: one LEGACYPRODUCTNAME definition; two registry-key definitions use it; FindWixInstall accepts either exact current V19 or historical Axiom Agent concatenated with the SAME manufacturer. Everything else, including version checks, uninstall invocation, consent, shell context, privileges, protocol registration, WebView logic and signing support, remains unchanged. No new package/code dependency or custom installer action is introduced. Existing Tauri renders this local template and its normal included helpers.

The unchanged legacy NSIS registry paths are architecture-independent in upstream, so all currently supported NSIS architecture branches retain those same prior keys and per-user/per-machine context. This preserves rather than adds cross-architecture install behavior; only released x64 needs qualification now. New registry display metadata still says V19. Existing NSIS installs can recover their original installation path from the legacy manufacturer/product key. Fresh installs default to the V19 directory. MSI recognizes old MSI by the explicit same UpgradeCode, but its default directory and new registry display keys become V19. Existing MSI paths and cross-format transitions may migrate differently and REQUIRE actual old-installer→new-installer qualification; do not claim exact path continuity from source alone. The previous NSIS matching approach itself matches display+publisher rather than cryptographic product identity; this patch preserves that upstream trust model and adds only the historical exact pair.

Five pure tests cover independently recomputed UUIDv5 bytes, V19 display versus legacy protocol/bundle IDs, exact reverse-patch SHA256 equality with the pinned upstream template, expanded legacy NSIS registry paths, existing-path restoration and dual-name/publisher MSI recognition. Baseline RED retained, then GREEN5/5. No Windows/native/build/installer execution occurred.

Important remaining gates: independent source review before applying; actual Windows MSI/NSIS compilation; verify resulting UpgradeCode/ProductCode/display names/publisher and signature policy; clean and0.1.21 upgrade/relaunch/uninstall tests (MSI→MSI, NSIS→NSIS, supported cross-format paths), no stale parallel installation/shortcut/protocol, same vault/service/session namespace. Existing closed Windows QA scaffold currently refuses every custom NSIS template; its exact reviewed template/hash policy must be deliberately adapted at enrollment, not silently bypassed. No candidate publication or installer compatibility success is claimed.
