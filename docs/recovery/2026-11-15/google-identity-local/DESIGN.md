# Local Google identity repair proposal — review before implementation

No source change, migration execution, account read, OAuth attempt, build, or deployment performed. This fixes source identity gaps; it does not establish the cause of historical AccessDenied or prove live Google configuration.

## Existing evidence and reuse boundary

Current lib/auth.ts signIn ignores raw Google profile and upserts User by email; JWT separately resolves by email and can return without canonical id; audit receives Google sub as user.id. Installed NextAuth without adapter passes the same profile object from signIn to JWT/events (core/routes/callback.js and core/lib/callback-handler.js). Its openid-client callback already verifies OIDC tokens/state/PKCE. Keep that verifier and canonical Host guard intact.

User has no OAuth binding. EmailVerificationToken proves a mailbox for password signup, is not Google-sub/purpose/browser bound, and resend deliberately excludes OAuth-only rows. Enterprise TenantIdentityProvider/SCIM, desktop sessions, integration accounts and historical audit rows cannot safely establish Google bindings. Reuse existing mail transport, password comparison, rate limits, safe callback parser and membership bootstrap; do not infer bindings from historical email or audit.

## Minimal identity flow

1. Only after NextAuth's qualified Google callback, validate raw profile: issuer is Google's permitted issuer normalized to https://accounts.google.com; nonempty sub <=255 equals account.providerAccountId; email_verified === true; valid normalized raw email matches mapped email. No token decoding endpoint or caller-submitted claims. Missing/invalid proof refuses with fixed actionable retry/help code, no User creation.
2. Look up OAuthIdentity(provider,issuer,subject). Bound identity selects its canonical User.id/email even when Google's current email changes. Do not change User.email or email-derived workspace silently. Show email-change information separately. A bound Google identity never falls back to an email lookup to choose another account.
3. For an unbound identity, an existing User email ALWAYS requires explicit account ownership confirmation. No silent upsert/link, including legacy OAuth-only rows. If no User exists, Google-authoritative email (verified Gmail, or verified Workspace hd matching email domain) can atomically create User + binding. Non-authoritative third-party email requires fresh mailbox proof before User creation because workspace IDs derive from email. Recheck uniqueness transactionally on every completion; an intervening signup refuses this intent and requires a fresh explicit recovery attempt, never reselects or silently merges the new existing account.
4. Existing verified password account: the recovery page offers its existing password, with current verification and rate limit requirements. OAuth-only legacy account or no-password route: offer a fresh explicit email confirmation code. This is a deliberate legacy recovery boundary, not an inference that a verified Google email is current mailbox ownership. Existing accounts already bound to a different Google subject cannot be replaced by this flow; offer existing-account login/help rather than weakening the binding.
5. Resolve canonical identity before membership bootstrap. Preserve best-effort personal membership and enterprise/seat authorization. In signIn replace the same provider user object's id/email with canonical values and register a module-private WeakMap attestation keyed by that exact object (provider/sub/canonical id); no global email-keyed map. Initial Google JWT requires matching attestation/account, sets canonical id/sub, never performs a second email lookup. Missing attestation fails before session cookie issuance. events.signIn uses canonical id/email from the same resolution. Keep account.providerAccountId as Google sub. Test actual installed callback object flow; if installed adapter behavior changes, refuse until updated, not fallback by email.
6. Subsequent JWT/session reads require a canonical signed identity version/id. Existing signed sessions without that new version reauthenticate once; do not promote legacy ID-less/email-derived sessions. Explicitly test any legacy compatibility boundary rather than adding another email fallback. Credential sign-in issues the same canonical version using its verified returned User.id; preserve GitHub/Cognito security gates and give their existing canonical resolution equivalent attestation.

## One-use recovery and usable transition

New stores are exactly migration.sql: OAuthIdentity and PendingGoogleIdentityLink; Prisma adds matching models plus inverse User relations only. No existing data backfill. IDs are random/cuid, subject is never a user-facing account selector. No OAuth access/refresh/ID tokens, password, raw cookie or mail code persisted.

The qualified Google callback creates a pending intent with candidate User.id + updatedAt snapshot (or neither), issuer/sub/email, validated same-origin callback PATH, hash of random 256-bit browser nonce, separate CSRF hash derived by HMAC-SHA256(raw browser nonce, fixed purpose + intent id), expiry min(now+15m, verified token expiry). Capture one Node now and explicitly supply both createdAt and expiresAt; do not rely on database default now for the 15-minute bound. The form token is rederived from the HttpOnly nonce on GET; a hash alone is never treated as retrievable plaintext. A request-local AsyncLocalStorage route wrapper collects this cookie response effect and appends HttpOnly Secure SameSite=Lax Path=/ nonce cookie to the fixed /auth/link-google redirect. No session is issued yet. Local HTTP exception stays existing explicit loopback-only development rule. Do not put Google claims/nonces in URL or readable browser storage.

The page says “Finish Google sign-in” and explains account confirmation. It offers password where appropriate and “Email me a confirmation code” without account enumeration. POSTs require canonical Host + same Origin, original nonce, separate CSRF token, live intent and rate limits by intent/email/browser/IP using existing infrastructure. All outward recovery outcomes are uniform until browser possession is established. The send action generates a random >=128-bit copy/paste code, stores only SHA-256 hash and <=10-minute expiry, and sends via existing mail transport. No email GET mutates identity, so scanners cannot link accounts. The mail instructs pasting into this original sign-in window. New send rotates code; bounded resend and max five failed proof attempts atomically invalidate intent. Failure increments use atomic SQL updates, not read-then-write counters. emailProofExpiresAt never exceeds intent expiry (code and SQL constraint). Missing mail transport is explicitly “Email confirmation is unavailable; use your existing password or contact support”; never pretend sent.

“Confirm and link Google” POST verifies fresh password (verified credentials account) OR fresh email code and then atomically rechecks candidate id/email/updatedAt, subject uniqueness, no different bound identity, expiry, unused proof/intent, and consumes intent + inserts binding (+ User only where proven new). Use a SERIALIZABLE transaction and CAS updateMany on intent id + original expiry + consumedAt:null + attempts<5; count must equal one. All identity/user inserts and consumption commit together; conflicts roll back and return a fixed restart code, without unbounded retry. Race/expiry/conflict returns fixed restart guidance, never switches canonical user. Existing password proof runs comparison outside transaction, then transaction rechecks unchanged password hash and candidate updatedAt. Email proof is consumed only with binding commit. Clear pending cookie on completion; expired unused intents may be deleted in a bounded existing maintenance path (not required for acceptance).

After successful link show “Google is linked — Continue with Google”; invoke normal provider sign-in for a fresh qualified OAuth callback, preserve original safe callback path, now resolve binding and issue the standard NextAuth session. No custom session/JWT mint, no automatic replay of provider code. If desktop pairing deadline expired, tell user to restart pairing; do not extend capability lifetime. The explicit additional round trip is the minimal safe legacy transition, not a dead AccessDenied.

## Local acceptance before any release

Focused tests: verified/unverified/malformed raw claims; exact sub/account mismatch; stable binding despite email change; no takeover of existing email; new authoritative vs third-party mail paths; canonical JWT/audit id; no ID-less fallback; actual installed NextAuth object propagation; all password/enterprise/membership gates retained. Recovery tests: actual handler cookie/CSRF/origin, mail-not-configured, code hash/expiry/resend, browser mismatch, five-attempt limit, token/nonce leakage, consumed replay, signup/link races, rollback, account email/password changes and different-subject conflicts. Owned local PostgreSQL migration + concurrent uniqueness/atomic-consumption integration tests use synthetic identities only; actual compiled HTTP exercises new page/POST and credential session. An isolated fake OIDC issuer may test NextAuth wiring but MUST NOT claim real Google validation.

Real post-release check remains owner-visible Google authorization on canonical origin: real state/PKCE callback, stable subject binding, canonical session id and permitted workspace, sign-out/sign-in, legacy explicit linking, failed/denied/canceled authorization recovery, and original desktop callback/pairing expiry behavior. Read-only configured-provider presence is not live sign-in proof. No prod SQL/deployment is authorized by this proposal. Missing migration must fail closed with fixed “sign-in update unavailable” recovery, never fall back to email upsert. Rollback cannot restore unsafe automatic email linking.

Primary Google references: https://developers.google.com/identity/openid-connect/openid-connect and https://developers.google.com/identity/sign-in/web/backend-auth . Google documents stable sub versus mutable email, and Gmail/Workspace versus third-party email authority. This proposal uses those rules only after the installed verifier has authenticated the claims.

No handler logs raw provider profiles, tokens, cookies, mail codes, passwords, native/Prisma errors, or URLs. Only fixed allowlisted reason codes reach diagnostics.
