# Agent review and execution separation — local implementation proposal

Status: user approved local implementation November1 (“Approve local separation”); implementation is partial. This is a concrete extension of the approved Governance integration design; it changes existing Agent decision semantics and must be reviewed before implementation. No rollout, provider write, role change or historical recovery is included.

## Confirmed current composition

Both app/api/control/agent/actions/[id]/decision/route.ts and the desktop approve/reject routes call lib/axiom/agentRuntime/browserApprovalDecision.ts. That function records an approval with a compare-and-swap transaction and then calls executeApprovedAction immediately, passing the reviewer's actor ID. The desktop entry requires agent:approve, which includes the security_reviewer role. The execution responder currently has an enrollment refusal callback, not a separately authenticated executor. The browser route also has its own authenticated approver rule; it cannot be assumed equivalent to a current tenant execution role.

This does not assert every tool is exploitable: tool restrictions, credential ownership, independent proposer checks and downstream controls still apply. It does establish that the review decision and execution identity are combined, which prevents an honest complete current-executor coverage claim.

## Proposed exact behavior

1. Approve and reject remain human decisions on the exact organization/conversation/proposer/tool/argument digest. Approve records only an immutable review outcome; it must not resolve provider credentials, reserve deployment quota or invoke an execution responder. Rejection remains non-executing and available under existing authorized stop rules. Current reviewer membership/authority is checked in the decision transaction; a caller-supplied role string is never authority.
2. Add a separate paired desktop execution action for the saved approved proposal. The original proposer is the designated requester/executor; another account cannot adopt that identity. It must be distinct from the recorded independent approver. Authorization is resolved from the current paired session and persisted accepted membership, then repeated before claim and final transport. Do not elevate the reviewer or authorize a background agent to use its account.
3. Use a closed server tool-to-requirement table matching current direct APIs: repository mutations require github:write; ECS dispatch requires deploy:execute (plus production-bypass capability only if a supported, exactly reviewed bypass exists); environment creation and target configuration require policy:manage; identity-provider creation requires current owner/admin authority. Unsupported tools refuse. A proposal or numeric limit never creates a permission.
4. Store a new exact execution record in the existing DurableAgentWorkflow/events tables, bound to org, original proposal/digest, independently recorded reviewer, requester, paired session and closed tool input. Reuse the existing one-attempt durable-store/CAS/audit patterns, not a volatile callback or execution flag. No new schema or arbitrary SQL recovery. Claim consumes at most one attempt and validates current exact approval, expiry, workspace Agent policy and target/source binding.
5. Separate immutable approval metadata from execution outcome. Retain confirmed/refused/unknown history; an unknown result is never reset, renewed, resent or automatically retried. Pre-dispatch refusal is distinct from possibly accepted provider traffic. An expired or changed proposal needs a new exact review; no old approval is extended. Existing already-executed/failed/consumed records remain historical and cannot be migrated or adopted as fresh authority.
6. Compose current provider credentials and fixed transports only after trusted stored-operation binding. Repeat exact session, role, proposal/approval, connection revision, Agent allow-list, target/source and enrollment checks at the actual write boundary. Provider reads stay outside DB locks. In enrolled scopes, require real baseline admission; until coverage is registered the operation refuses. No fake coverage receipt is issued.
7. Native/web review UI says “Approved — waiting for requester execution.” The designated requester's desktop offers a separate exact “Execute approved action” control with effect/expiry/outcome. Reviewer-only UI has no execution control. Approval never automatically resumes the model or executes a queued change. Read-only outcome checking remains available after uncertain responses and app restart; no automatic resend. Existing browser approval origin controls remain.

## Local verification before any activation request

- Approval routes record exact independent decisions with zero provider/credential/quota/executor calls; self-review, stale digest, role loss and expired decisions refuse.
- Actual request-service and durable-store journeys: requester-only execution, reviewer-executor mismatch, two competing claims, replay, expiry/revocation/target changes before claim and after await, current Agent policy removal, enrolled/unavailable coverage.
- Real fixed transport composition with simulated providers: final refusal makes no provider write; one dispatched lost response stays consumed/unknown and read-only recovery cannot issue another write.
- Existing history is byte-preserved; no blanket backfill or grandfathered approvals. Simulated identities/provider responses are labeled; no genuine human review is performed by the agent.
- Native DTO, current capability display, approved-waiting state, deliberate execution, uncertain recovery and restart tests; focused types/builds and independent code review. No unsupported live or whole-suite completion claim.

A separate specific activation approval, genuine exact human review and provider-action authorization remain necessary for live acceptance. This proposal grants none of them and does not complete the wider Governance catalog/enrollment or website work.
