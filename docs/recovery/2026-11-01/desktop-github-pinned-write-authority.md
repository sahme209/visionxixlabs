The actual branch, commit and pull-request routes previously used two-argument installation-token resolution, with a current paired-user/enrollment guard but no captured installation revision at final dispatch. They now resolve through their server-created guard: it captures the current active installation ID/provider ID/revision, mints only a repository-scoped token through the pinned resolver, rechecks after issuance, and repeats authority at the actual transport boundary. Missing, changed, revoked or suspended installations refuse. The request's bounded cancellation signal also applies to token resolution and authority reads.

Review caught an explicit stale-connection window in the first draft: later enrollment/principal awaits followed the installation read. A new regression reproduced it. The final guard therefore ends with one PostgreSQL statement observing the persisted session, accepted membership/capability, latest active installation and enrollment together. Only synchronous validation and cancellation checking follow that query. No provider request is made under database locks or inside a database transaction. This narrows the decision-to-dispatch window; it cannot promise atomicity between an independent provider and a local database.
