# Current settings source: three approved official pages consumed

Owner approved official documentation search and up to three public Vercel pages. One connector documentation search and exactly the following three page opens were used; later section lookups reused those same pages. No account, API, variable, credential or live provider was accessed. No additional page is authorized by this consumed grant.

1. [Project variable listing](https://vercel.com/docs/rest-api/projects/retrieve-the-environment-variables-of-a-project-by-id-or-name): GET /v10/projects/{idOrName}/env supports explicit team scope, branch/custom-environment filters and a deprecated decrypt parameter. The rendered contract exposes metadata alongside a required value field; decrypt=false is not evidence that a response cannot contain sensitive bytes. The inspected page does not specify a pagination cursor/completeness protocol. A safe reader must use fixed decrypt=false, bound and discard raw bodies, project a strict metadata allowlist and refuse unsupported/ambiguous shapes or scope. An absence assertion needs qualified completeness; lack of a pagination section alone does not prove it.
2. [Exact variable lookup](https://vercel.com/docs/rest-api/projects/retrieve-the-decrypted-value-of-an-environment-variable-of-a-project-by-id): this is explicitly the decrypted-value endpoint. It is unsuitable as a harmless exact-metadata fallback. Do not call it to resolve absence or use it in the intended metadata supplier. No secret-value access is authorized here.
3. [Config and Secret variables](https://vercel.com/docs/environment-variables/sensitive-environment-variables): Config remains readable by authorized members after saving; Secret is write-only. The current documented REST examples map Secret to type=sensitive plus visibility=secret, and readable Config to encrypted/plain plus visibility=config. Secret is now allowed in Development. The existing local transport sends encrypted/plain without an explicit visibility and therefore has NOT established native Secret behavior. Its unavailable qualification default must remain closed. Build-log redaction has documented limits; never market it as comprehensive secret protection.

## Consequences

- Do not enable the current write profile or call encryption alone write-only custody.
- Prepare an explicit deterministic native type/visibility mapping correction and exact response checks for owner design review; do not silently broaden the accepted manifest/provider boundary or renew historical receipts.
- Metadata source must not fetch the per-ID decrypted endpoint, return/hash values, follow guessed pagination or call an empty/partial response qualified absence. Real response shape/completeness, ownership/visibility, external-writer race behavior and actual credential/custody qualification remain open.
- Existing-setting updates remain held; no automatic deployment follows a setting change. This research resolves documented semantics, not actual platform acceptance.
