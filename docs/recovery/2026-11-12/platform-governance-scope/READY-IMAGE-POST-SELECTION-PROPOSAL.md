# Ready image selection for a separately reviewed post — proposed local completion

Status: proposal only; no implementation or new authority. This closes the important finding from the final three-family source review of56858a41. Existing approved image custody remains unchanged.

## Verified missing step
The image executor can confirm an exact original upload and AVAILABLE observation. The later post source accepts only already-associated draft.imageUrn. Actual create/edit forms and growth preparation have no media-selection input; current positive SQL fixtures inject that association directly. An uploaded image therefore cannot be selected through the prepared user workflow. That is a local functional gap, separate from deliberately unqualified real sources/defaults.

## Recommended approach: selection belongs to the new proposal
Add an OPTIONAL confirmed-upload action reference to the existing publish/schedule proposal selection. Do not write imageUrn into the draft, change content status, mutate an old review or add an attachment side effect. The exact requester chooses an existing upload; the server resolves immutable ready lineage for the selected current connected account/author and binds the chosen upload, image identity, byte digest and lineage into the new plan and rendered payload digest. A separately current distinct reviewer decides that new exact post/schedule plan. Its original requester executes once through existing admission/final-send controls.

For scheduling, the choice is recorded only in that exact schedule plan. A schedule is not a future publication approval; the later publication still requires its own exact selection/review. Existing native posting automation stays refused. Do not silently change the draft or carry this selection into an unrelated later plan.

An alternative direct draft attachment would introduce a new content mutation/CAS/reset policy, so it is not recommended for this correction. No raw image URL, arbitrary URN, caller lineage, credential or Boolean qualification is accepted as a selection.

## Exact boundaries
1. Preserve old text-only and existing-image plans as immutable history with their original digests. The new selection is optional. Older image references without compatible managed ready proof still refuse; no old plan is upgraded.
2. Resolve the selected upload through actual private SQL parent/child/grant/result/event proof, then verify current connection ID/author compatibility. Unknown, claimed, missing, legacy-without-readiness, different-account and different-image records refuse. No provider, decoder or key access is required merely to compile metadata.
3. A non-null existing draft.imageUrn must either match the chosen ready image or refuse; do not silently replace media. Bind original draft revision/status/image association AND chosen upload/lineage into source and payload digests. Source changes cannot preserve an old approval accidentally.
4. Original-reference lookup must compare the optional choice as well as current selection fields. Reusing an original reference with a different image refuses. Lost replies recover only the exact saved proposal, never renew or replace it.
5. Review preview, claim, final source reconstruction and native publication all resolve that same stored choice. The actual default publisher cannot accept a client-selected image override outside the privately admitted plan. The existing selected-effect comparison remains mandatory before credentials/send. Revocation/changed proof after claim prevents dispatch and retains consumed uncertainty.
6. **Additional artifact-access boundary requiring owner decision:** allow the current new-post requester and its genuine distinct reviewer to inspect the chosen original image bytes only THROUGH that exact proposed/approved post action and compatible confirmed lineage. Arbitrary artifact/upload IDs remain insufficient. This extends the earlier image-review rule, which names only the original upload action; do not implement this extension without approval. Reuse the qualified bounded decoder, scoped artifact key and current possession/source/role/deadline checks around all awaits. No preview after claim/expiry, no plaintext persistence, no change to the earlier upload's creator or reviews.
   Preview authority and the active deadline belong to the NEW proposed/approved post/schedule action: its current original requester may preview; before approval a current eligible distinct platform reviewer may preview for that exact decision; after approval require that saved current reviewer (or that action's original requester). Old creator/reviewer/session rights are not transferred or revived. The original upload is confirmed historical readiness provenance: expired original upload-review/grant windows and a revoked former upload reviewer do not automatically prohibit a later separately reviewed reuse. Do not call the original upload preview service as a shortcut; it deliberately requires that original action to be proposed/approved/unexpired. Decrypt only in the old immutable artifact context, while authorizing against the new action/current account/author and currently qualified exact artifact key/decoder. Missing key/format/source qualification still refuses; no re-encryption, renewal, metadata rewrite or old-token delivery is authorized.
7. Prepared UI adds a clearly optional confirmed-upload reference/choice and an exact action-bound image preview beside the existing post text/account/operations. No automatic association, review, publication, URL opening, new permission or qualification follows. Old terminal upload history is evidence, not execution authority.
