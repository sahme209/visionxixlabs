# ECS private issuance — proposed authority design

Status: bounded design preparation and subsequent local implementation/isolated tests approved November12. Three official AWS pages read; allowance consumed. No account evidence, IAM change, real credential, provisioning or deployment authorized.

## Verified public contracts

- [AssumeRoleWithWebIdentity](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRoleWithWebIdentity.html) needs an accepted identity token, not AWS signing credentials. Its session policy is optional; returned credentials can sign service requests. This supports the bypass concern when the runner possesses an accepted token; it does not establish the actual account trust configuration.
- [AssumeRole](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html) uses a role trust policy to select the permitted principal. Cross-account use also requires caller-side permission. The minimum requested session is900seconds; role chaining is capped at one hour. A service-specific session policy can narrow a session, but is not a trusted-origin or custody mechanism.
- [STS permission controls](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_temp_control-access_assumerole.html) distinguish role permissions from optional session restrictions. Without a supplied session policy, the role's permissions determine the session's access. Therefore, a policy generated by Axiom cannot stop another allowed caller from omitting it.

These are public API semantics, not verification of Axiom IAM roles, private runtime, fleet, account or provider behavior. No linked pages were opened beyond the three approved targets.

## Current source and rejected shortcut

`workloadRunner.ts` supplies its incoming raw token to `createOperationalStsIssuer`; `stsIssuer.ts` calls AssumeRoleWithWebIdentity. The final request/body guards and durable one-use claim protect that process's exchange, not every native exchange of the runner-held JWT. Keep this path without a qualified default; do not bless its supplier using environment approval alone.

Rejected: treating a GitHub job hold, secret audience, ExternalId, caller-selected session policy, wrapper check or a second GitHub token as proof only Axiom can mint. Axiom's admission is application state; AWS will not consult that state merely because a run is approved. No new custom identity provider, arbitrary customer role or broad server-wide AWS environment fallback is introduced.

## Proposed connected architecture

The GitHub job authenticates to Axiom only. It receives a nonsecret command result, never a native AWS credential, private proof or issuance handle. The Axiom-side execution custodian performs both credential acquisition and the exact native send within its qualified private runtime. No route exposes an assume-role proxy or arbitrary service operation.

Proposed initial deployment profile: a dedicated AWS-hosted execution custodian with its own qualified workload principal, separate from the GitHub runner and general website/AI processes. Its actual task/workload identity, image/code, resource access and credential supplier must be owner-provisioned and qualified before use. The present private Mac/native issuer is not automatically an AWS-hosted identity. This is a concrete candidate profile, NOT provisioning authority or an assertion that such a service exists. Hosting/cost/configuration choices remain owner decisions before actual setup.

The target execution role must trust only the qualified custodian principal for this flow, not the GitHub token or a runner-accessible equivalent principal. Its full native permissions and alternative trust/credential paths must be reviewed. Separate read-only observation access cannot imply write access. Other legitimate administrator/break-glass authority must be explicit and excluded from claims of universal interception; it cannot be silently counted as governed. No policy JSON or real ARN is guessed here.

### Required immutable binding

New execution proposals must bind a versioned issuer profile reference in addition to exact repository/run/attempt/workflow/source/environment and protection profile. The issuer profile fixes the custodian identity, destination account/role/service, reviewed image/runtime and native trust/permission evidence revision. Selection is private source-derived, not caller-supplied credentials, role overrides or an arbitrary URL. Review displays these nonsecret identities and changes invalidate eligibility. No old approval/hash/receipt is rewritten or upgraded; legacy records remain history and unqualified for this profile.

### Execution sequence

1. Existing genuine human proposal/review/requester delegation binds the exact already-created run. Native GitHub protection remains an additional hold, not the credential boundary.
2. Axiom verifies the fresh GitHub JWT for its configured request audience and exact signed run metadata. The token is never forwarded to STS. The request audience no longer needs to double as the AWS role's web-identity client ID; actual exact source verification remains required.
3. In the protected custodian, claim original delegation and physical service generation once. Preserve pending credential liability BEFORE acquiring a write-capable native session. Recheck current people/source/expiry/profile/issuer around every await and immediately before acquisition and send. A stale or unknown issuer cannot be replaced with the old web-identity path.
4. A private qualified supplier provides the custodian's actual bounded identity to a fixed regional AssumeRole exchange. No default SDK credential chain, environment token, HTTP caller identity or arbitrary command can supply it. Both source credential lifetime and resulting session liability must be recorded/qualified; the base identity may outlive one action and must be included in fleet enrollment/drain readiness. It cannot be erased merely because a request expired.
5. The resulting session stays lexical/private and can reach only the original one-use native command handle. Actual native request, destination and scope are checked after signing before dispatch. At most one acquisition and one native send; unknown issuance/commit/send is consumed, with no automatic replay or rollback.
6. Return only the immutable original command receipt. Explicit qualified readback can establish native stability separately. Normal recovery never exports credentials, resets history or manufactures exact-once guarantees beyond observed native evidence.

## Required qualification, not just mocked tests

- Raw GitHub JWT offered directly to AWS cannot obtain this profile's native write session; demonstrate under separately approved real trust qualification. Reject all alternate runner credentials, broad shared roles and legacy scripts/workflows for this covered path.
- Actual custodian identity/runtime/image matches the immutable profile; developer shell/AI/website processes cannot access its credential source, memory, native send or maintenance path. Prove current custody and process/fleet closure using the existing issuer completion gates; merely passing a profile object is insufficient.
- Scope the custodian's source identity and target role according to native AWS controls, including permission-changing and role-passing escalation paths; qualify current trust and every in-flight old credential before enabling enforcement. Trust/profile reads require separate permission.
- Source principal authentication and resulting role/account/session/expiry must match the accepted contract; no ambient fallback or second platform principal. Revocation/currentness failure before mint or send refuses.
- Demonstrate expired/revoked people, wrong environment/protection revision, wrong custodian/role/runtime, changed run attempt, concurrent claims, duplicate identity, cancelled acquisition, lost issuance/send/DB acknowledgement and earlier active liabilities. Each must refuse or preserve unknown truth without replay.
- Positive isolated journey: real persisted people/review/delegation/native generation, synthetic verified custodian supplier, actual installed AssumeRole/ECS serialization intercepted at native I/O, exactly one source-acquisition/mint/send and original receipt recovery. This proves local composition only. Real profile/provider/runtime qualification, same-artifact acceptance and owner enablement remain separate.

## Implementation boundary and remaining owner decisions

Design-only approval is consumed by this specification/research, not code. A later reviewed local implementation would replace the workload issuer coupling, introduce the explicit versioned immutable supplier/profile, preserve historical readers, exercise native installed-SDK signing/dispatch with synthetic resources, and retain unqualified defaults. It must reuse current ledger/claims/liabilities, not create a parallel approval system.

Actual AWS-hosted custodian provisioning, workload principal/role trust, costs, credentials, service installation, old-session drain, workflow/environment changes, deployment and live qualification require their own concrete owner decisions. Until the connected path and qualification are complete, P01 remains incomplete and activation refuses. No claim that a new service is installed, the credential bypass is fixed in production, or full Governance is complete.
