## 1. Deliverable and fixed assurance semantics

Extend the existing joined time core and ONE private Linux composition so every live time decision can explicitly consume either its original strict interval or an authenticated **AWS/Linux operational observation**. No new approval/attempt/reservation mechanism. The operational branch trusts the named AWS-managed source, exact OS and its one clock writer; it claims the host-reported time at a native observation, not a physical UTC enclosure. Preserve unavailable defaults and immutable old history.

Proposed closed private `ExecutionTimeObservation` union:

- `physical-utc-interval-v1`: original earliest/latest and strict supplier/profile provenance; preserve existing enclosure algorithm and premises. Existing structural interval ports do not become an operational supplier automatically.
- `aws-linux-operational-v1`: exact nonnegative signed64 `unixTimeNs`, native monotonic read bracket, exact accepted profile ID/digest, host/boot/producer generation and source/publication/disruption receipt reference. No earliest/latest or B/lambda field. Observation authentication is an original private native/bootstrap handle held in a WeakMap, not caller JSON or a boolean; the serializable summary is evidence only.

Keep `ExecutionTimeInterval`/`encloseTimePublication` unchanged as the strict mathematics. Add the observation union and closed private dispatching policy in `executionTime.ts`; explicitly migrate callers to the named union rather than casting an operational object into the old interval type. Private request wrappers forward the original branded observation/context without cloning away provenance. `assertExecutionWindow` returns the union, with only two existing direct scalar consumers requiring special treatment below.

Window predicates remain exact: strict branch uses `earliest>=notBefore` and `latest<expiresAt`; operational branch uses `unixTimeNs>=BigInt(notBefore)*1000000` and `<BigInt(expiresAt)*1000000`. Never round a host stamp down before expiry comparison, manufacture a zero-width interval, add a tolerance or extend a deadline. Conversion to display/SDK Date milliseconds is separately labelled and never substitutes for the exact predicate. Inverted/malformed windows refuse. These operational comparisons accept the host clock's possible error as a named risk, not mathematical safety.

### Routine publication versus original authorization identity

Bind the action/owner/dispatch checkpoint to the original accepted **policy revision, host boot, producer/source generation and fixed native resource/credential/request identity**, NOT forever to the publication counter sampled during prepare/approval. A routine synchronized daemon publication increments its counter within that same accepted generation; it is not a new policy acceptance, refreshed approval, replaced credential or renewed deadline. Every later original owner/phase and same-proof dispatch check performs a NEW bounded hold/capture/status/sample using the then-current publication. Preserve the original immutable narrowed action/people/JWT/credential deadlines and consumed attempt/proof; the newer observation only tests those same restrictions. No cached Ready boolean or reused sample.

Within ONE observation, CHECK-A/native sample/CHECK-B and original held file must refer to the same publication/transition tuple; a change during that bounded observation refuses that invocation, with no automatic recapture/retry. Across separate legitimate checks in the same workflow, increasing routine publication counters are allowed under the SAME accepted revision/source generation and actual currentness. Source/generation/policy replacement, counter regression, disruption or withdrawal is different: retire the original composition and refuse continuing its attempt; no reacceptance to repair old authority. Thus an action lasting several publisher cycles can continue through fresh observations without pinning its first counter, while never extending its original authorization.
