## Current decision

**Activation remains unavailable.** `lib/governance/intelligence/requestService.ts` deliberately installs no `verifyCoverage`, returns `coveredActions: []` from `readExecutionCoverage`, and throws from `activate`. `revisionStore.ts` independently requires trusted `verifyCoverage` inside the same organization-locked activation transaction. Neither this catalog nor a flag is that port.

The actual release merge/deployment callers now compose exact admission. Direct configuration refusal and native Git write-credential leases are additional real enforcement increments. They do not cover the alternate Airflow, workforce domain-action, notification, authority-management or platform provider families below. In particular, a record named "approval", an AI packet saying "approve", a transport import, and a unit-test coverage Boolean establish no authority.

Status terms:

- **Admission composed:** a real caller selects current baseline/action/provider checks; no production coverage registration is implied.
- **Refusal composed:** the actual caller/transport refuses enrolled or unknown authority, preserving its existing mutation gates. Ordinary preclaim refusal need not create a durable attempt; postclaim outcomes remain the durable store's responsibility.
- **Lease only:** credential lifetime metadata closes new-issuer uncertainty; it is not action admission or legacy-runtime qualification.
- **Gap:** the concrete call chain can reach a mutation without Governance admission/refusal. This is source evidence, not a newly executed exploit or provider acceptance.
- **Scope decision pending:** the mutation has existing authorization but has not been classified as governed tenant action, safety management, or separate platform operation. Do not silently exempt it.

## 2. Concrete alternate-caller findings and permission mutations

### U01 — model recommendation is not a human signature

`app/api/workforce/approver_engineer/run-domain/route.ts` authenticates with `requireContext`, generates/persists a packet using `runApproverEngineer`, then calls `dispatchApprovalActions`. Unlike manual/test integration routes, it does not call `integrationMutationContext` or an `actions:apply` gate. `actionExecutor.ts::shouldDispatchApproval` accepts `recommendedDecision === 'approve'` plus impact/reversibility strings and labels the result `high_stakes_signed`. Those are model-produced packet fields; no genuine independent human decision/audit/claim is checked there. `decisionAuthority` is displayed content, not cryptographic or current human authority.

This is a concrete source-level authority gap in addition to missing enrollment enforcement. It was reported before this document was written. No model call, provider action or exploit test was executed. Next safe work should retain packet generation but close automatic dispatch until trusted current action authority and a durable one-attempt decision exist. “Synthetic test issue” routes still create real provider objects and need the same refusal boundary.

### U02 — DAG trigger is a different mutation from downstream PR/deploy

Manual DAG POST and the scheduler's `triggerMode === 'schedule'` branch both reach `AirflowClient.triggerDag` directly. Guarding `executeAirflowAutomation` does not intercept either provider request. A saved connection/rule and deterministic DAG run ID are useful provenance/idempotency but do not supply Governance admission. A next refusal increment should bind the actual persisted tenant/connection/rule/manual actor and refuse before credential/provider work and at the real trigger callback, preserving unknown-run reconciliation instead of automatic re-trigger.

### M01 — role grants, invitations and acceptance

`app/api/desktop/workspace-members/route.ts::PATCH`, `app/api/team/role/route.ts` role-update branch, `app/api/team/invite/route.ts`, and `app/accept-invite/[token]/page.tsx` → `claimOrganizationSeat` can create/expand membership authority. Existing current role, tenant, signed invite, email, quorum/seat and browser-navigation controls must remain. None composes Governance enrollment/admission. Removal, demotion, sign-out and revocation are safety operations to classify separately; blocking all membership writes would be incorrect. Old unaccepted invite tokens are also outstanding authority artifacts, not proof of current activation readiness. An explicit control-plane scope/action and lifetime policy is pending.

### M02 — policy/autonomy/budget/branch and execution eligibility

`app/api/control/ai-governance/route.ts` changes provider policy, Agent `allowedTools`/enabled identity, autonomy charter and budget. `app/api/account/ai-policy/route.ts`, `app/api/autonomy/charter/route.ts`, `app/api/desktop/branch-policies/route.ts` and its actual create responder are alternate authority-affecting writes. Branch-policy creation retains production controls but is not F19. Existing owner/admin and origin/production checks are not Governance registration. These require a reviewed management boundary: baseline administration must stay possible, while weakening execution prerequisites cannot silently escape the activation model. No existing administrator permission is reinterpreted here as a new baseline grant.

### M03 — integration consent/configuration, reactivation and credential brokers

Connected-action Teams/Linear consent start/callback (`connectedActionConsentHttp.ts` / `connectedActionConsentRuntime.ts`), Outlook action consent (`outlookBrowserHttp.ts` / runtime), Slack OAuth start/callback, Jira write/reporter consent and activation, ServiceNow registration/consent/refresh, direct Airflow connection POST/automation configuration, workforce integration/Slack config and dashboard Slack config can add or expand operational capability. Their current admin, OAuth state/PKCE, exact registration/site/account/revision and grant-validation controls remain meaningful. None is generic execution admission. OAuth exchange is a credential broker, not automatically a customer resource mutation; subsequent token lifetime/control-plane classification still matters. Pause, disconnect, grant revocation and recovery must remain separately available. Native Git's ledger does not track these other credentials.

### M04 — other extension and management surfaces

API-key issuance, webhook endpoint configuration, cloud-account/connector activation and workload/pipeline policy changes appear in the source/candidate set. They need an exact control-plane versus governed-operation classification and caller trace before a closed manifest can be certified. This audit does not assert a tested bypass for every such endpoint. Registry declarations (`apiGateway.ts`, `actionRegistry.ts`) and client `fetch` syntax are not proof that a provider mutation is implemented or reachable.

## 5. Activation blockers retained after native leases

1. No trusted registered executor/action/refusal manifest is installed; `readExecutionCoverage` is empty and activation refuses.
2. F15/F16 and notification variants are actual alternate provider callers outside current admission/refusal. M01–M04 need explicit control-plane/safety scope decisions. The AI “signed packet” path needs current human authority, not just a policy label.
3. The native lease reader exists, but no production activation composition installs it as a complete coverage/legacy qualifier. `readNativeGitCredentialLeaseBlockers` validates history under the organization lock and always returns `legacyQualification: 'unavailable'`, including zero rows. Pending/unknown issuance must never age into safety; known issued leases block until actual recorded provider expiry by database clock. Cache reuse can create overlapping leases, which must all be counted.
4. Empty new history cannot prove absence of old untracked bearers, other write-token issuers, old process versions or mixed deployments. A concrete rollout/drain plus provider-backed revocation/expiry/installation-generation proof remains separately required. No guessed grace period, SQL backfill or checkbox can qualify it.
5. Canonical current scope supports repository/resource and production/staging/development/qa. Standalone mailbox/channel/team/native-window/organization management actions cannot be assigned an invented repository/environment. Unsupported mapping stays unavailable/refused until a reviewed binding exists.
6. Refusal callbacks without a coherent organization-lock/final freshness proof must not be presented as a completed enrollment transition barrier. Recheck every family against concurrent activation and postclaim cancellation/expiry; preserve irreversible attempt consumption and read-only recovery.
7. Native frontend source/review/activation/drift workflow, genuine independent humans, separately authorized live acceptance, mixed-runtime behavior and production deployment/enablement remain separate gates. This catalog changes none of them.
