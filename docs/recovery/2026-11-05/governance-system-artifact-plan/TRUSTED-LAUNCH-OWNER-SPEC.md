# Fixed trusted launch owner — specification candidate

Approved scope: call_zm8q4jC1CkVDX5AGd44zYxUp, design specification only. No code or operational authority. Generation/layout names below are proposed fixed installation constants, not created paths.

## 1. Actors and effects

Root owner: one native, non-JIT, no-runtime-exception executable, AxiomSyntheticLaunchOwner, under the fixed root-owned synthetic app Contents/Helpers. It holds no customer/provider/bootstrap secret. Its only privileged effects are creation of its own root-only launch journal, one fixed child launch with irreversible privilege drop, and cleanup of that owned child. No command/argument/path/UID/environment selector, arbitrary file service, signing operation or provider transport. Dedicated non-login custodian remains non-root and retains the existing private-consumer architecture. Trusted admin/root may install/arm a NEW generation; they are outside the attacker model.

## 2. Advertised topology and installation

Propose one root-owned System LaunchDaemon plist with fixed Label/MachServices name com.visionxixlabs.axiom.synthetic.launch-owner.<generation>, absolute root-owned program, no caller arguments, KeepAlive=false, no restart policy and no customer environment. Launchd registration/boot-trigger behavior, domain visibility and no automatic fresh-generation restart MUST be qualified before use. The broker client explicitly selects XPC_CONNECTION_MACH_SERVICE_PRIVILEGED, which the installed public header documents as the privileged bootstrap; a user-domain shadow is not an acceptable owner. Root owner creates the advertised listener with the ordinary listener flag. Fixed generation/signer requirements are compiled constants, never environment input.

The plist/application/journal parent are root-owned, non-symlink and not writable by group/other. Launch journal is distinct from bootstrap-transaction.v1 and issuer-startup-claim.json, fixed filename launch-owner.v1, root0600, one regular link. No live owner activation under existing installer authority. The dedicated UID/GID and exact signed owner/broker requirements must be bound by a later installation packet; absent values refuse preparation instead of inventing identities.

## 3. Persistent state and attempt definition

Exclusive O_CREAT|O_EXCL|O_NOFOLLOW creation in the protected root directory reserves the generation; any existing entry, including empty/truncated/unknown, refuses. No later process reopens an existing journal for launch, and no recovery path removes it. Fixed records identify generation, monotonic sequence and one phase: reserved, launch-intent, broker-created, broker-exited or unknown. No record or read-only observer grants launch authority. Partial writes, collisions, fsync/full-barrier/close uncertainty and malformed records terminate with no retry. A crash need not append unknown: any existing prefix already refuses a later launch.

Before spawning, both file contents/metadata and directory entry publication require qualified persistence, including the documented F_FULLFSYNC barrier on supported storage; no fsync-only fallback. Directory synchronization/full-barrier behavior is a mandatory platform qualification gate, not assumed from the file API. Spawn occurs only after the successful durable reservation+intent. Root-only access removes the same-UID deletion/reset route without granting the custodian append or write access.

No universal hardware guarantee is promised. Storage that ignores flushes, unsupported directory durability or unknown generation history cannot qualify. No child/resource effect is possible before the durable-intent branch in this source design. Operator handling of ambiguous storage/installation history MUST deny reuse of that generation; it cannot be inferred pristine merely because an entry is absent. Actual supported storage and administrative arming/history are acceptance requirements, not supplied by this document.

## 4. Fixed child and privilege drop

Proposed implementation shape is a minimal intentionally single-threaded pre-fork C launch path, before dispatch/XPC/Security initialization can create threads; actual single-threaded/runtime behavior needs qualification. It prepares no secret or writable resource descriptor. Fork once only after durable intent. In the child, close unrelated descriptors, setgroups(0,NULL), setgid(fixedGid), then setuid(fixedUid); every return and resulting real/effective IDs/groups must match, otherwise _exit without broker exec. Installed setuid(2) documents real/effective/saved-ID changes for the privileged caller; mere seteuid or POSIX_SPAWN_RESETIDS is not the selected mechanism. Exec only the fixed immutable broker with argc1 and the fixed clean environment. No shell or root broker. Fork failure remains consumed; no alternative spawn path.

The parent tracks the actual unreaped direct child, does not adopt a PID from IPC, and never creates a second child. Failed/late setup kills/reaps only that child and records unknown if cleanup cannot be established. Blocking kernel work is not a preemptible deadline guarantee. If the required single-threaded fork safety cannot be established, this shape is rejected for a separately reviewed supported mechanism; no silent multithreaded fork workaround.

## 5. Owner-to-broker authentication

Reuse the existing actual received-XPC-message code requirement checks and owned-child/native SELF pattern, as a NEW fixed protocol family. Both ends pin release requirements before activation and dynamically validate actual received messages. No same-team wildcard, UID/PID/path/JSON/receipt alone. Owner accepts only exact begin/ack/live messages from the expected broker requirement, never launch commands. Before replying, it confirms its direct child is still unreaped/alive. Broker verifies actual owner code and privileged-bootstrap service, checks native getpid()==the owner's intended direct child, and answers a fresh private challenge on that connection. Sequence/deadline/one-use challenges and exact generation are native state. Foreign same-signed broker may cause denial, never adoption or a replacement slot. Actual relay/SELF/race behavior is required evidence, not inferred from source similarity. The original approved xpc-controlled-origin/contract.md relies on native SELF in exact trusted code plus per-message signature and the owner-held child slot; it explicitly does not defend against arbitrary malicious native code already in that trusted process. This design cannot silently claim a stronger kernel-derived sender-to-child join. A public supported per-message process-instance join is not specified here. Until either that join is established OR the original trusted-source-flow/SELF boundary is independently confirmed sufficient and actually qualified for this added owner layer, authentication remains UNRESOLVED and no positive owner grant may be implemented. Code identity and the existence of some live child alone are never sufficient.

The journal and live protocol are distinct state machines. Journal records: reserved(1)→launch-intent(2)→broker-created(3)→broker-exited(4), with unknown(5) terminal from any incomplete phase; no success after unknown and no parser-based launch/resume. Live protocol: reserved→child-created→authenticated-once→revoked/ended. Journal phase3 must precede accepting authentication; live authenticated-once does not reopen/update launch eligibility. Revocation requires immediate live denial, optionally a terminal unknown journal record if persistence is still possible; missing terminal record remains existing/consumed. Journal phase4 requires actual reaping, not an IPC exit claim.

Owner live protocol transitions reserved→child-created→authenticated-once→revoked/ended. Never return to reserved; no reconnection/reinitialization. A successful owner exchange is only launch origin, not Governance authority. Broker main must complete that current owner binding BEFORE axiom_private_supplier_startup or ANY resource query; current source calls supplier startup earlier and therefore requires an explicit reviewed integration change. The broker's existing Node protocol remains separate and unchanged in meaning.

## 6. Liveness, action ordering and termination

Every broker resource read, native initialization and existing claim/credential/final-send path must synchronously establish current authenticated owner/child liveness through the real chain. Cached ready state, polling snapshots and journals cannot substitute. Exact implementation must specify bounded waiting/threading and async-to-sync seams, and qualify loss during every await. Owner disconnect/exit, broker exit/re-exec, changed release/generation, stale challenge or late response permanently revokes; no reconnect. Original final-send and operation/approval/current-access requirements remain.

No design can prevent a process from dying immediately after a liveness observation. Acceptance requires current checks at the original dispatch seams and preserves uncertainty after possible dispatch; it does not claim atomicity with arbitrary external provider effects. Owner loss observed before dispatch prevents the effect; loss after intent preserves consumed history and forbids replay. This is the existing action rule, not a new permission.

On termination the owner stops accepting messages and revokes before cleanup. The broker must cancel its jobs, revoke private Node state, kill/reap its owned suspended/running child and report actual cleanup; root owner then reaps its actual broker child. Forced owner/broker death may leave cleanup uncertain; qualification must prove containment or deny future enrollment/drain, never assert that killing one PID proves descendant quiescence. No generic process-group kill or unverified PID cleanup is authorized by this specification.

## 7. Mandatory acceptance and next implementation scope

Source/test preparation, if separately approved: exact finite journal/protocol transitions, injected syscall adapters with no privileged default entry, strict pure/parser tests and explicit unavailable integration. Ordinary tests cannot qualify root ownership, storage, privilege drop, Mach domains or actual sender/child behavior. Do not implement a positive operational gate or unreviewed generic launcher.

Actual qualification later requires: root/nonroot isolation and alias/reset attempts; durable journal before one launch; every write/full-sync/close/kill/crash/boot failure schedule; fixed privilege-drop/no retained handles; false owner/user-domain shadow/foreign same-signed broker/relay/re-exec/second connection; loss at resource/claim/credential/final-send seams; actual Node/private compiled consumer; cleanup/unknown drain and old runtime/fleet exclusion. Actual platform setup/service/signing/root experiments need frozen per-run approval. No real secret/customer/provider resource enters the initial synthetic qualification.

All21master parents remain open. Node arithmetic, metadata, signatures, pure tests or this specification alone cannot enable issuer identity, custody, enrollment, Governance or deployment.
