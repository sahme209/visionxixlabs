## Confirmed source seams

1. `privateDesktopToken.ts` mints and verifies `axm.desk.<sessionId>.<HMAC>` using its privately copied key. It splits at the last dot; the transport must preserve custom IDs. The token alone proves neither current role nor active membership.
2. `privateDesktopSession.ts:55–95` and `privateDesktopSessionStore.prisma.ts` already support real isolated rows/current expiry/revocation. `desktopSessionResolverCore.ts:105 onward` then resolves current membership, capability and commercial access. Reuse these actual factories; do not create a fixture authentication bypass.
3. `fixture-seed.sql` currently creates synthetic requester/reviewer users, memberships and session rows only. `runFixedSyntheticFixtureProducer` returns fixed phase bytes over stdout. It issues/delivers no scoped requester/reviewer credentials or saved merge/policy/review scenario. Production paired tokens cannot authenticate against the fresh isolated signing key.
4. `privateReleaseMergeRequestData.ts` exposes only six fixed execution/history operations. There is no plan/policy/review writer operation or caller actor/org field. `privateReleaseMergeComposition.ts` owns the real private repository/session/commercial/App-auth/drain/Governance graph; do not bypass it with a second executor.
5. `privateReleaseMergeBootstrap.ts:13,35` captures `fetch.bind(globalThis)` into that graph. Current App-auth/source/final transport use fixed GitHub URLs. No admitted simulator selection exists in the current installed composition; a fake source row by itself cannot make a safe positive remote workflow.
6. Source search of `desktop/src` and `desktop/src-tauri` found no `axiom.issuer-request/1` client. The broker listener is implemented, but current desktop HTTP behavior is not an existing native-channel fixture driver. The actual signed sender and request framing must be supplied deliberately.

These are unimplemented source/procedure prerequisites, not runtime-ready switches. Existing local source completion remains valid at its recorded scope.

## Least-authority joined design requirements

- **Keep fixture and customer authority distinct.** Use fixed `qualification_requester` / `qualification_reviewer` labels and fresh fixture-only sessions. Never label a seeded/test decision “Fatima approved,” reuse a real account token or infer a human identity from a fixture user ID. Seeded or driver-produced scenario authority remains **simulated authority** for the control matrix; genuine independent customer/native review acceptance remains a separate retained requirement.
- **Issue through existing private mechanics.** The fixed trusted producer/scenario composition can use the actual private session store/service and token codec with its already held fixture material. It may issue only the selected short-lived sessions for this isolated workspace. A separate reviewed bounded private handoff may deliver those opaque session tokens to the exact owned/authenticated fixture client. It must not export the session-signing/vault key, datasource/password, App key, provider token or a generic mint/session-creation API. Current phase-only stdout cannot silently become that channel.
- **Bound the recipient and lifetime.** Specify the exact fixed signed client/code requirement, actual owned instance and private descriptor handoff; no caller PID, request-selected code requirement, same-team wildcard or token file/log/env/argv. Reuse current native sender authentication, one-slot request IDs, cancellation/deadlines and one-attempt semantics. A new client must match the selected fixture-only peer policy; do not weaken the production desktop requirement merely to admit a CLI.
- **Construct one fixed scenario using actual domain contracts.** Reuse existing plan parsers/hash constructors and private repository/store APIs for saved plan/source binding, action review, baseline/policy and operation state. Bind tenant, requester/reviewer sessions, expected head/base and versions. Scenario setup belongs to the exact trusted isolated administrator/writer, not six-operation request fields, arbitrary SQL, public registration or a caller-supplied `approved`/`current` boolean. The fixture seeder's output is labeled synthetic; no consumed/UNKNOWN row may be reset, adopted or replayed.
- **Select simulated remote behavior at trusted composition time.** A reviewed fixed fixture transport/source leaf must be composed lexically with the same actual private consumer/coordinator/auth/store/final-send code. It is immutable in the named fixture artifact, not an environment flag, public fetch setter, request URL, TLS/proxy workaround, global monkeypatch or replacement miniature executor. It must refuse every unmatched URL/method/body/case and perform no network. Any synthetic App-signing material needed by actual auth code stays encrypted/private in the isolated authority tier. Do not use real provider credentials to make this test pass.
- **Do not change native identity into a test approval.** The real canonical main/cache/readonly/native-owned instance still establishes current identity and asserts freshness. The driver must reach that same compiled consumer via real native ingress. It supplies no identity digest, positive reader, test getter, copied readiness descriptor or module hook. Mocks may qualify local source units; they cannot stand in for the actual native/compiled instance in the operational matrix.
- **Keep supported controls honest.** If a fixed fixture setup seeds policy/review rows, report simulated policy/review authority. A genuine human review journey needs its own existing or explicitly approved private review writer/UI; do not claim the six-operation execution channel implements one. Do not silently add a seventh operation or broaden a history reader into a writer.

## Required connected acceptance cases

| --- | --- |

Do not invent path exclusivity or blanket denial of a genuine signed-app copy where the existing policy does not establish it. No PID/requirement substitution or reconnect execution. |
| Fixed simulator match | Actual private transport receives only the selected exact fixture request, records a bounded simulated effect, and never reaches network. Unmatched host/path/method/body, changed credential scope or source response refuses. |
| Native loss/cancel/expiry before claim, during credential admission or before final send | Original durable state is preserved with zero forbidden subsequent effect; neither a private token nor a simulator response rearms the instance. |

| Import/custom-main/worker/cache/native replacement | Same-consumer identity refuses; the fixture API cannot create a positive reader or evaluate a substitute consumer. |
| Close and teardown | Stop accepting new requests, drain/record unsettled work, revoke fixture sessions as scoped and wipe mutable token staging; unknown cleanup is reported without deleting/reusing uncertain resources. |

Local tests should first join the actual token codec, private row/session resolver, real scenario parsers/stores, fixed data adapter and lexical simulator with isolated/mocked boundaries explicitly labeled. The later exact operational packet then replaces mocked native/OS facts with actual installed custody and same-consumer observations, preserving the chosen simulated remote/authority classification. Neither phase closes production writer withdrawal, fleet/enrollment or full A2/A9.

## Corrected enrolled-coverage audit and lifecycle — November 5

The concrete assembler [driver proposal](governance-fixture-driver-design.md) correctly retains the actual default guard. `releaseProviderMergeCoordinatorCore.ts:121–130` constructs `createGovernanceMergeRequestAdmissionV2` and `createGovernedProviderMergeExecutor` when current enrollment exists; an omitted `ports.governance` is **not** a missing executor. A seeded active pointer therefore cannot make the real guard pass.

The minimum new composition is a **private, trusted registration** for the actual mounted direct-merge graph, shared by current scope coverage reads and baseline activation. Bind the same private repo/auth/coordinator/claim/credential/final-transport instances and native-derived current canonical instance; derive repository/environment scope from the stored reviewed intake/plan. Do not replace the guard, accept arbitrary action arrays, use a test `verifyCoverage => true`, or publish a caller registration/ready setter. Global/unregistered composition must retain its present empty/refusing behavior. All other action families and private AWS evidence remain unsupported, not silently covered.

Activation must use the existing baseline service/store: warm fresh source proof outside locks, propose/review exact revision with actual current participants, verify registered coverage under the existing organization transaction, then create the pointer/history atomically. Execution must read that same real service registration through the already mounted V2 guard and the real persisted execution-policy authority. Missing/changed instance, scope, source, policy/reviewer/session or unsupported action must refuse both activation and later claim/final write. Baseline proposal/review is not enrollment; an execution-policy record is not baseline coverage.

Current artifact identity is distinct from accepted external qualification. `index.cjs:43–60` always checks native origin and additionally checks request currentness **when** `activeRequest` exists; a genuine canonical instance can be current outside a business request. There is no need for a test identity getter or a circular “successful enrolled test grants identity.” Coverage registration still needs concrete current source/instance and scoped authority facts; a stored qualification digest or static manifest alone supplies none.

The isolated fixture may demonstrate a closed, explicitly synthetic scope through its actual private interface and source-owned simulator while production fleet/resource withdrawal remains unavailable. ## Closing review of the refined concrete candidate

The refined proposal now explicitly separates F0 base identity/session/**billing** initialization and token/pure schedule preparation from F1 canonical writer/coverage setup; F3 retains the current native job/cancellation until its real handler settles and the fixed continuation finishes. It also requires concurrent capped draining of phase stdout and the authorization pipe: a 64 KiB credential frame cannot rely on OS pipe capacity or be read only after child exit. Publication waits for phase2, normal owned reap, both exact EOFs and successful item/locator provisioning; every partial/unknown path releases zero credentials. These corrections resolve the earlier concrete lifecycle/auth/bootstrap/deadlock concerns without changing the original identity mechanism.

One implementation-order clarification remains essential in the coverage interface: F1 registration/activation must bind actual **mounted factory closures and their private captures**, because per-attempt credential/final-transport instances are constructed later inside `Coordinator.run`. Each request then verifies its actual created instances against that same private registration before claim/exposure/final send. Do not require future per-attempt objects at activation, mint credentials to establish coverage, or replace the registration with a caller DTO. This is source-order alignment of the selected interface, not another security mechanism.

No additional architecture change is recommended. The exact non-root controller launch/descriptor ownership, actual fixture account/key/SQL/native operation and all qualification facts remain later explicitly authorized gates. This review approves no implementation or operation; the root agent coordinates the user's validation-first decision after the last interface clarification is recorded.
