## Fixed helper identity and input protocol

Select a fixed compiled module `Contents/Resources/qualification/fixture-producer.cjs` inside the protected administrative application closure. It runs once with the same exact protected minimal-JIT Node candidate, not `node` from PATH or a repo symlink. Maintenance verifies actual pinned input files/ancestors and their immutable byte/code bindings before owned fork/exec; Node accepts only that fixed module, clean allowlisted nonsecret environment, fixed working directory and no loader flags. No generic script argument, supplied executable path or caller-selected SQL is allowed. This module and the real generated Prisma/engine dependency closure require a new reviewed artifact binding; they are not in the currently sealed packet.

Only the exact admitted root maintenance parent may create the producer; it cannot derive administrative identity from a requested UID, arbitrary launcher or packet boolean. The fixture-server and issuer UID/GID allocations remain explicit operator decisions. The root maintenance parent creates anonymous input/output pipes and launches this one owned root helper without shell or public endpoint. Child stdin receives exactly one binary frame: fixed version+generation binding; database password32-byte source/64hex encoding; vault32; session32. Fixed sizes eliminate JSON objects/callbacks/variable route fields. The child's stdout is reserved for one bounded binary status record; stderr contains fixed numeric failure phases only. Reject inherited unrelated descriptors, trailing frames, EOF/timeout/unknown exit and any target mismatch. Actual descriptor/process ownership follows the existing trusted-owner model; a copied pipe frame is not installation readiness or caller authority.

The helper derives the admin URI internally (`axiom_fixture_admin`, same fixed database/socket, no password); peer authentication binds actual root. Root admin access is intentional trusted maintenance, not available to the ordinary application tier. The helper creates a private Prisma instance with this URI, performs reviewed fixed SQL, loads only synthetic rows, verifies schema/role/grants and runtime password access using a second explicit instance, then closes both. PostgreSQL `CREATE DATABASE` cannot run inside a transaction: establish the fresh database through a separate fixed admin connection to `postgres`; record that phase independently. This initial root-peer connection is admitted only by the explicit bootstrap HBA rule above, after `initdb` created the fixed admin role. The final-HBA transition is another separately recorded phase before Keychain Adds. Existing source's `createPrivateAuthorityDatabase` accepts that fixed URI as well. Do not imply database/role/item creation is one atomic transaction.

For password DDL, identifiers are fixed literals and the only interpolated value is length-checked lowercase hex generated by maintenance; no public SQL text is accepted. Ordinary fixture inserts use bound parameters. Review and disable password-bearing query diagnostics before this path is permitted. No test helper imports global app DB/session/env configuration.

## Logs, schema and administrative staging

Choose cluster settings `logging_collector=off`, `log_statement='none'`, `log_min_duration_statement=-1`, `log_duration=off`, `log_min_error_statement='panic'`, `log_parameter_max_length=0`, `log_parameter_max_length_on_error=0`; client Prisma query/error logging must not print SQL/parameters/DSNs. Operational preflight verifies these effective settings using the fixed admin connection before password DDL. Capture only fixed output phases, not database exceptions. If PostgreSQL17 rejects a setting or another logging path is present, refuse; do not silently omit it. These settings need actual supported-binary qualification, not a documentation-based secrecy claim.

The schema SQL and HBA/config/ident files are nonsecret fixed reviewed artifacts. PostgreSQL data persists synthetic rows and password verifiers as expected; the prohibition is on plaintext bootstrap/key/password copies in general files, not on the database itself. A database server necessarily retains internal memory/state. No perfect zeroization or database-at-rest encryption claim is made by this fixture.
