# Private synthetic material origin — connected design

**Design only; no implementation or operational permission.** This replaces the public placeholder inputs, not the original custody, same-consumer, coverage or production-cutover requirements. Read alongside the current master/board and [next qualification audit](../governance-next-qualification-audit.md). No runtime, provider, database, Security/Keychain or installation operation was performed for this document.

## Source baseline and missing seam

- `native/synthetic_resource_provisioner.m:61–79` currently supplies the invalid `postgresql://axiom-synthetic.invalid/qualification` locator and public constant key arrays. Its private `AxSyntheticInstallerMaterial` and `valid_material` checks are useful shapes, not private origin. `ax_synthetic_native_provision()` takes no caller argument; preserve that property.
- `native/synthetic_resource_maintenance_main.c:35–43` admits only the fixed protected installed maintenance executable as root and prints fixed numeric statuses. Its present `AX_OWNER_OPERATIONAL` gate conflates runtime unavailability with permission to run maintenance. A reviewed source change must separate these meanings; a root receipt must never become issuer authority.
- `native/origin_private_resource_supplier.m:22–34,107–122` remains unavailable and checks current owner context around exact item-reference reads. The supplier and owner must receive only their existing fixed generation/recipient contract, not a caller-selected datasource or credential callback.
- The installed-resource preparation and synthetic-custodian policy specifications already select three serial new-item Adds, exact persistent references, collision refusal and no automatic rollback/reuse. Those contracts remain. Historical rejected simple-ACL recipes do not establish effective policy; subsequent prepared application-only construction still needs actual installed enforcement qualification.

Native paths above are relative to `packages/verified-issuer-runtime/`. Existing isolated PostgreSQL runners demonstrate bounded `initdb`/`pg_ctl` fixtures with private Unix sockets, but their trust authentication is unsuitable as custody proof: another allowed local principal must not obtain the business database merely by choosing a username.

## Recommended bounded mechanism

Use one **fixed, protected, administrative maintenance composition** owning both isolated-fixture preparation and the current three-item provision transaction. Do not add a general secret-entry form, public IPC endpoint, environment fallback, secret file or arbitrary installer parameter. This requires new reviewed source and a later exact operational packet; it is not implemented today.

1. A separately authorized operator allocates one fresh fixed synthetic installation generation, dedicated runtime principal and isolated PostgreSQL fixture. The approved packet names the exact database binaries, protected fixture helper and immutable application/recipient artifacts, database/schema, socket/port and permitted cleanup. The fixture may contain only synthetic roles, sessions, memberships, plans, reviews and policies. It must not point at the production datasource or import existing keys.
2. The maintenance process generates fresh 32-byte vault and session keys and a fresh database password using the existing native `arc4random_buf` facility already used by the broker's challenges. Encode the password as fixed-length hex, avoiding SQL/URI delimiter ambiguity. The session key is 32 bytes, within the existing 32–4096 supplier bound. Values live only in owned mutable buffers; no source constants, secret digests in public receipts, stdout/stderr values or secret argv/environment.
3. The maintenance process creates anonymous pipes before launching **one fixed owned fixture helper**, closes unrelated descriptors and executes the pinned protected Node plus fixed compiled fixture module without a shell. The helper is an administrative trusted writer, not a customer/runtime supplier. It receives only a versioned bounded binary frame on its inherited private input, including the newly generated database password, vault/session keys needed to encode the approved synthetic fixture rows, and fixed nonsecret fixture coordinate binding. The helper is inside the same trusted administrative material boundary; no general runtime caller receives this frame. It cannot select a target URL, process, generation or executable. Its administrative connection uses only the packet's isolated local fixture, not current app environment/global Prisma resources.
4. The helper uses the existing explicit-instance Prisma database factory for that fixture to create a fixed non-superuser runtime role/database authority, load the reviewed synthetic schema/records and set the generated password. PostgreSQL HBA must require password authentication for the runtime connection; fixture-admin access is limited to the trusted maintenance/fixture owner. No `trust` shortcut is accepted for runtime custody. The actual installed Prisma engine/Unix-socket DSN compatibility must be tested; select one exact compatible local coordinate in the packet rather than claiming any socket form works.
5. Administrative SQL and provider/client error logging must not persist the generated password: fixed generated hex and fixed identifiers avoid arbitrary SQL input, but PostgreSQL statement/error/parameter logging and Prisma logging must also be explicitly configured and qualified. The helper returns only a bounded fixed success/failure record over its private return pipe after real SQL verification. An uncertain response is not proof that role creation failed. Do not automatically rerun provisioning or delete roles on failure.
6. Only after confirmed fixture preparation does maintenance assemble the actual bounded PostgreSQL URI and its existing in-memory `AxSyntheticInstallerMaterial` (datasource ≤8192 UTF-8 bytes, vault exactly32, session32). Reuse the existing private transaction internally; never expose a public material-taking provisioner. Add the three items under the fixed generation/service/accounts and selected effective policy; publish only nonsecret persistent references after its existing journal/persistence checks. The runtime broker cannot invoke this maintenance path.
7. Close the helper's channels, reap only the actual owned child and wipe the native staging buffers on success/refusal. The helper must close its private Prisma resources. Node/V8/SQL client buffers and OS copies have no general zeroization guarantee; trusted helper lifetime, no dumps/logs and separately qualified resource access are part of the explicit administrative boundary. Do not claim perfect memory erasure.

This is a concrete proposed origin: fresh native randomness → owned private fixture helper/real isolated SQL → private maintenance material → three exact new items → fixed recipient supplier → existing one-use bootstrap pipe → actual lexical compiled graph. A fake constructor, fixture datasource string or returned readiness boolean cannot replace any arrow.

## Authority, generation and partial outcomes

Maintenance admission must be fixed protected executable/root identity plus an exact unconsumed operator-approved generation transaction; it is **not** runtime readiness. Persist only transaction identity/phase/outcome and nonsecret selectors. Owner startup separately verifies protected installation, selected principal, image/code bindings, effective item policy, original owner/broker epoch and actual owned recipient. A successful maintenance record neither arms a native instance nor authorizes a merge.

The generation, app/broker/maintenance paths, resource roles and recipient artifact bindings are compiled/packet-selected before secret generation and cannot change via input. An owner restart creates no inherited delivery capability; any new resource generation requires a new reviewed installation, not replacement of an active generation. Exact references remain selectors, not grants.

Fixture role creation, any item Add, missing locator, delayed OS result, helper exit or publish failure may leave partial state. Preserve each phase and the original unknown result. Do not infer absence, query/adopt existing matching items, SetAccess/update/delete, regenerate keys and overwrite, retry an Add or silently switch targets. Administrative recovery is a new reviewed action against that history. Failure before items exist can still leave a database role; record it without printing its password.

## Finite preparation and qualification gates

Local source tests can use fake randomness/process/SQL/Security ports to prove exact framing, output bounds, helper/target binding, serial transaction ordering, buffer wiping, collision/partial/unknown refusal and no general material API. They cannot prove actual SQL, inherited-descriptor custody or OS policy.

A later exact authorized fixture qualification must establish: real isolated schema/roles; runtime password accepted only for the intended database; unrelated principals denied; actual helper identity/ownership/channel exclusivity; noninteractive new-item transaction; exact effective-policy/outsider/copy denial; no secret logs/files; and original same-recipient one-use bootstrap followed by the real compiled private handler. No synthetic success creates executing identity or authorizes a real provider effect.

**Still unresolved, not guessed:** exact installed fixture helper packaging/code identity and administrative UID/SQL access; approved fixture socket/port and engine compatibility; effective PostgreSQL logging/authentication controls; actual Keychain effective-policy/owner/alternate-program semantics; noninteractive supplier access; original process/reap/cancellation qualification. These must be specified and observed before positive operation. They do not justify more static signing of the current closed path.

Production is a separate decision: select actual resource owners, migrate trusted DB writers, withdraw general-tier/shared Vercel keys and authority, drain old runtimes/leases/unknown work and verify fleet coverage. This synthetic mechanism grants no permission to read, migrate, rotate or reuse production credentials. Full A2/A9 remain open.
