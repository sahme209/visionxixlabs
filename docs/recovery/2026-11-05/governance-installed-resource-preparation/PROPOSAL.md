## Exact locator and write-history contracts for the proposed source unit

The nonsecret locator file is a strict version1 binary record, not permissive JSON or a serialized grant. All integers are unsigned big-endian; bytes are copied into owned bounded storage, with no pointer deserialization:

- Header32bytes: exact8-byte ASCII magic `AXLOC001`;16raw bytes for the exact fixed generation hex; count byte exactly3;7reserved zero bytes.
- Exactly three ordered entries: role byte1(datasource),2(vault),3(session);3reserved zero bytes;4-byte locator length; that many opaque locator bytes. Each length1–16384; no UTF-8/base64 reinterpretation.
- Check the outer file size at most65536 before reading; read at most65536+one nonaccepted overflow sentinel. A valid record is at most49208bytes. Require the exact expected generation, roles/order/count, all zeros and exact EOF. Reject unknown magic, wrong generation, duplicate/out-of-order roles, empty/oversized/truncated/overflowed lengths and trailing bytes. No permissive extensions or ignored fields. A valid parser result is selectors only, not authorization or item existence.

The trusted installer journal is a **separate** root-only fixed-record history, not a financial ledger or startup grant. Source preparation must implement this contract with mocked I/O; actual filesystem persistence still needs later qualification:

- New journal creation only, using a protected fixed generation directory and exclusive/nonfollowing creation, mode0600. Any existing journal refuses the generation, even if it appears complete. No resume, truncate, adoption, rollback or automatic recovery. Journal/refusal paths must never log material or opaque locators.
- Each record32bytes: exact magic `AXTXN001`(8); fixed generation(16); strictly increasing sequence(4); phase(1); reason code(1); two zero reserved bytes. Maximum10records/320bytes. Reject duplicate, truncated, invalid or illegal transitions on observation; no journal text can qualify startup.
- Phases are finite: generation-claimed; intent-add-datasource; confirmed-add-datasource; intent-add-vault; confirmed-add-vault; intent-add-session; confirmed-add-session; intent-publish-locators; locators-published; incomplete. These phases use the listed numeric order1–10; the first sequence is1 and each next record adds exactly1. Reason is0 on phases1–9. Terminal phase10 requires one fixed reason:1duplicate item,2returned Add refusal,3invalid locator,4journal/record I/O failure,5uncertain durability,6publication collision,7unknown possible effect,8unsupported platform operation. A crash need not leave a terminal record: any unfinished prefix is incomplete, not resumable. At most nine records on the success path. `incomplete` may terminate any prefix with a nonsecret finite reason, within the10record limit. No transition leaves incomplete or locators-published, and no confirmed phase skips its exact preceding intent.
- Before each of the three Add effects, write the corresponding full intent record and obtain the qualified file/directory durability acknowledgments. Only then invoke that Add once. After a valid returned locator, record the exact matching confirmed phase. A failed/uncertain journal write or sync prevents the next effect. If the Add might have occurred, missing confirmation remains incomplete/unknown; never infer absence or send it again.
- Only after all three confirmations, journal publish intent; write the bounded locator record to the fixed new staging name, complete its ownership/mode and file synchronization, then perform an exclusive no-replacement publication to the fixed final locator name and synchronize the protected directory before journal locators-published. Any collision/partial write/uncertain sync/publication leaves incomplete with no launch and no retry/automatic cleanup. Existing final records are never overwritten. The precise native exclusive-publication API must be verified against the existing SDK during implementation; unsupported semantics refuse rather than fall back to overwrite.
- Mocked successful fsync/publication tests prove the source orders acknowledgments correctly; they do not prove storage power-loss durability, root provenance, OS permission enforcement or atomicity of the three item writes. A future supported implementation must qualify directory/file synchronization and publication semantics before operation. `locators-published` does not enable a service or assert installed-policy enforcement.
