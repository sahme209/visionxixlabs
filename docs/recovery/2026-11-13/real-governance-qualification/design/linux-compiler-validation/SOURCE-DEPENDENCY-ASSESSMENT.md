The prepared execution request must explicitly bound this possibility or use a reviewed selected-graph acquisition method; do not promise that selecting `-p clock-bound --features daemon` limits a separate fetch to20/127packages.
2. Verify actual resolved package/features and target in the real locked Cargo phase. Root exclusions (`algorithm`, `env-filter`, `test-utils`, `test-side-by-side`) do not mean similarly named TRANSITIVE dependency features are absent. The JSON manifest feature walk is not a substitute for compiler evidence.
3. The inspected manifests have no exact Rust compiler pin. Edition2024/resolver3 implies a minimum capability but does not prove the installed runner compiler satisfies all locked dependency MSRVs. Existing-toolchain preflight followed by a single honest failure remains appropriate; no silent rustup upgrade/retry.
4. The absence of source-level Cargo configuration/overrides does not constrain inherited runner Cargo settings or build scripts. The eventual runner must use a fresh fixed Cargo home/config, refuse registry/git overrides and bind locked checksums. An offline Cargo flag prevents Cargo acquisition, not arbitrary network by executed build scripts/proc macros. If the grant excludes all nonregistry requests, the runner needs an actually reviewed enforcement mechanism; do not claim `--offline` alone provides process network isolation.
5. Upstream lock/manifests remain byte-identical. Any validation overlay introducing an external crate, changed lockfile or dependency override changes this acquisition inventory and must stop rather than re-pin automatically. This inventory supports a finite reviewed compilation request. It does not establish compiler success, dependency safety, Linux runtime behavior, native time correctness or Governance activation.
