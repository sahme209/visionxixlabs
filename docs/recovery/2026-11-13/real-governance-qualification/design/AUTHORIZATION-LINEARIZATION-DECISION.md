# Original authorization and dispatch — owner boundary decision required

## Why the previous completion condition cannot be supplied by another clock library
Actual ECS execution authorizes/commits the original transaction, then invokes the fixed bounded handler (`lib/governance/platform/operations/ecsSdkTransport.ts`). The process can pause after the last time check or commit and before physical network send. The same concern applies to source acquisition, STS and other native dispatch phases. `lib/governance/platform/executionTime.ts` explicitly leaves native validity through dispatch unproven.

Neither ClockBound, no additional await, a native helper, abort signal, timer nor invented safety margin proves a maximum future ordinary Linux scheduling pause. Strict receipt-before-original-expiry requires documented receiving-provider enforcement of that exact deadline for EACH phase. That complete provider contract is not established. More generic source searches or mock qualifier ports cannot close this gate.

## Recommended explicit boundary — not yet accepted
Authorize the exact action at the original durable, locked transaction's commit (the authorization linearization point). Every current human/source/role/policy/time/native check must pass INSIDE that original transaction; no weakening of precommit revocation. Seal the original exact action/generation/request digest and intersection of original deadlines into one private one-attempt dispatch proof, with a consumed record before effect. No new grant, claim, execution attempt or deadline is issued.

Allow the fixed private dispatcher to use that SAME proof for one final native DEADLINE/CURRENTNESS-ONLY check after commit, immediately before its original effect. This is NOT another approval or a fresh human/source authorization transaction. It must not renew expired approvals, restore an unknown result, expand source scope, acquire replacement credentials or extend any original lifetime. Expired, canceled or unqualified dispatch refuses without sending; ambiguous dispatch remains consumed/unknown, never replayed. A failed check cannot roll back an already committed consumption or invent a definitive provider refusal.

For providers that demonstrably enforce the exact original not-after, bind that native enforcement and prove it per phase. Otherwise document the remaining check-to-send scheduling race and characterize authorization as having taken effect at commit. Work already authorized and in flight remains a tracked liability; approval expiry/revocation after commit does not prove no effect occurred, automatically retry, or erase history. Never advertise guaranteed provider receipt before approval expiry for such a provider.

Credential expiration/custody, source renewal cutoff, independent human review, current target/transport/provenance, exact request binding, one use, audit, unknown/no-replay and native effect closure all remain separate required controls. Stopping a host or rechecking time is not credential closure. No universal phase coverage or complete Governance follows from this decision.

## Alternative
Keep strict physical-send/receipt expiry for every phase. Such phases must remain unavailable unless an exact provider-enforced original deadline or a separately proven execution gate is established. No ordinary-runtime or mocked substitute may be marked qualified. This may leave current providers unsupported; no promise of a near-term completion date.

Do not change existing transactions' authority checks or fabricate supported native suppliers. Public/internal descriptions must accurately distinguish authorization-at-commit from provider-enforced deadline.

No production flags, enablement, migrations, actual SQL/native clock/credential/provider actions, services/resources, installation, signing, deployment or spending. Existing approvals did NOT authorize changing the no-postcommit-clock/strict-dispatch boundary; this decision therefore requires explicit owner consent. ## Final independent decision review
File-only review by /root/handoff_design_review found no important security inconsistency and considers this ready for the owner boundary decision, not implementation/native acceptance. CURRENTNESS-ONLY means read-only verification of the ORIGINAL sealed runtime/source generation, credential, target/request bindings and cancellation; it may tighten/refuse but cannot substitute new facts or create fresh human/source authority. Before any conditional local implementation, the reviewed plan must enumerate EACH phase commit → proof consumption → final check → first native effect and crash/lost-ack outcomes. No additional production/native/resource permission follows.
