## Token arithmetic checkpoint (Task2 partial)

Added a pure TOKEN-unit liability kernel, deliberately separate from the existing cents ledgers. Current-window settled usage is charged; pending, dispatched, unknown and overrun liabilities survive window/revision changes. Malformed records, unsafe integers and arithmetic overflow refuse rather than understate exposure. Valid overreported usage retains its full liability. Zero is an explicit valid operator cap, never a default allowance.

## Token store and repository checkpoint (Task2 still partial)

The accounting service now reserves under a workspace lock, binds the request/actor/model/config/window, refuses duplicate request digests, durably consumes one dispatch claim and settles through a private one-use capability. Config changes, cap reductions and expiry before claim refuse without releasing the hold. Unknown settlement retains exposure; overrun records the full reported amount. This service is not yet mounted in the Agent and is not a model-limit qualification or final transport authorization.

A PostgreSQL adapter now uses the existing `DurableAgentWorkflow` and append-only event tables with the distinct `customer_hosted_token_call_v1` kind. These are terminal scheduler records, never queued jobs; no cents field, new schema, migration or default token allowance is used. Organization-scoped transaction advisory locks plus ReadCommitted make the next reader see the preceding holder's committed liabilities. All windows are read, with a 10,000-record fail-closed ceiling. Insert/update and content-free transition events share a transaction; storage failures are not retried. The adapter is implemented but actual PostgreSQL concurrency, rollback and database-clock acceptance are still required before Task2 completion. Process-clock versus database-clock expiry and final request-policy checks also remain integration review items.
