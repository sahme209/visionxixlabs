## Scope and prerequisites

The public `/download` route mounts `DownloadContent` with its default `cockpit=false`. This guide covers its installer/help/release links, mount-time metadata read, size helper, public manifest and download resolver, installer-availability fallback, and shared navigation/footer. Opening the website does not require an Axiom account. Network access is needed for live metadata and artifacts; JavaScript performs the client metadata read. Account help requires an account; installation, sign-in, entitlement, provider consent and action approval require separate supported flows and evidence. Downloading grants none of these. `cockpit=true` is an alternative component branch, not the public route: it changes heading/layout, hides navigation/footer and installation-help section, replaces the demo link with `/control/integrations`, and adds provider setup requirements. That text calls for the same account/workspace, installed-version capability review and supported administrator authorization; it explicitly says cloud enrollment is unavailable on that page and providers remain setup-required until configured and validated. This guide does not qualify its host route or those provider flows. [download-ui]

## Loading, readiness and failures

On mount one client fetch requests `/api/desktop/release-manifest`. Non-OK HTTP, JSON rejection, or missing `ok:true` / object `data` / object non-array `assets` sets **Release status unavailable**. Initial text is **Checking the latest release…**. There is no in-page retry button, polling, abort, or persisted state; unmount ignores late results with a cancelled flag. Reopen/reload to request metadata again. Validation is shallow; source does not establish hostile or malformed asset payload safety. Links stay usable through resolver fallbacks while loading or on failure. After a successful ready snapshot with an asset, links point directly to the artifact URL: clicking does not recheck runtime readiness through the resolver. The snapshot can become stale, and this is not a fresh per-click authorization or end-to-end availability check. [download-ui]

With a manifest but runtimeReady not exactly true, status uses runtimeMessage or the default temporary sign-in-unavailable copy. With readiness true it shows the manifest tag (desktop-v replaced by v), or a generic latest-installer label. Missing all assets can still produce that generic/latest-tag status when storage readiness succeeds; it is not evidence that a particular download exists. Each card independently needs its asset. Asset filename, size, signing report and friction may display even when readiness blocks direct download. Size is decimal MB/kB/bytes for a positive safe integer; otherwise **Size unavailable**. It is compressed download size, not installed footprint; a valid card size exposes exact bytes in a title attribute. [download-ui, size]

The public manifest route concurrently calls the release builder and storage readiness reader and wraps success in the standard API envelope. Its catch maps errors through existing API error helpers. The storage gate performs five selected-ID database reads for pairing challenges, sessions, billing plans, deployment requests and playbooks; failure logs server-side and returns a generic paused message. A successful read is storage accessibility only: it does not exercise account sign-in, installation, billing eligibility, schema migrations, provider access or a complete user journey. This authoring task did not execute any of those reads. [manifest-route, storage-gate]

## Resolver and availability fallback

The resolver recognizes exactly `mac-arm`, `mac-intel`, `windows`, `linux`. Invalid platform gives JSON400 with valid values, or browser302 to `/download`. JSON is selected by `format=json`, or Accept containing application/json without text/html. Valid requests concurrently read manifest/readiness. Runtime unavailable gives JSON503 or browser302 to `/download/preview?platform=…&reason=runtime`. Ready plus matching asset gives JSON available metadata or302 to its URL. Ready without asset gives JSON404 with note/default explanation, or302 to preview with platform only. The resolver has no local catch around these reads; unexpected exceptions follow framework error handling rather than a guaranteed friendly fallback. No guessed binary URL is manufactured. [download-resolver]

The preview consumes **reason**, not platform; it does not display architecture-specific findings. Runtime reason rechecks storage and redirects to `/download?status=recovered` if ready (the main page does not consume that status). Otherwise it explains paused storage; the non-runtime branch says no verified installer selected and promises no release date. **Return to downloads** navigates `/download`; **Contact support** opens `mailto:support@visionxixlabs.com`. Returning rechecks availability rather than resuming a captured download. Preview text describing checksum availability is not evidence of a checksum control on the main page. [fallback, download-ui]

## What the release metadata means

The builder uses configurable repository owner/name (defaults sahme209/axiom-releases), requests GitHub's releases list without Next fetch caching, and keeps a per-process60-second cache, including empty results. It filters published non-draft/non-prerelease tags starting desktop-, preferring the greatest valid publication timestamp rather than semantic version; if every timestamp is invalid, its reducer retains the first filtered release. It uses the returned list only: no pagination or artifact HEAD/download verification occurs. Network/non-OK/non-array/no-release paths return an empty manifest with note; shape failures deeper in processing can throw. Concurrent cache misses are not coalesced. [manifest-builder]

Filename classification maps Mac dmg/app.tar.gz architecture patterns (an otherwise unqualified dmg defaults ARM), Windows msi/exe, and Linux AppImage/deb/rpm. Per-platform preference is AppImage over deb over rpm and msi over exe; equal-ranked first asset survives. The source copies URL, size and optional GitHub digest without downloading bytes, and matches an optional `.asc` sidecar by installer name. Previous releases exclude current tag, require desktop-vX.Y.Z, valid publication time and at least one classifiable asset, sort descending and cap at10. This is metadata selection, not cryptographic verification. [manifest-builder]

Signing flags require exact machine-readable release-body lines `macos-artifact-signed: true`, `macos-artifact-notarized: true`, `windows-artifact-signed: true`, `linux-artifact-signed: true`; Mac flags are shared across its two architectures. The UI labels these as manifest reports; Mac distinguishes notarization unconfirmed, and false/missing signing says Signing not confirmed. Friction text can suggest Gatekeeper/SmartScreen bypasses or chmod; those strings are source behavior, **not this guide's recommendation to bypass organizational controls**. A `.asc`, digest, signed flag, or release prose does not independently prove authentic current bytes, certificate trust, notarization, clean-host acceptance or safe execution. [manifest-builder, download-ui]
