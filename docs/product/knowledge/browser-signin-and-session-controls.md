## Choose the intended browser identity

Use the configured canonical sign-in page. The server page compares the incoming host with the configured auth origin; a different host navigates to the configured page rather than selecting a destination from an untrusted Host value. The NextAuth endpoint separately refuses noncanonical-host requests instead of forwarding passwords/OAuth codes/state across hosts. Missing/invalid server configuration is unavailable service feedback, not an instruction to disclose a secret, run a command or change production settings. [signin-page, canonical-page, canonical-origin, nextauth-route]

The form derives a same-origin callback, default `/control`. It rejects protocol-relative URLs, backslashes/control/space characters, cross-origin destinations and URL credentials; a same-origin absolute URL may be normalized to its path/query/fragment. Canonical-host page navigation has its own narrower callback allowlist. Do not treat these as one universal redirect validator. Signing in and navigating to a callback do not approve a waiting desktop challenge or establish workspace entitlement. [signin-form, canonical-origin]

### Selected server boundary, not a complete auth audit

The inspected credentials provider normalizes email, rate-limits its lookup, requires stored password hash and verified-email state and compares the supplied password; identity-store failures refuse. Workspace bootstrap is a distinct best-effort side effect, not proof of workspace permissions. The configured browser session strategy is JWT with a 30-day maxAge; that setting is not a guarantee that any real session remains usable for 30 days or that desktop credentials share its lifetime. Provider/SSO callbacks have additional rules that this guide does not exhaustively qualify. [auth-credentials, auth-session]

`/auth/success` redirects either to `/control` or a connection-return page using recognized integration/status display parameters. It does not blindly forward provider OAuth codes/state, authorize an integration or certify a deployment. [auth-success, connection-return]

## Recover browser workspace access without changing identities silently

Unauthenticated Control entry redirects to sign-in with a bounded Control callback. A valid browser identity with an unverifiable selected workspace can instead see **Choose an available workspace**; this is different from invalid credentials. Current server context uses session identity plus accepted workspace membership; a saved workspace-selection cookie is not authority. [control-layout, current-context]

An unavailable current value is a disabled option. Choosing locally does not yet switch or alter roles. |

The browser account alias `/account` redirects to Settings, or to usage/billing on the recognized billing-return parameter. No billing actions are inventoried. [workspace-route, account-alias]

## Inspect and revoke a paired desktop session

Open Settings → Sessions (or its recognized section URL). Because Settings keeps its panels mounted, the session read can start before the Sessions tab is selected. The panel fetches `/api/desktop/session` once on mount using browser credentials and `cache:no-store`. Loading, unavailable, ready-empty and populated rows are distinct. It shows device label, platform, optional desktop version and last-seen date; invalid dates display Unknown. It deliberately does not render bearer tokens, device fingerprints or provider credentials. Its TypeScript row type includes expiry/status, but this UI is not an expiry countdown or revoked-device history. [settings-page, sessions-panel]

| Documentation ID / control | Exact effect | Limits and safe recovery |
| --- | --- | --- |
| `browser.session.device-review` — row **Revoke device** | Opens **Revoke device access?** for the chosen displayed session. | Only that row is disabled while its ID is revoking. Reviewing the dialog is not revocation, independent Governance approval or proof of device ownership beyond returned session metadata. |
| `browser.session.dialog-close` — **Close dialog** | Dismisses the pending confirmation. | Disabled while busy. Does not revoke a device or cancel a DELETE already sent. |
| `browser.session.dialog-cancel` — **Cancel** | Dismisses the pending choice and returns focus through the dialog's provided heading ref. | Disabled while busy; ordinary Escape closes only while not busy. Dialog body/backdrop has no click-to-close handler. |
| `browser.session.dialog-confirm` — **Revoke device** | Sends DELETE `/api/desktop/session?id=<encoded ID>` with browser credentials. A successful HTTP status removes that row locally; the dialog closes after either outcome. | The client does not validate a returned revocation receipt body. A thrown or non-OK response says revocation was not confirmed and may have completed; refresh/reopen the actual session list before trying again. No automatic resend, all-device revocation or local token deletion is performed. |

The selected GET lists only the browser user's active sessions in the current organization. DELETE independently checks current browser context and that the selected active session is owned by that user in that organization before calling the store's revoke method. The selected service writes revokedAt/reason; already missing/revoked rows can return without a new write. GET no longer listing a row is not proof of device-side credential deletion, all-server/worker quiescence or provider logout. The panel's “immediately prevents” copy is not qualified here as a universal timing guarantee for already-started work. [session-route, session-service, session-composition]

There is **no refresh button, polling, per-device expiry editor, new-token display, device-renaming control or revoke-all control** in this panel. The error's refresh guidance therefore means an actual remount/page reload, not merely switching tabs: `keepMounted` retains it. Its mounted-read cleanup ignores a late initial response, but no AbortController/request cancellation or comprehensive mutation-response ownership guard is established here. A returned OK is browser/UI acknowledgement, not a separately verified end-to-end native outcome. [sessions-panel, settings-page, tabs]

The shared confirmation initially focuses Cancel, locks document scrolling and contains boundary Tab navigation; busy state focuses the dialog and disables its action controls. On unmount it restores the body overflow and focuses the supplied sessions heading if connected, otherwise the previously focused element. These are source mechanisms, not real browser/IME/AT acceptance or a universal modal guarantee. [confirm-dialog]
