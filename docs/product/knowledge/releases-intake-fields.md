## Editing, required fields and saving

Every listed field updates the local intake draft through `update`, except workflow source ref, which uses `setWorkflowRef`. Editing alone does not create a service record, approve a change or dispatch a provider operation. Initial values come from `initialDraft` or `draftFromIntake`; an edited revision does not silently change the historical saved version.

Three layers remain distinct. **HTML required** below means the actual static `required` prop forwarded by the local helper. **Step presence** means only the `validateStep` nonempty-trimmed-string check, with the condition recorded in JSON; it does not establish URL syntax, chronology, owner identity or provider access. Final submit also checks workflow/batch issues, complete local steps, string-valued workflow-input JSON and valid deployment-window instants, then calls `createDeploymentRequest` or `reviseDeploymentRequest`. Server acceptance and other server constraints remain separate and are not exhaustively mapped here.

Continue checks the current step (including reported workflow/batch issues at Execution); final submit checks every local step and reports the failing section. Local validation and service refusal retain entered draft for correction. Successful create/revise invokes the parent completion callback. These saves create/revise the Axiom request, not a deployment, native ticket or independent approval. **Pending saves:** the enclosing native **Release intake fields** fieldset is disabled while submitting, pausing its nested fields and navigation. `update` and `submit` also synchronously refuse while the submission flight is held or the form is unmounted. The request uses its captured payload; the completion callback runs only while that original form remains mounted, so a departed form cannot close a replacement form through a late completion. Leaving does not cancel or establish failure of the save. Thrown-save recovery retains the captured mounted form and asks the user to check saved requests before another submission; this is not a server idempotency or automatic-retry guarantee. Each record separately captures the `fieldset` disabled expression as well as its visibility/required context.

## Interpretation and recovery boundaries

- **Readiness, PR approval, ownership and facts:** Development ready, Production ready, PR approval, no-PR-required, owner/contact fields and the entered “confirmed” fact/attribution are reported intake assertions. They do not create an independent provider decision, verify a person, waive downstream policy or grant execution access.
- **Dates:** Window start/end and expected follow-up date use datetime-local values. `localToIso` uses the machine’s date parsing and converts valid instants to UTC; the separately recorded display-zone label does not convert those inputs. This mapping does not assert date ordering checks. Submit explicitly refuses invalid deployment-window instants; do not infer the same explicit check for every other date.
- **Workflow source:** Blank local `workflowRef` falls back to `draft.sourceBranch`; matching observed workflow-source metadata is included only when it matches the current source context. Selecting a ref/path/environment does not establish current provider authority. Exact literal select options are preserved as source expressions in JSON.
- **Manual and rollback work:** Text describes planned instructions and responsibility. Serialized steps carry `completed:false` and `evidenceRequired:true`; recording them does not execute a command, validate an outcome or create evidence. Visible manual-step fields use raw `draft.manualInstruction` truthiness, whereas the step validator and serializer use trimmed nonempty text; the inventory preserves this distinction rather than merging the conditions.
- **Deferred validation and backup:** A reason, trigger, date, owner and monitoring plan record proposed follow-up, not approved deferral, scheduled automation or connected monitoring. Backup-required and cited evidence IDs do not perform a backup or verify the cited evidence.
- **Change creation and evidence:** Selecting an intended change-creation method does not activate that workflow or create a native change. A source evidence identifier is a citation, not a successful read or editorial acceptance. Preserve local error/context and reload the intended saved request before resolving an unconfirmed version or service refusal.
