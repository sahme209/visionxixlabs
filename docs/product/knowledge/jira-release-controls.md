## Open the mounted Jira workspace

In Releases, focus the intended release and open **Tickets → Jira**. `DeploymentRequestsView.tsx:651` mounts `ReleaseTicketWorkspace`; its Jira tab mounts both discovery and `JiraTicketLifecycle`, with `TicketGovernancePanel` below for the selected provider. Arrow Left/Right and Home/End change provider tabs. Hidden provider panels remain mounted; switching tabs is not cancellation. Release ID/version/status and desktop context changes key a new ticket session. Do not reuse stale IDs from another workspace.

For navigation, release intake, version history, saved deployment evidence and external request closure, see [Releases workspace controls](releases-workspace-controls.md). Recording an Axiom request closure is distinct from a Jira terminal transition. Common separate-review and uncertainty principles also appear in [ServiceNow evidence and closure controls](servicenow-evidence-and-closure-controls.md); ServiceNow process models, terminal policies, journal proofs, observed-note recovery and approval state do not transfer to Jira.

Discovery copy says publishing is unavailable because this explorer/preview cannot publish. The separate lifecycle has its own conditional provider execution controls. A successful preview is never a grant to create an issue. A discovery refresh outcome that is unconfirmed stops discovery: use **Reload connection status** only; do not retry discovery or token rotation. Other unavailable discovery messages preserve the release draft. The discovery client uses the captured paired desktop context, strict bounded response validation and no automatic retry; source inspection does not verify current administrator authority or permissions.

## Review, create and inspect lifecycle actions

Start with **Reload saved ticket actions**. The response controls `enabled`, `providerWritesAvailable`, `approvalAvailable`, `linkAvailable`, `closeAvailable` and per-action `canApprove/canExecute/canAmend/canCancel`; no visible card overrides them. Initial UI does not imply actions have loaded. Disabled drafting and unavailable execution have separate explanatory messages. **Review Jira ticket access**, when offered, checks a current owner/admin desktop identity with `connections:manage` before opening the authenticated browser ticket-access destination. Opening that destination grants no consent or approval by itself.

**Prepare ticket action draft / Hide ticket form** is available for draft/submitted releases when enabled. **Update saved ticket action** targets an amendable publish action. Closed-release copy preserves saved history and suppresses publish form preparation. Confirm the intended release/version before preparing. A successful draft is an exact saved plan, not a Jira issue.

For each **Create ticket**, **Link deployment evidence** or **Close ticket** card, inspect status, review version, expiry, issue identity, and provider-write result. **Review exact ticket action** exposes project/type/summary/description/Reporter for create; issue/run URL/run attempt/source commit for link; issue/terminal status/category for close. Expanding this disclosure records the displayed ID/version/digest as locally reviewed and enables a returned eligible approve/execute control; it is not approval itself. A genuine eligible different human must personally review and choose **Approve exact ticket action** under their own current identity. Requester and designated executor are excluded from independent approval by the Jira store. The authorized executor separately chooses **Publish approved ticket**, **Link approved deployment evidence** or **Close approved ticket** only when returned as executable. Do not impersonate a reviewer or automate this human decision. **Cancel unused ticket action** is offered only when permitted.

A controlled transport explicitly says no provider write and may display a simulated issue identity; confirmed local state alone cannot prove Jira creation. Confirmed provider write, refused action, pending/unknown outcome and cancellation are distinct. History lists at most five latest actions and explicitly marks truncation; it is not the provider's complete history.

Lifecycle closure offers **Read Jira closure options**, **Terminal Jira transition**, then **Prepare closure for independent approval** only under returned close availability for a confirmed provider-created issue. **Refresh unused closure action → Save refreshed closure for new approval** preserves history and requires a fresh independent approval; preparation performs no transition. Choose an offered unexpired terminal transition. No supported transition means stop. This is separate from the associated-release path below; do not invent a lifecycle link-preparation control merely because link execution/status rendering exists.

## Associate the original ticket with a deployed release

**Associate existing ticket with deployment evidence** requires **Original published action ID**, **Saved successful deployment evidence ID** and **Current deployed release head version**. These are saved Axiom provenance identifiers, not an arbitrary Jira URL/key import. The deployed release may be a different request from the original ticket request. **Prepare association for independent review** asks the service to recheck original ticket, successful run and current head, then saves an exact review; it neither links nor closes Jira.

Use **Saved ticket review ID → Reload exact ticket review** to inspect status/version, exact provider site/connection/issue identity, original request/action, deployed request/current head, repository/workflow/ref/source commit/run/attempt and expiry. **Technical provenance and integrity bindings** expands saved IDs, connection revisions and digests without mutation. Historical/noncurrent review is explicitly ineligible for approval. A genuine independent reviewer personally checks **I reviewed this exact ticket, deployment and policy evidence** and chooses **Approve exact ticket association or policy** only when current, eligible and unexpired. That shared label does not imply a Jira terminal-policy review exists. **Cancel or revoke review** appears only when permitted. Association approval is provenance only, never provider-action approval.

## Prepare an exact provider link or close

The association mounts **Jira deployment link and closure** and loads history automatically. **Reload associated action history**, **Saved provider action ID → Load saved action outcome**, and card-level **Check saved action outcome** read saved results. IDs, versions, payload digest, expiry, exact scalar provider target/content and attempt count are displayed. The list is bounded to five; empty history does not establish absence in Jira.

**Save deployment link for separate review** requires a current approved association and no existing link/action/draft/accepted link. **Refresh unused link for new independent review** reuses an unused saved draft, preserves history and clears old provider approval. Neither sends a remote link. Review the exact issue, deployment URL/title/global identity when supplied, run/attempt/source and payload digest. A genuine eligible reviewer checks **I reviewed this exact provider target and content → Approve exact provider action**. The authorized executor separately checks that exact version/digest and chooses **Send approved deployment link**. A different version/digest requires fresh review. **Cancel unused provider action** is conditional on returned permission.

For a confirmed provider-written link use **Read verified closure options**; an **Existing confirmed deployment link** card instead offers **Read closure options for existing confirmed link**. That card is historical evidence and never resends the accepted link. Select an offered **Terminal Jira transition → Save exact closure for independent review**. If an unused closure is refreshable, **Refresh unused closure for new independent review** clears prior approval and preserves history. Expired options, no supported transitions or **A closure attempt already exists** block preparation. Closure has its own exact provider approval and **Close approved ticket** execution; association approval and link approval cannot authorize it. Jira's candidate contract binds terminal category `done`; do not substitute a guessed status or ServiceNow terminal policy.

## Stop and reconcile uncertainty

Busy flags block overlapping consequential work; workspace context ownership prevents stale responses from replacing the active context. Reload/reopen the intended release after context change. Unavailable review/action messages ask for saved IDs, current connection, source readiness and release version; a failed read is not a successful empty result.

An unconfirmed mutation holds further changes: reload the exact saved review/action/history first. A pending `dispatching` action offers **Refresh pending execution status** (lifecycle) or **Refresh pending action outcome** (association); these reconcile the existing record. Unknown status consumes the single attempt (shown as attempt /1): do not resend, generate a replacement attempt, or infer refusal from a timeout. Lifecycle unknown copy requires a verified provider read; associated unknown copy requires provider history and reviewed reconciliation. This guide does not expose or promise a mounted Jira unknown-reconciliation form. Read-only outcome checks do not authorize replay. Preserve IDs, version/digest and recorded result for an authorized recovery process.

The previously accepted KAN-4 link and closure are historical accepted work supplied as a scope constraint. **Never repeat either action.** This source-only guide neither rereads nor asserts its current Jira status, and it does not turn those historical outcomes into authority for a new ticket or release.
