## What changes for the user

When the desktop configuration object or context revision changes, the mounted Releases workspace starts fresh for that context. Old request/execution rows, selected release/detail state, local closure inputs, generated results, error/loading state and nested panels are discarded with the old subtree. New-context request and execution reads start from the new mount. Unsaved local drafts are not migrated or promised recovery. Confirm the intended workspace and inspect its saved requests before entering new work. [app-mount, wrapper, view-state, initial-reads]

This differs from choosing another release **within the same workspace**. The focused release renderer keeps every request-keyed detail subtree mounted and uses `hidden` for inactive selections, preserving its local review/draft state while that workspace remains mounted. The context wrapper resets the whole view above that renderer; selection alone does not invoke this reset. Normal navigation away from Releases also unmounts its conditional App branch. No session/account is deliberately signed out by this local lifecycle repair. [app-mount, wrapper, focused-release]

## Actual mount and ownership

App imports `DeploymentRequestsWorkspace` under the local name `DeploymentRequestsView` and mounts that alias only for activeView `deployment-requests`; reading the JSX name alone would miss the wrapper. The wrapper subscribes separately to desktop configuration identity and numeric context revision through the existing context store. It increments a local generation if either changes and keys the original view with that generation. Equal object identity and equal revision do not request a new generation; this is not a comparison of every configuration field, a server tenant token, or a durable global identity. Behavior depends on the existing store notifying subscribers. [app-mount, wrapper]

The original view independently captures its configuration object and context revision at mount. `ownsView` requires it still be mounted and both values still equal the desktop client's current values. Its cleanup marks it unmounted and invalidates revision-read epochs. This second boundary matters before React receives a context notification and after unmount: retained event handlers and already-pending callbacks cannot rely on visual remounting alone. The guard does not authenticate a user or replace server authorization/current policy checks. [view-state, async-reads, action-completions]
