# Application database startup compatibility

INTERNAL SOURCE NOTE. Unpublished and customer/retrieval ineligible. Reviewed November 15, 2026. This records a local source correction, not a verified production recovery.

The application database factory composes the existing explicit PostgreSQL connection policy with a narrow direct-Neon compatibility adapter. Recognized direct `ep-*` Neon hostnames, including the optional `c-N` host label, use a custom installed-pg client that removes the startup packet’s `options` field. It preserves the other startup fields and configured identity, endpoint, verified TLS, channel-binding setting, pool limits and timeouts. It never rewrites a hostname. Pooler hostnames and unrecognized providers retain the existing startup policy.

Before the pool hands a newly connected direct session to an application query or transaction, an awaited initialization hook executes the fixed, qualified `pg_catalog.set_config('search_path', 'public', false)` query. Exactly one row acknowledging `public` is required. Its per-query deadline is the smaller of five seconds and the configured connection timeout. The installed pool awaits the hook and destroys the client on failure. Prisma still creates and owns the pool; missing application configuration remains lazy and refuses without an ambient PostgreSQL fallback. This direct-session initialization makes no transaction-pooler session guarantee.

Source: [factory](../../../lib/database/createDatabaseClient.ts), [connection policy](../../../lib/database/postgresConnectionPolicy.ts), [direct-session adapter](../../../lib/database/directNeonSession.ts), and [focused adapter tests](../../../lib/database/__tests__/directNeonSession.test.ts). The source assessment uses installed pg 8.23.1 startup construction and per-query timeout handling, pg-pool 3.14.0 awaited initialization and failure disposal, and Prisma’s configuration-owned pool path.

Local tests use the actual installed pg startup generator, including poisoned ambient `PGOPTIONS`, and the actual installed pool with a synthetic physical transport. They check preserved fields, endpoint selection, asynchronous handoff, reuse only after initialization, failed/malformed acknowledgments and bounded query configuration. Related factory/policy tests and strict root type checking pass. These tests do not perform PostgreSQL SQL, negotiate a real TLS session, verify a provider response or prove production sign-in/download recovery. A successful build or a demo step alone cannot establish that recovery. No credentials, production settings, schema, deployment or live repair are included in this note.
