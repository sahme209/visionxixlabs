## Find the current workspace and read its context

Use **Releases** in customer navigation. The actual mount is `App.tsx` → active view `deployment-requests` → `DeploymentRequestsView`. The similarly named `ReleasesView.tsx` is not this mount and is not evidence for these instructions. Prerequisites are the selected workspace and a current desktop session; exact consequential access, service enablement and independent-review eligibility must be checked by each returned control. A visible historical card grants no authority. Within **Recorded release details**, **Open Approval Center →** opens the separate authenticated browser approval destination; opening a link is not approval. Its explanatory copy says the context record cannot approve or dispatch. That statement must not be generalized to the separately mounted exact approval/execution panels described below.

Choose a release under **YOUR RELEASES** to focus its details; arrow keys, Home and End move selection. Switching the selected release keeps keyed release panels mounted, so it is navigation rather than cancellation of an outstanding action. Check title, status, **Version**, update time and **Request identifiers** before working. The identifiers expansion shows request and correlation IDs. **Recorded release details** expands scope, readiness, approval signals, window, recovery and recorded observation context. **Release next step** is guidance from recorded signals, not approval. “Ready for human approval” means recorded prerequisites are present; readiness checkboxes and a recorded PR approval value are not independent provider or deployment approval.

**Refresh** reloads requests and recorded workflow executions. Initial loading says **Loading current workspace requests…**. A successful empty list says no deployment requests exist; a failed read is not an empty workspace. If refresh fails, retained records are explicitly stale; compare **Service last responded** and restore current access before relying on them. Session-expiry recovery is sign out/in; network failure recovery is restoring connection and refreshing. Other load failures say to try again. Per-action errors can also add **Needs attention**; that indicator is not a diagnosis. **Working** identifies some request-level operations, while nested panels also show their own busy states.

## Create or complete a request

**New release** opens intake; **Cancel intake** closes it. **Start from ticket** opens a smaller **Ticket-first release draft** with title, applications, what needs releasing, optional ticket link and optional application owner. **Save draft** saves only an Axiom draft, not a ticket, playbook, approval or deployment. **Explore Jira ticket fields** optionally opens read-only discovery; a paired administrator session is required for that discovery, while a manually entered existing ticket link can still be saved. **Cancel draft** or **Back to release requests** leaves the draft screen. After a workspace change, close the old draft and start again in the selected workspace. A saved draft displays **Complete release details**; its original ticket request remains in the immutable record.

For full intake, use **Continue** in order; **Back** and already reached step buttons let you review prior sections. Future steps and Back at step one are disabled. Do not infer persistence from a completed step. The final submit validates the complete request, while errors retain entered values.

| Step / purpose | What to enter and check | Result / recovery |
| --- | --- | --- |
| **Window** | Request title, request class, start/end, display time zone, change type. Ad hoc/emergency additionally require reason, priority, business impact and schedule exception. | Local datetime inputs become UTC instants using the machine's date parsing; the display-zone selection is recorded separately. Verify intended instants rather than treating a display-zone label as an input conversion. Complete highlighted required information before Continue. |
| **Scope** | Applications, clients, deployment/application/escalation owners, repository URLs, source and target branches. Supply production PR URLs and recorded PR approval, or explicitly choose **No production PR required**. | Scope/ownership are recorded, not independently proven. Commas or line breaks separate list entries. The no-PR choice also changes which downstream panels are mounted; see below. |
| **Execution** | Deployment method, workflow name/trigger, target environment, workflow source ref and exact inputs. Optional manual instruction also requires owner and validation. | Blank workflow source ref uses source branch. An exact protected tag requires rereading workflow fields at that tag and does not change the PR source branch. Discovery assists intake; it does not authorize dispatch. |
| **Validation** | Tested lower environments, development/production ready, exact technical validation and owner, expected result; functional validation and owner when required. Deferred validation needs reason, trigger, follow-up date/owner and monitoring plan. | These are recorded obligations and readiness assertions. A monitoring plan is not connected monitoring, and a deferred validation record does not prove later completion. |
| **Recovery** | Rollback availability; exact instruction/owner when yes; backup-required and evidence identifiers when required; change-creation method; confirmed operational fact, source evidence ID and confirmed-by. | Saves planned recovery and cited facts. It neither performs backup/rollback nor creates a native change merely because a creation method was selected. |

**Submit release request** saves a workspace request. **Submit completed request** completes a ticket-first draft and preserves the original draft. **Revise** loads the current intake and opens **vN → vN+1**; **Save revision** saves a new version with history. None of these deploys. Revision loading has **Opening…** and failure states; if the read cannot be confirmed, retain the existing intake and reload the intended request rather than guessing a version. Closed requests disable revision and next-playbook generation. Saving can be refused by the service despite local completeness; preserve the error/context and reload current state before resolving a version conflict.

### Discover workflow fields and select exact batch dependencies

In Execution, **Find workflows** needs one supported GitHub repository and a source ref. Choose **Repository workflow**, then **Read workflow fields** for that exact repository/ref/path. Empty listings and a recorded workflow missing from the listing are explicit and do not overwrite the recorded path. Failed discovery retains manually recorded inputs. Reading fields blocks advancement while verification runs. Repair JSON before continuing; undeclared inputs have **Remove**, required values must be supplied, and boolean/number/choice fields must match their declared type. **Apply missing defaults** fills only missing values. Environment inputs require the exact repository environment name; this panel does not enumerate environments. A listed file does not establish workflow-dispatch support.

Under **Required batches**, **Read Airflow connection** reads the current connection. Enter **Batch DAG**, **Find batch runs**, choose **Exact batch run**, then **Use selected batch**. This records a specific DAG/run/logical date, not “latest successful batch.” **Remove** drops a selected dependency from intake. Duplicates, changed connections and the maximum 25 runs prevent addition; remove old selections before using a changed connection. Unavailable/unverified reads do not prove completion. Batch completion never approves a release.

## Review history, planning and evidence

For a draft, the main actions are **Complete release details** and **Review history**, plus the Tickets workspace. Non-drafts offer **Planning tools**, **Revise**, **Review history**, **Review execution controls** and **Collect GitHub evidence**. The latter read controls can remain available on closed records; their presence does not reopen the release.

| Control / location | Steps and expected result | Boundaries / recovery |
| --- | --- | --- |
| **Review history** | Load governed version entries, safe changed-field categories, author category and timestamps. | It omits contacts, URLs, workflow inputs, evidence references and full member identities. Load failure is shown separately. Empty history is not proof that no other record exists. |
| **Review execution controls** | Read durable operation kind, saved status, attempt count, timestamps and external-reference flag. | This particular panel cannot create, retry, approve or dispatch operations. An empty ledger means no consequential operation is recorded there. Use nested exact execution controls separately. |
| **Planning tools → Generate next playbook** | Generate/persist the next playbook, then inspect version, scope, content SHA-256, ordered roles/activation/evidence and validation instructions. | Disabled when closed or generating. A persisted playbook is generated/audited only: no merge, dispatch or environment approval. Errors display locally. |
| **Review persisted playbook / Review historical playbook** | Open the stored version and digest. A superseded playbook is labeled historical after revision. | Historical content is not current authority. An opening error is reported in the playbook error area. |
| **Collect GitHub evidence** | Read displayed repository observation/branch protection/latest workflow and linked PR state/checks. The response also contains repository-enabled and target-match metadata, but this card does not display those values as separate controls. | Read-only evidence may be unavailable, in progress or not reported. ### Saved Terraform plan evidence

Open **Planning tools → Review Terraform evidence → Read saved plan metadata**; choose **Inspect** on a digest to read the artifact summary. The list covers at most 20 recent artifact records. Inspect scope, binary SHA-256, request version/environment, expiry, counts and resource rows. A local fixture verifies no customer cloud account. Customer producer evidence can be historical or expired; even verified producer bytes do not establish current target authority. A displayed current backend match is a read-only observation with no held lock. **Terraform apply stays disabled**; approval/current authority are unavailable. Metadata-only, missing, malformed or unavailable evidence must not be presented as an inspected current plan. Ask the workspace administrator to review storage/trusted producer when unavailable.

The nested **Customer CI plan evidence** panel also mounts here: **Read customer plan profile**, current role/permissions, profile status/revision, environment, canonical repository and observed AWS connection. Authorized configuration requires the exact repository/ref/source SHA; reviewed workflow/script paths and SHA-256 digests; trust/toolchain profiles and separate CI plan-role ARN; canonical JSON root/tree/provider-lock digests; existing region/state bucket/key/lock table and artifact bucket/prefix/KMS identity. **Save review profile** saves configuration locally; reread to obtain the fresh **Protected CI profile export**. Environment is immutable once profiled: a different environment requires a new deployment request. **Revoke profile locally** does not revoke provider grants or issued sessions. The export contains configuration identity, not credentials or an execution permit. **Import completed CI plan** requires an active current-version profile, import permission, unchanged saved fields and completed CI run ID/attempt. It imports evidence from a separately authorized protected customer CI job; it does not start CI, Terraform or apply. Changing fields invalidates evidence; save and reread before import. These are main-control instructions, not customer CI provisioning or producer acceptance instructions.

## Review exact merge plans and separate approvals

**Mount limitation:** **Merge review** mounts only when the release is `submitted` and **No production PR required** is false. **Saved operation plans** and all its nested approval/execution/evidence panels mount inside that component. This guide does not promise these controls for a draft, closed release, no-PR request or another status merely because backend routes exist.

**Review merge / Refresh merge targets** reads linked PRs. Select **Linked pull request** and **Merge method** (merge commit, squash or rebase), then **Read merge plan**. Compare repository, PR, head/base refs and commits. This first preview is review only; it cannot run a merge. Selection changes invalidate its preview; unavailable/changed evidence requires rereading targets.

In **Saved operation plans**, **Load saved plans** reads at most five plans with status, version, digest, release version, deadline and expandable **Plan history**. Empty, service-disabled and access-limited results are distinct. Eligible managers use **Load plan targets → Pull request / Method → Read current plan → Save exact plan** while the preview is unexpired. Saving persists an exact snapshot, not execution authority. A reviewer uses **Read fresh review preview**, compares the same saved digest and version, then personally chooses **Record independent review** or **Reject plan**. **Cancel saved plan** appears only when permitted. An expired preview, changed digest/window/version, stale plan or unavailable read requires refreshing the source/plan; a deadline never extends itself. After an uncertain mutation, **Load saved plans** confirms the original outcome before another change.

A genuine eligible human must perform each independent review using their own current identity; do not impersonate, auto-check on their behalf or treat the requester/executor as independent. Saved review, simulation approval, provider merge approval and deployment approval are separate decisions:

| Panel / control | Purpose and required steps | Outcome and limits |
| --- | --- | --- |
| **Independent execution approval** | **Reload execution approval**; an eligible different person may choose **Approve exact plan for simulation**. **Revoke execution approval** appears only for an unused revocable approval. | This approval is explicitly simulation-only. Approved, consumed, revoked, refresh-needed, disabled and absent states are distinct; this panel does not execute a simulation or provider action. |
| **Provider merge approval** | **Reload provider merge approval**; personally inspect exact repository/PR/method, source head, observed base and displayed Governance baseline. Check **Review exact provider merge policy**, then **Approve exact provider merge** if eligible. | Requester remains designated executor; approval belongs to a different eligible person. Simulation approval cannot authorize a GitHub merge. Governance unavailable blocks current authority. **Revoke provider merge approval** only when unused/revocable. |
| **Review deployment access** | **Load verified deployment review**; inspect exact protected/immutable-release tag policy, source commit, workflow blob/path, inputs, executor, window, plan digest and Governance baseline when shown. Eligible independent reviewer checks **Review exact deployment approval → Approve exact deployment action**. | Creator, requester and executor cannot approve this action. Approval alone dispatches nothing; an unconfirmed approval requires reloading the release before another action. |

Simulation/provider-merge approval panels are conditionally mounted for reviewed/stale stored plans at plan version 1. Deployment review/execution and release-workflow evidence are mounted for each loaded plan, but the service still determines whether current actions are available. A historical/stale card never overrides those checks. Current enablement and permissions were not exercised for this draft.

## Deliberate provider execution and recovery

Only perform these steps for an authorized exact action after genuine separate approval. Source inspection of a button does not establish that execution is enabled in the current service.

| Panel | Supported sequence | Read outcome and recover |
| --- | --- | --- |
| **Run the reviewed merge** | **Load merge execution**; when available and no operation exists, **Prepare provider merge** saves preparation without sending a merge. On the prepared operation, inspect repository/PR/method, exact head and observed base; personally check **Confirm exact merge execution**, then **Execute reviewed merge**. **Cancel prepared merge** cancels an unused prepared operation. | Attempts are shown as **of 1**. Confirmed merge displays merged commit. `dispatching`/`unknown` means unconfirmed: do not send another merge request. **Recover saved merge record** reconciles the existing operation, then load execution again to confirm saved outcome. |
| **Run the reviewed deployment** | **Load deployment execution → Prepare provider deployment** when available. Inspect request/plan, repository/workflow, tag/ref policy, source commit/blob, window, digest and **Review workflow inputs**; personally check **Confirm exact deployment execution → Execute reviewed deployment**. **Cancel prepared deployment** acts only on an unused prepared operation. | Preparation does not dispatch. An acknowledged workflow run/attempt and **Open acknowledged GitHub run** prove acknowledgement, not successful deployment. `dispatching`/`unknown`: do not send another request; use **Recover saved deployment record**, then load execution again. |

The merge enforces the source head; the observed target base is evidence, not an atomic merge condition, and the target may advance. Deployment source guarantees and exact independent approval are checked by the server before dispatch. Access-disabled panels can retain readable prepared targets/history; do not interpret those as runnable. Busy states prevent repeated clicks. Uncertain responses hold further mutations; reload the original saved outcome. Recovery is reconciliation, not permission to reset, duplicate, renew or replay a consumed attempt. A refused status is also a saved outcome, not a blanket instruction to create a replacement.

### Read evidence for the accepted run

Within a saved plan, **Deployment evidence → Load release workflow evidence** reads evidence bound to this release/plan. When available, **Collect accepted run evidence** saves the accepted run's observation and can immediately reconcile a pending record; it does not dispatch another workflow. Check repository, run ID/attempt, workflow path/ref, observed source and observation time. **Refresh workflow observation** reconciles eligible pending/unknown records. **Stop tracking this evidence** cancels local tracking, not the provider run. Unknown means unconfirmed without automatic retry. The list is limited to five records, and reconciliation/tracking controls are version bounded. Unavailable observation can still show saved history; absence of saved evidence is not proof of provider failure. Workflow success alone does not verify delivery, health or ticket closure. Unconfirmed evidence mutations require loading original saved evidence before further action.

For submitted releases with selected batches, **Check batches** reads current completion, distinguishing waiting, changed context and unverified outcomes. **Monitor batches / Refresh monitor** reads saved background status. If offered to a deployment operator and enabled, choose **Watch duration** (15 minutes, 1 hour, 4 hours or 24 hours) → **Start watching**; **Stop watching** cancels only the monitor. Expired/failed monitoring requires manual batch checks. “Batches finished” still requires release approval; monitoring cannot auto-approve or deploy. An unconfirmed monitor mutation refreshes saved status, and unavailable status must be refreshed before another attempt.

## Tickets and recording an external outcome

Every selected release mounts **Tickets** with **Jira / ServiceNow** tabs. The tabs select provider controls, not provider authority. **Explore read-only Jira form** requires a paired desktop session and opens discovery separately from saved lifecycle actions. A preview does not publish a ticket. ServiceNow uses configured native process metadata and explicitly loaded saved history; no connection or native lifecycle stage is assumed.

For detailed ServiceNow association, already-written UNKNOWN-note observation, genuine native lifecycle, terminal policy, independent review and closure/readback, use [ServiceNow evidence and closure controls](servicenow-evidence-and-closure-controls.md). Do not duplicate that lifecycle from this workspace overview. The project's existing note is already written under a consumed **UNKNOWN** attempt: **never resend, reset, renew or create a descendant of it**. Load original saved history and follow the separate exact written-note observation route. Axiom approvals cannot impersonate native ServiceNow approvers or substitute for genuine native lifecycle requirements.

For a non-draft, non-closed request, **Record external outcome and close request → Validation or change reference / Recorded outcome summary → Record closure** records an external report and closes only the Axiom request, using its current version. **Cancel** exits the closure form; **Recording…** disables resubmission while busy; a returned API failure leaves the form/error for correction against current state. This handler has no catch/finally around the awaited close call: a thrown transport error is not guaranteed to clear busy state or render an actionable error. Treat an unconfirmed close as unknown, read the current request before any further change, and do not infer failure from a stuck form. A closed card says **Closure recorded** and can show its time. This control neither merges, dispatches, independently approves nor proves native ticket closure. It is separate from ServiceNow's exact native closure action and verified readback.

## API meaning and explicit omissions

The inspected direct desktop-client calls target `/api/desktop/deployments`: list/create, `/drafts`, request revision/history/closure/playbook/operation/evidence reads, request-bound `/operation-plans` preview/save/review/cancel, and plan-bound `/execution-approval`, `/provider-approval`, `/provider-execution`, `/provider-operation`, `/deployment-approval`, `/deployment-execution`, `/workflow-evidence`; request-bound batch waits/readiness and Terraform evidence/profile/import also support the controls described. Read previews use GET, while POST can mean local save, approval, read reconciliation or deliberate execution. DELETE can revoke/cancel a local record. HTTP method or a successful response alone does not prove a provider write or successful release. Exact expected versions, digests, current-context checks and returned authority gate client actions; this draft does not audit every route/store or establish every backend invariant.

Finite coverage is the actual main Releases mount, its intake, direct planning/history/evidence controls, and the mounted children described above. Deliberately omitted nested scopes: every Jira discovery field and Jira lifecycle/action/recovery control; the full ServiceNow native lifecycle (linked guide owns it); the manual workflow JSON editor's complete subcontrols; provider settings/setup, Governance editing, native GitHub/CI/ServiceNow pages, cloud/storage/CI producer provisioning, dormant `ReleasesView`, browser Change tickets handoff, and all backend/test/native acceptance matrices. Terraform configuration fields are inventoried for their main profile purpose, not a provisioning walkthrough. This guide provides no catch-all “every release control accepted” claim.
