## Entry and scope (`batches.entry`)

`customerNavigation.ts` labels `airflow-automation` **Batches**; App mounts `AirflowAutomationView` for that view. The four tabs are Workflows, Automations, Approvals and Connection. Investigate with Agent sends DAG ID, optional run ID, current desktop configuration and workspace identity to Agent and navigates there. This guide does not establish the receiving Agent's behavior or execution authority.

## Connection (`batches.connection`)

Connection accepts an HTTPS deployment URL and either username/password or bearer token. Client validation rejects credentials in URLs, query/hash, unsupported paths and `/api`, `/auth`, `/home`; the service validates separately. Validate & connect is disabled while busy or inputs are incomplete/invalid. It PUTs the connection, validates provider version and DAG access, and saves scoped encrypted credentials and validation metadata. Successful form submission clears password/token. The connected summary shows endpoint, version and DAG count from returned metadata; it is not an ongoing health probe. Disconnect DELETE revokes the matching connection and disables organization Airflow automations when a connection exists; it does not promise to cancel work already sent to Airflow.

The view checks connection status on load and refresh. Loading shows “Checking Airflow connection…”. Unavailable status offers Retry connection status and explicitly says existing connections are not removed. A confirmed disconnected state offers Open connection setup. Setup is not rendered when status is unavailable. Connection labels referring to protection or encryption are UI copy, not independent security certification.

## Workflows, runs and task observations (`batches.workflows`)

Select a returned DAG; the catalog marks paused DAGs and displays description or its fallback. The provider client requests up to 500 DAGs, with no mounted catalog pagination. Run now is disabled while busy, with no selected DAG or for a paused DAG. It opens a review dialog naming the DAG and warning that a real run uses default configuration and may change external systems. Confirm DAG run rechecks ready catalog, same selection and unpaused state, then POSTs an empty object through the desktop client; the service supplies empty `conf`, generates a run identity and returns an identified provider run. Success notice says queued, not completed. Cancel closes this local review before dispatch; it is not a provider cancellation control.

Recent runs loads the selected DAG, shows run ID, logical date or fallback, and state. Its default provider request is 50 runs ordered by descending logical date; no older-run paging control is mounted. Refresh run history is disabled during loading. Watch runs toggles 15-second polling only while Workflows is active, a selected connected DAG is ready, history is not loading and the document is visible. Investigate on a run uses the App handoff described above.

Inspect tasks fetches observations on demand; Refresh tasks reloads offset zero. Each page displays task ID, mapped index when nonnegative, state or “Not scheduled”, and try number. Previous uses offset minus 100 bounded at zero; Next uses offset plus returned count while more entries remain. Busy disables task buttons, and errors state that no execution outcome is confirmed. The service requests at most 100 task instances and verifies selected DAG/run identities and response shape. These controls expose neither logs nor XCom/rendered templates, task mutation, retry, clearing, cancellation or deployment approval.

## Automation configuration and lifecycle (`batches.rules`)

The automation panel first mounts after a successful DAG catalog read; it stays mounted but hidden off-tab. Its verified flag requires a ready connected connection, DAG catalog and automation read. The form and Pause/Enable require verification and no busy action. Failed optional repository/environment reads leave those catalogs empty; they do not hide pending approvals.

New automation fields are name, source DAG, Finishes successfully or Run on schedule, and Then. Schedule offers hourly, daily 06:00 UTC or Monday 06:00 UTC. Then offers completion recording with configured webhook notification, opening a pull request, or restarting an environment's ECS service. GitHub/cloud choices additionally require a listed repository and a branch from a successful repository-specific branch read; restart requires a listed environment. Branch-read failure exposes Retry source branches. Advanced expands dependency DAG checkboxes (excluding the selected DAG) and human approval. Approval is locked on for GitHub/cloud changes; it can be unchecked for the `none` action. No webhook destination editor is mounted here.

Create requires a nonblank name, listed source/dependency DAGs and applicable verified destinations. Payload fixes required state to success, source kind to branch, PR base to repository default, generated PR title, three retries with 60-second delay, and success/failure notifications on. These are submitted configuration values, not evidence a scheduler or webhook delivery is currently operating. Service validates schedule/configuration and connection, scopes environment lookup to organization, and forces approval for writes.

Active rules show name, DAG/action, approval indication and next schedule when supplied. Pause/Enable PATCH only the enabled boolean. No mounted control edits an existing rule's name, schedule, action or destination; no delete button or delete desktop-client method is present. The direct DELETE route exists but is outside mounted controls: it refuses rules with execution history and advises pause, otherwise deletes the unused rule and records an audit event. Do not present that route as a customer click path. Pausing is not cancellation of an already dispatched provider action.

## Approvals and recorded outcomes (`batches.approvals`)

Approvals reads the returned execution set (service caps it at 100). Pending approval records show automation name (or fallback), source DAG/run/state. Non-restart records mount Reject and **Approve & run**; the latter POSTs approval and invokes the executor with the authenticated session user. It is a combined approval/execution request, not the Agent flow's separate review protocol. Reject updates a still-pending execution to rejected with decision/completion timestamps and an audit event. Neither button is an invitation for an assistant to impersonate an approver.

Restart records instead mount AirflowRestartReviewCard. Review restart destination fetches immutable review evidence and validates execution ID, digest shape, operation, dependency policy and target fields. It displays source evidence, repository/ref context, environment/tier, target/revision, AWS role/region, ECS cluster/service and digest. Approve service restart stays disabled until a matching review is read and while busy. It submits that digest; context changes invalidate the read. Reject remains available while review is absent, unless busy. The card states service restart does not promote a source release, select an image, verify cloud health or recover an image; dependencies use latest-run freshness, not exact cross-DAG run correlation.

The executor requires an enabled/actionable record and any required human approval, rechecks accepted approver authority, validates connection/source/dependencies for writes, checks governance refusal and restart review, and claims the observed execution attempt before dispatch. A request may therefore be refused even when its UI button is enabled. Success of the request is not proof of application health. The panel displays at most 20 non-pending records from the returned set, status and attempt count; `needs_reconciliation` becomes “Outcome unconfirmed — review before retrying”. It mounts no replay, manual retry, cancellation, full audit explorer or general history detail control.

## Permission and recovery boundaries (`batches.recovery`)

All inspected desktop Airflow routes disallow API-key authentication. Reads require `pipeline:read` plus `workspace:read`; connection writes require `pipeline:trigger` plus `connections:manage`; rule creation and enabled changes require `pipeline:trigger` plus `policy:manage`; direct DAG trigger requires `pipeline:trigger` plus `deploy:execute`; approve/reject require `pipeline:trigger` plus `agent:approve`. The view does not receive a role prop to hide these controls by role: the service remains authoritative. Direct DAG trigger additionally rechecks current desktop session, persisted expiry/revocation and mutation authority around provider dispatch. This is a source description, not a claim of atomic cancellation of in-flight network actions.

Workspace Refresh is disabled while busy/refreshing. Catalog and automation read failures show distinct alerts. Run-history loading, unavailable and empty states are distinct; empty runs say “No runs returned”, empty rules “No automations yet”, and empty pending approvals “No actions are waiting for approval”. Request generation and context revision guards prevent old reads/actions from updating a changed workspace view. The shared action wrapper serializes mutations, reports a bounded recovery message, reloads workspace data on success and failure, then refreshes selected run history.

Missing credentials/configuration/destinations call for correcting inputs. Changed connection or unavailable preconditions call for refreshing and reviewing. Missing/stale immutable review calls for rejecting and waiting for a new proposal; unavailable review storage leaves approval unavailable and directs an administrator to inspect the installation proposal. Unconfirmed allowance release, local action state or provider acceptance pauses automatic replay according to the displayed notice. Unknown error codes and thrown failures use the generic unconfirmed-outcome notice: refresh and review history before retrying. These notices are guidance, not proof recovery has occurred. Never blindly replay an uncertain mutation or manufacture a human approval.
