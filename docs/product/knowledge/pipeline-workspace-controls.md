## Direct controls and displayed states

| Surface/control | Actual effect and limits |
| --- | --- |
| Catalog **Back to Workforce** | Navigates to `/dashboard/workforce`; grants no action permission. |
| Per-catalog **Run pipeline** | Sends a cookie-authenticated POST to the fixed registered pipeline start route with an empty JSON object. It supplies no repository, instruction, cap, model or approver form. **Starting…** spins/disables the button. Success with a run ID navigates to its timeline; API/parse/network error renders a message and re-enables it. No automatic retry, original-request lookup, durable idempotency key, cancel or refresh control is implemented in this button. A lost response may follow a created run; inspect recent history before any deliberate new start rather than assuming rollback or blindly resending. |
| Recent-run row | Navigates to exact run detail. Catalog loads at most20 newest workspace runs, status/count summaries and registry descriptions. It is not an exhaustive audit browser. Database failures are caught as empty runs/counts; **No runs yet** or zero cannot establish that history is empty or service healthy. |
| Run **Back to pipelines** | Returns to catalog; no execution, cancellation or rollback. |
| Stage **approval · ID →** link | Appears only with a saved approval ID; navigates to the separate approval detail. It does not vote or execute by navigation. Nested approval UI is outside this direct-control inventory. |

Both pages require authenticated workspace context or display **Sign in required**. Run detail returns not-found for missing, inaccessible/caught-read failure or foreign-workspace run; no cross-tenant record is displayed. They are dynamic server renders, not a continuously polling console. There is no run-detail Start again, Resume, Retry, Cancel, cap editor, model picker, artifact editor, stage vote or Execute button in these two pages. Backend comments about manual re-trigger do not create such a control.

Catalog displays queued/running/succeeded/failed/cancelled run values with fallback styling. Timeline displays ordered queued/running/succeeded/failed/skipped/awaiting-approval stage states (unknown values fall back to queued presentation), timestamps, kind, output/error text and optional approval link. Pending summary counts queued/running/awaiting approval. These are saved workflow states and descriptions, not independent proof that repository tests, deployment, provider action or security acceptance succeeded. Registry duration copy **~seconds dry-run** and marketing language do not establish dry-run mode, complete executor coverage or safe execution. Unregistered stage kinds fail unavailable rather than succeeding by default; real coding executor registration is separate server composition, not a UI guarantee. Coding lint/test definitions describe static patch/assertion review, not execution of the repository compiler/test suite.

## Start, read and decision authority

Session start requires same-origin request, authenticated organization/user/session-user identity and a role with `actions:apply`; it records the session user as requester. Unknown pipeline refuses. It creates the run/stages, then advances synchronously until failure, gate or completion; HTTP success/run ID only means start returned, not all stages succeeded. The catalog's empty body cannot supply required coding repository/instruction metadata; use an existing authorized task workflow where applicable, not invented fields, credentials or a new endpoint from this guide.

The separate v1 API family is not what the catalog button calls. It uses existing authenticated API-key scopes: `pipeline:trigger` for start/decision and `pipeline:read` for exact run read, with tenant-derived lookup. Machine decision actor is `api_key:keyId`; caller `approverUserId` labels are ignored. Distinct keys are distinct machine principals, not genuine independent human reviewers. No API request is executed or credential supplied here.

An awaiting stage links to its saved approval. Session decision uses existing decision-role authority, exact workspace/principal and durable vote/quorum rules; duplicate/decided/unbound/changed coding review refuses. Coding approval must match the exact saved artifact digest. Terminal quorum can resume the stage and advance the runner automatically; it is not a promise the downstream action succeeded. Resume is best-effort, so a terminal vote and a paused run can coexist. Do not invent a run-detail resume button or duplicate votes to repair that uncertainty.

Generic linked approval execution is a distinct route/control in its own workflow, guarded by current `actions:apply`, approved snapshot and not-started execution CAS. It is not a pipeline-detail control or an extra click universally required by every pipeline. For coding PR writes, the runner's original requester is separately checked with current membership/apply authority, running run and exact approved artifact; provider credentials/access/base-content and one-attempt outbound lifecycle still matter. Stage approval alone is not generic provider authority, permission to merge a PR or proof of two human approvals. The coding path can push a branch/open a PR when its own guards succeed; no autonomous merge is claimed. Uncertain write outcome remains unknown, not a safe retry invitation.

## Coding budgets and recovery

Current fixed request reservation defaults to1000cents, while the platform run cap defaults to500cents. A default-sized paid coding attempt can therefore be refused before provider dispatch even when workspace credits exist. Saved policy/run metadata can restrict allowance; request metadata does not grant a larger cap/unlimited spend. Do not automatically raise caps, change model, lower holds, manufacture cheaper estimates or retry to make a refusal disappear. Exact pricing quotes and useful default-sized completion remain separate unfinished work; this guide adds none.

Actual queued-to-running CAS mints an opaque stage capability. Each initial/refinement admission rechecks run/stage/generation/actor/correlation, current member/model/policy/cap and atomically coordinates run/workspace holds. Initial/refinement are distinct one-use phases; unknown is not a refinement/retry. Reserved safe-void and dispatched-unknown/pending/settled are different states. Dispatch uncertainty keeps full held exposure; timeout, missing usage or lost response is not a refund or TTL-based release. Settled provider cost and billed margin differ; over-estimate anomalies are retained and block later paid work.

The global-admin telemetry route is gated by configured admin email, not ordinary tenant pipeline UI. Its pending/unknown/final cost projections are not authorization or provider invoice proof, and display zero is not verified final zero. New telemetry source here is local implementation only; no deployment or live acceptance is inferred. Neither pipeline page supplies this ledger/telemetry management UI.

Normal next step is inspect the exact saved run/stage error or linked approval in the existing authorized workflow. For denied role, missing metadata/connection/executor, stale artifact or budget refusal, preserve that prerequisite and obtain the responsible existing administrator/workflow review. For lost start/vote/write acknowledgement, inspect existing run/approval/history first; no automatic replay, reset, new nonce or provider undo is authorized. Pending/expired/rejected approval states do not authorize execution. This source inventory does not prove expiry-sweeper operation, current access, registered runtime executors or full recovery after restart.
