## What the root checks

App keeps accepted identity separate from mere credential presence. It subscribes to the current client **configuration object**, captures that exact object when verification accepts identity, and shows authenticated/access-required content only while that owner is still current and `hasAuth()` is true. `hasAuth` itself means only a loaded session token is present; it does not prove validity or entitlement. A present replacement configuration shows **Verifying saved sign-in** while the existing coordinator checks it; the departed workspace is unmounted rather than left available behind a loading label. Local drafts in that departed subtree are not migrated or promised recovery. [root-verification, root-render, client-presence]

The client replaces its configuration object on `setSession` and `setApiBase`; it notifies context subscribers when the token/base value actually changes. Ordinary numeric context-revision notification with the same configuration object does not trigger root reauthentication. Same-value setters still replace the object but do not themselves send a changed-value notification; this guide does not promise notification of arbitrary in-place mutation or every external change. Root ownership is not a server tenant token, role grant or a comparison of every nested field. [client-context, root-verification]

The existing coordinator starts verification for a changed root configuration and on window focus. It captures the configuration before awaiting and accepts only the latest request, same current configuration, still-present credential and non-disposed coordinator. Missing credentials invoke the missing path without a request. Canceled results are not treated as rejection. Unexpected verification errors become the fixed unavailable result. Rejection clears the loaded transport session/identity, not the saved vault solely because of a network/schema failure; unavailable classification retains the existing saved-sign-in recovery option. No automatic saved-credential retry loop is introduced. Explicit verified sign-in or access-granted callbacks invalidate older coordinator work and bind the current configuration. [root-verification, root-render, coordinator]

## Sign-out and cleanup states

In the actual App mount, Settings **Log out** and access-required **Use another account** delegate to the root's existing-helper sign-out operation. Optional child fallback handlers remain for mounts without that callback; this supplement describes App's delegated path. Root handles cleanup outcomes after those child subtrees are removed. It checks mounted state, expected configuration and a synchronous single-flight flag before invoking the helper. [root-signout, settings-entry, access-entry, root-plumbing]

The unchanged helper immediately clears the in-process session, writes a signed-out selection tombstone, then attempts all three legacy credential-key removals. A failed tombstone write can leave saved selection intact; failed legacy cleanup can leave older values. Neither case silently restores a session. These are local persistence operations, not remote revocation, provider logout or proof of server-side session cancellation. Root captures the now-locked configuration immediately after calling the helper, before awaiting it. [credential-signout, root-signout]

| Current owned state / control | Visible result and next action | Limits |
| --- | --- | --- |
| Sign-out cleanup pending | **Finishing sign-out**; normal sign-in is unmounted | A sent vault write is not canceled by this UI. No timed completion guarantee. |
| Cleanup failed | **Finish signing out**, a truthful alert, and **Retry saved credential cleanup** only | Normal sign-in is unmounted so it cannot compete with cleanup over secure writes in this same root workflow. |
| Retry saved credential cleanup | Deliberate normal button activation invokes the same helper again; pending returns to the locked Boot screen | Requires that exact failed configuration still be current and transport still missing. Synchronous flight guard refuses burst repeats; no automatic retry. |
| Cleanup succeeds | Failed state clears and normal sign-in becomes available | Initial Settings sign-out retains its reload-on-success behavior, only while the captured locked owner remains current. Access-required sign-out and cleanup retry return without that reload. |
| Configuration is replaced while old cleanup is pending/failed | New configuration must verify independently; old result cannot apply warning/state or reload its workspace | Does not cancel the older physical vault operation or establish a cross-window transaction guarantee. |

The exact failure alert is: **Sign-out could not be saved completely. Your workspace is locked, but saved sign-in details may remain on this device. Retry saved credential cleanup when secure storage is available before reopening the app.** Retry after secure storage becomes available. Do not interpret a locked UI as proof that saved values were removed, and do not close/reopen expecting the failed operation to have completed. No alternative credential-restoration or bypass action is provided in this failed-owner screen. [root-signout, root-render]

A retained old sign-out/retry handler checks the client's current configuration directly, including before React receives a replacement notification. A retry additionally requires missing transport. Old success/failure callbacks apply only while App is still mounted, exact locked configuration remains current and transport remains missing. These local owner checks do not serialize other processes or external vault writers, resolve unknown persistence outcomes, or revoke credentials already used remotely. The helper/client/coordinator authority sources were not changed by this repair. [root-signout, credential-signout, final-receipt]

## Sign-in cleanup and cancellation boundaries

The actual sign-in component owns an AbortController for browser sign-in, saved-sign-in recovery and administrator-key attempts. Unmount cleanup aborts its controller and clears the local reference. Result handlers check the controller/current attempt before calling `onSignedIn`. Browser/key paths mark a committing phase through existing callbacks; the explicit Cancel handler refuses during that phase. Earlier browser cancellation resets its local UI and abort signal. Saved recovery checks current selection/context separately in the helper. These are source observations, not proof that abort reverses a secure write or revokes a session. [signin-lifecycle, credential-save, credential-recovery]

The credential helper checks abort before committing one selection value and again before activating a verified candidate in the client. A write already awaiting secure storage is not made transactional or reversible by component unmount. The exclusive failed/pending cleanup view prevents normal sign-in and manual cleanup from being concurrently offered in this same App workflow; no cross-process, cross-window, native vault or general credential concurrency qualification is claimed. No provider call or new identity permission is added by the retry control. [signin-lifecycle, credential-save, root-render]
