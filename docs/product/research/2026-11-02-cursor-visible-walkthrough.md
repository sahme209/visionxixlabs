## Axiom implications — design inferences, not shipped changes

- Explain the governed-release purpose before listing integrations. Pair each supported outcome with authentic Axiom evidence and a clear next step.
- Separate work surfaces and workflow stages instead of presenting every feature as an equal card.
- Make documentation part of each feature journey: prerequisites, steps, outcome, limitations and recovery, with a stable direct link from the app.
- Use a navigable security index that separates platform commitments from customer configuration and distinguishes deterministic enforcement from model guidance. Publish only controls Axiom has actually verified.
- Provide searchable docs with keyboard access, topic breadcrumbs and compact results. The future support knowledge layer must remain version-bound to verified Axiom documentation.
