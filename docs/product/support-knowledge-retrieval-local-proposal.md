# Local support knowledge retrieval and evaluation proposal

November 3, 2026. **Local implementation approved November3,2026 (call_ac21a7d79cf24669a2a52beea689affe); bounded offline implementation verified (see recovery receipt). No customer ingestion, publication or activation authorized.**

## Decision requested

Approve a subsequent, separately bounded implementation of one offline, deterministic, read-only retrieval/evaluation composition. It would validate an explicitly supplied reviewed catalog and exact local bundles, select eligible article sections, and return quoted guidance with reproducible citations or a fixed uncertainty response. It would use no model, embeddings, network, database, credentials, provider calls, uploads, UI, endpoint or background service. Approval of this design would not approve customer content, establish a human editorial decision, ship a release or activate a support agent.

## Source grounding and present limits

- [B5](axiom-master-action-plan.md#b5-prepare-the-support-ai-knowledge-foundation) requires reviewed ingestion, version matching, citations, uncertainty, representative evaluations, private/role boundaries and prompt-injection controls. Structured JSON alone does not satisfy it.
- [Coverage README](documentation-coverage/README.md) distinguishes schema/hash validation from genuine editorial review, release verification, supersession discovery and executed retrieval. Its current summary calls deployment revision 2 latest, while a revision-3 article and fixture exist on disk. A directory summary or supplied bundle alone therefore cannot establish currentness.
- [Article contract](documentation-coverage/article-record.schema.json) provides IDs/revisions, classification, exact version, sources/media, review metadata and a supersedes link. It cannot authenticate a reviewer or prove absence of later revisions. [Existing validator](documentation-coverage/validate-support-knowledge.cjs) validates schema, local safe paths, hashes and fixture bindings; customer checks reject draft/internal/local-preview metadata. Do not weaken or replace it.
- [Evaluation contract](documentation-coverage/retrieval-evaluation.schema.json), [Agent cases](documentation-coverage/agent-reviewed-action-evaluation.json), and [deployment revision-3 cases](documentation-coverage/release-deployment-reviewed-action-evaluation.r3.json) contain proposed textual expectations, not executed retrieval assertions. Exact expected answer behavior needs independently specified executable assertions in the future harness; matching fixture prose to itself proves nothing.
- [Website support entry](axiom-website-information-architecture.md#support-entry) preserves `/account/help`, `/docs/troubleshooting`, `/status`, `/contact`, and the separate funding meaning of `/support`. Search and a public `/help` hub remain proposed. This design changes none of them.

All existing Agent and deployment articles remain internal drafts for source-only local previews and customer-ineligible. Revision existence, a status string, valid hashes or a simulated reviewer must never promote them. Historical revisions, fixture bindings and consumed/unknown action records remain intact.

## Fixed inputs and authority boundary

The future ordinary retrieval command accepts only a repository root, explicit catalog snapshot path, exact product version, audience (`public` or `internal-inspection`), bounded question and a separately verified invocation context described below. The separate simulation evaluator additionally accepts an explicit fixture-suite path/digest. No recursive discovery, URL input, arbitrary file upload, tenant log ingestion or automatic “latest” fallback. Suggested hard limits for this first composition: 64 article revisions, 1 MiB per JSON file, 16 MiB total bundle, 128 sources per article, 256 cases, 512 question characters and 3 returned components including context. Reject excess, invalid UTF-8/JSON, unsafe paths, symlink escape, duplicate composite identities, unknown fields and ambiguous catalog entries before retrieval. Read declared regular files only; treat every failure as unavailable, never partially eligible.

The catalog is a reviewed, immutable local release artifact, separate from article self-declarations. Its conceptual entries bind article path and byte digest, ID/revision, exact supported release/source manifest digest, audience, approved section identifiers, verification/media evidence digests, editorial decision evidence digest, validity window, and replacement/revocation relationships. The complete snapshot also binds a monotonic catalog generation, predecessor digest, supported-release set and explicit full member set. This is a proposed input contract, not a schema change or migration in this batch.

Trust originates with a specifically designated human editorial/release authority reviewing the complete snapshot and supplying its digest through a separate trusted invocation/review record. Neither an article's `review.reviewer`, an author-generated approval file, nor a catalog's own `approved` field authenticates that authority. Identity, scope and decision evidence must be verified by the designated authority outside this offline program before a real catalog is pinned. If that process/evidence is absent, the program has no customer-eligible catalog. Cryptographic digest equality proves bytes, not human identity, semantic truth or completeness.

The verified invocation context must contain: context kind `real`, authority identity and verified decision-record digest, allowed audience/product/version scope, exact expected current catalog generation and SHA-256, freshness assertion expiry, invocation identifier, and evaluation instant in UTC. It must be delivered through a trusted launcher boundary established independently of article/catalog/query/CLI inputs. The launcher supplies its current trusted clock observation for this invocation; callers cannot supply `--now`, replay an old observation or override generation. The observation must be at or after the decision issuance and within both decision/catalog validity windows; unavailable or untrusted clock/current-generation verification refuses. An operator-selected timestamp, digest or locally authored “trusted” record cannot satisfy this boundary. No actual issuer, trusted launcher, clock facility or genuine decision is established here: until separately designated and verified, ordinary public retrieval must fail closed. The normalized verified context, including its instant and generation, is part of the fixed input record for deterministic replay; replay is evaluation evidence only and cannot authorize a fresh public result.

A separate simulation-only evaluation command may use a clearly labeled **SIMULATED editorial authority, clock and supported release** to exercise the same pure eligibility rules with purpose-built synthetic public fixtures. Its context kind is `simulation`; all envelopes are `simulationOnly: true` and `customerEligible: false`, even for an expected positive selection. It cannot invoke the ordinary public output path or emit a genuine customer-eligible result. The ordinary command has no simulation flag and rejects simulation contexts, synthetic catalog/release pins and replay contexts, regardless of article metadata. Synthetic fixtures live separately from real articles and are never promoted, written into real catalogs or described as genuine approval/customer acceptance. Internal inspection is a deliberate local operator mode, not authentication/role enforcement for a multi-user product. Public mode cannot retrieve internal content, expose internal source paths, rejection details or snippets; choosing a mode would not be sufficient access control for a future deployed service.

## Eligibility and immutable updates

1. Verify the complete catalog bytes, generation and validity window against the verified invocation context's expected current generation/digest and trusted evaluation instant. Missing real authority, clock or freshness/current-generation evidence refuses. A disconnected machine cannot discover a newer remote revocation: results are valid only against the supplied reviewed snapshot, never a claim of globally current knowledge. An expired or unconfirmed snapshot yields no answer.
2. Require the requested version to be an exact member of the catalog's independently reviewed supported-release set; compare article `productVersion` and `verification.verifiedVersion` exactly. No semver nearest match, title match, branch inference, preview-to-shipped conversion or cross-version merging.
3. Resolve the complete catalog's replacement/revocation graph before searching. Entry uniqueness is the composite `(article ID, revision, exact productVersion)`; each ID/revision also binds one immutable article digest and version. Repeated article IDs across distinct revisions and repeated product versions across distinct articles are valid history. Refuse duplicate composite entries, conflicting ID/revision bytes/version, cycles, forks, missing referenced revision metadata or multiple conflicting current entries for the same article ID/exact version. A later replacement excludes its predecessor for the applicable version even if the replacement's article payload bytes are missing or invalid: absence must not reactivate old guidance. Revocation excludes the target immediately; revoked replacement does not revive its predecessor. Old-version historical entries require explicit current authorization for that exact still-supported version.
4. Require exact article bytes, source manifest and all declared source/media hashes, evidence identities/digests and catalog decision binding. Retain the existing validator's schema/path/hash checks. Evidence paths/transcript existence alone are insufficient for the proposed catalog: bind their bytes as well. Validate source against the catalog's exact local release snapshot, not the unrelated moving worktree. If that snapshot is missing, stale or mutated, quarantine; do not update hashes automatically.
5. Public eligibility additionally requires genuine catalog authority, approved/public metadata, a supported shipped version, factual/release review and safe media review where applicable. A source-only or simulated verification label never by itself proves shipped behavior. Every current repository draft must fail this gate. Internal draft inspection may return only labeled source-review material, never customer answers.

Updates are manual, append-only new article revisions and new reviewed catalog generations. Revocation/supersession are new catalog decisions rather than overwriting history. A file disappearing, changing status or appearing outside the pinned full member set never silently updates eligibility. No ingestion job watches directories, repairs digests, approves content or writes a catalog automatically.

## Deterministic retrieval and citation contract

Each catalog entry must bind a complete routing table: route ID; exact version/audience; reviewed exact screen/control IDs or ordered required token sets; primary JSON pointer; ordered required-context pointers; an exclusive answer-group ID; explicit incompatible route IDs; and approved public destination plus destination version and fragment. All pointers resolve against that entry's exact article bytes. Pointer targets are restricted to existing string values (including individual prerequisite/permission/limitation/recovery array elements and individual step `instruction`/`expectedState`/`effect` fields); no independent section schema or invented text is assumed. Required context must explicitly enumerate all prerequisite, permission, limitation and recovery elements and the whole selected step's three fields where a step is selected. Missing/unresolvable context, asymmetric incompatibility declarations or a route without this mapping refuses the catalog. Review approves the complete routing/context/conflict/destination table together with the catalog digest, not merely the prose.

For each pointer target, define `sectionDigest = SHA-256(UTF-8(JSON.stringify(decoded string)))`: standard JSON string serialization with double-quote delimiters, escaped quotation marks/backslashes/control characters, no whitespace outside the value, no Unicode normalization, no newline insertion and no BOM. Invalid Unicode scalar content is rejected. The displayed quotation is the decoded string without alteration; its citation hashes that canonical JSON string value, not a claimed raw byte span. The whole article digest still binds original file bytes. Every context pointer has its own digest and citation. This deliberately restricts targets to strings so object-key ordering and array serialization cannot be implementation choices.

After eligibility, tokenize question text with Unicode NFKC normalization, Unicode lowercase conversion and maximal letter/digit runs, using a pinned Unicode version recorded in the future implementation/evaluation identity. Match only the catalog-reviewed routing table. Exact control/screen match precedes all-required-token matches; use stable article ID/revision/route ordering only for display. No fuzzy expansion or invented synonyms. Two or more distinct highest-priority route candidates always produce no answer, even when their relative pointers, answer-group IDs or displayed text match. A candidate is identified by its catalog entry's article ID/revision/exact productVersion and route ID; relative pointers never establish equality across articles. Any explicit incompatible pair among matches also produces no answer. This conservative rule does not attempt semantic contradiction detection: semantic safety remains editorial responsibility. Empty or unsupported queries produce no answer. These deliberately limited rules make failures measurable and do not promise general natural-language support.

Return only verbatim approved sections selected by their stable JSON pointers, with their prerequisites, permissions, limitations and recovery context included. If the complete required context exceeds the output bound, refuse rather than truncate a safety condition. No generated synthesis, permission inference, execution, automatic recovery or action buttons. Source text and question text are inert data: never evaluate code, follow embedded instructions, open URLs, import modules, read suggested paths or let article prose modify routing/authority. Render no active HTML/links from untrusted text.

Each quoted primary and context component carries article ID, revision, exact product version, article digest, JSON pointer and canonical section digest, plus the catalog generation/digest. Internal results may carry reviewed source identifiers/digests; public citations resolve only to the routing table's approved public destination/version, never repository/evidence paths or tenant identifiers. Destination version must equal the exact requested version; absence/mismatch produces no customer answer rather than an invented URL. A mutable public page is a reading destination, not proof of immutable quoted content: the local pinned article/pointer/digest tuple is that proof, and no network fetch occurs. A citation must resolve back to the exact decoded string/canonical digest. External source links are provenance, not automatic authority. Conflicting mappings or missing prerequisites produce no answer/escalation.

Use fixed reasons such as `no_eligible_evidence`, `version_unavailable`, `catalog_unconfirmed`, `integrity_failure`, `ambiguous_evidence` and `unsupported_question`. Public wording: “I do not have approved guidance for this version and question. Check the documented troubleshooting or contact path.” No draft-derived operational answer accompanies that refusal. For lost acknowledgments, consumed attempts, expired/revoked authority or uncertain outcomes, do not recommend retry, reset, new approval impersonation or automatic resend. Route unresolved uncertainty to existing documented support contact guidance without inventing an SLA or uploading diagnostics. Questions containing apparent secrets are refused without echoing/storing them; no secret detector is claimed exhaustive, so inputs are restricted to synthetic/safe support questions and no logs are persisted.

## Representative evaluation composition after approval

Run the same eligibility/selection/citation pipeline used by the proposed command, entirely in memory, against immutable synthetic bundles and current real drafts. Compare explicit status/reason, selected exact citation tuples, exact extract bytes, forbidden leaks/actions and deterministic ordering. Fixture instructions never act as an answer engine. Report suite/bundle/catalog/code digests, case IDs, actual versus expected results, simulation labels and failures to stdout only; saving a report requires a separate explicit operator action. No automatic writes or test updates.

| Case group | Required result |
| --- | --- |
| Synthetic genuinely labeled simulated positive; exact control and exact version | Exact expected section and context, reproducible resolvable citations; clearly simulated result |
| Current Agent/deployment drafts, including revision 3 | Public no answer; draft/internal/local-preview never bypassed |
| Forged approved/reviewer fields or self-authored catalog | No authority; no answer |
| Synthetic catalog/release/context supplied to ordinary public command | Refused; cannot emit customer-eligible success |
| Caller historical clock, replay context or generation override | Refused; only independently verified fresh invocation context is admissible |
| Wrong/unknown/preview release, case-changed version or nearby semver | Exact-version refusal; no fallback |
| Changed article, source, evidence, transcript, media or catalog bytes | Integrity refusal; no auto-rebinding |
| Newer replacement present, missing, invalid or revoked; cycles/forks | Old entry excluded; malformed catalog refuses; no resurrection |
| Stale/expired/rolled-back catalog or absent trusted freshness pin | Catalog-unconfirmed no answer |
| Public query matching internal title/control/source | No content/path/existence leak in public output |
| Malicious prose asking to ignore rules, read credentials, run commands or upload data | Inert text only; no effects; unsafe guidance excluded by editorial routing |
| Oversize/path traversal/symlink/duplicate/malformed input | Bounded early refusal; no extra reads |
| Unsupported/ambiguous/conflicting/zero-match query or missing public destination | No answer or safe clarification; no fabricated citation |
| Lost response, expired/revoked access, missing record, unsupported AWS capability, approval-versus-execution, health claim | Existing representative semantics preserved; no blind retry or authority/health inference |
| Valid citation ID with wrong revision/pointer/hash or misleading extraction | Evaluation fails, even when answer wording appears plausible |
| Missing routing/context citation, altered canonical string digest, conflicting routes or wrong destination version | Catalog/result refuses; complete context never silently dropped |
| Multiple immutable historical revisions versus duplicate/conflicting current entries | History is representable; duplicate composite identity or conflicting current guidance refuses |

Passing requires every negative boundary and every synthetic positive assertion, with zero unintended effects and identical repeated outputs for identical fixed inputs including verified/simulated invocation instant and generation. Replaying a real context can establish deterministic evaluation only, never fresh authorization. No pass count is claimed here. Existing proposed fixture files remain `proposed-not-executed`; future execution reports are separate artifacts. These checks validate this bounded offline composition, not authentic media, editorial truth, multi-user authorization, deployed currentness, cloud safety or B5 completion.

## Acceptance boundary

This proposal is complete for design review. The user approved this bounded local implementation after independent design review; genuine customer authority and activation remain unapproved. It changes no existing schema, validator, fixture, article, product navigation, backend, database, endpoint or customer eligibility. A future implementation review must verify the catalog trust/freshness contract and the negative evaluation matrix before any broader integration. Genuine editorial approval, supported-release/media acceptance, private-content authorization and separately approved customer/public activation remain outstanding. Cloud AI requires its own data-boundary/security review; this composition contains no model or cloud path.
