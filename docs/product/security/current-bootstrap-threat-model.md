## Memory and residual access

Native material and frame buffers use explicit wiping paths. Native allocation failures wipe mutable key array buffers; initializer and canonical cleanup wipe supplied key staging. `privateCredentialVault.ts` and `privateDesktopToken.ts` intentionally make independent `Buffer.from` copies for private factory closures. The lifetime drops the graph, but provides no key-destruction operation for those retained copies. Datasource JS strings, V8/GC, Prisma/driver/crypto state, Foundation/Security return buffers and kernel pipe buffers have no demonstrated zeroization guarantee. Wiping staging is bounded hygiene, not proof that all copies disappear, including on abrupt process failure.

Current global `lib/db.ts`, legacy vault environment lookup (`CREDENTIAL_ENCRYPTION_KEY` / `STARTER_TOKEN_SECRET`) and legacy desktop signer (`DESKTOP_SESSION_SIGNING_KEY`) remain source-visible alternative resource paths. Private composition avoids selecting those global resources, but cannot withdraw credentials from general web/workers/older processes. Source visibility is not proof of actual deployed grants or a newly demonstrated exploit. Actual resource placement, equivalent signer/decrypt access, caches, reusable tokens and authority writers require the separately approved custody/cutover work. See [custody design](../../recovery/2026-11-03/compiled-consumer-authority-bridge/custody-profile-decision.md). Protect trusted approvals, exact history and unknown effects throughout any later migration.

The model assumes trusted local kernel/platform services and trusted native code in the qualified process. It does not protect secrets against malicious code already running inside that process or an administrator/kernel controlling it. Fresh origin checks cannot guarantee survival for a remote effect's entire duration, nor replace current session/approval/source/connection/claim checks at original business boundaries.
