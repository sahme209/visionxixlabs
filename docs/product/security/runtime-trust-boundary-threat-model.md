# Canonical issuer runtime: bounded threat model

Snapshot: main `d34805d00dd0716d8b4a58f74eb7b3edd4af70ea`; proposed native core `97f24857` and packaging `fce7fd07` are separately reviewed, unmerged inputs. This document describes source mechanisms and open evidence gates, not qualified Governance enforcement or a security guarantee. Later fixes are not assumed present.

## Objective and assumptions

Only the fixed, verified canonical main and its actual compiled consumer should obtain a current owned-origin observation. A request, matching JSON, source hash, cached export or caller-selected process must not initialize authority. Protect package bytes, native lineage, credentials/claims and one-attempt effect history. The objective assumes the existing trusted local host and platform signing/kernel services; it does not promise protection against a hostile kernel, administrator or malicious native code already inside the trusted runtime.

## Residual risks and acceptance rules

1. **Consumer substitution remains unverified.** `docs/recovery/2026-11-03/canonical-consumer-validation-status.md` records automatic safety review blocking specialized test generation. This document does not recreate, rephrase or delegate that test. No behavioral result is claimed. Source inspection and component exchange cannot replace the original gate; activation stays unavailable until an appropriately permitted validation route satisfies it.
2. **TOCTOU and lifecycle are core risks.** Inputs can change between observations; filesystem/signature work can stall. Final package binding, cancellation before late spawn, per-message ownership, permanent revocation and truthful uncertain history need actual integrated evidence. A last-moment freshness check cannot guarantee broker survival throughout a remote effect.
3. **Preparation is not issuance.** Compile recipes, mock signatures, manifests, isolated database tests and diagnostic origin exchanges establish only their stated bounded properties. They do not establish real canonical identity, customer safety, universal execution coverage or fleet qualification.
4. **Failures stay closed.** Do not enable enrollment or replace throwing readers until the actual chain and existing Governance completion gates pass. Never replay uncertain provider effects or weaken genuine independent approval to obtain a positive demonstration.
