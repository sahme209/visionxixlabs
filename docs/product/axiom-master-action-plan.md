### A9. Orchestrator Independence & Enterprise On-Prem Deployment

**Goal:** Make Axiom Agent orchestration-agnostic and fully deployable within customer-controlled infrastructure without compromising governance, security or usability. This extends the full master scope; it does not replace A1–A8 or B1–B6.

**Priority and dependencies:** Architecture foundations first, while closing core Governance enforcement. Adapter migration and on-prem deployment follow verified core enforcement. Preserve current release commitments, existing Airflow behavior, genuine independent approvals, one-attempt/unknown-outcome history and all security/spending/provider restrictions. Adding this requirement is not authorization for infrastructure purchases, trials, migrations, live provider operations, new grants or publication.

1. **Orchestrator abstraction layer.** Build a unified versioned interface supporting Apache Airflow, Temporal and custom workflow engines. Standardize workflow execution, status, cancellation, retries, events and recovery. Detect engine-specific capabilities explicitly; unsupported features must be reported rather than silently simulated. Preserve existing Airflow functionality while migrating to adapters. Keep approvals, policy enforcement, audit trails and rollback governance independent of the orchestrator. Engine retries must never replay a consumed consequential operation or turn an uncertain outcome into permission.
2. **Fully self-hosted / air-gapped enterprise deployment.** Support complete on-prem operation of workflow engines, Governance policies, approval services, audit logs and supporting databases. Keep source code, credentials, secrets and sensitive execution data within customer-controlled infrastructure. Support customer-managed encryption, local authentication/SSO, offline operation and optional local AI models. Provide reproducible installation, upgrades, backup/restore, monitoring and disaster recovery. There must be no mandatory cloud connectivity, external telemetry or hosted licensing dependency for the enterprise offline mode.
3. **Required acceptance evidence.** Existing Airflow workflows remain functional. Airflow and Temporal pass the same core workflow contract tests. A documented adapter lets a custom engine integrate. No workflow can bypass mandatory Governance or genuine independent approvals. An enterprise installation completes a real governed deployment with internet connectivity disabled. Automated and end-to-end tests verify security boundaries, audit integrity, rollback behavior and recovery. Simulated adapters, an offline web page or a container starting successfully are insufficient evidence for these end states.

**Architecture decisions to record before migration:** tenant/execution/source identity across adapters; stable engine/run/event IDs; supported capability and error vocabulary; retry/claim/uncertainty/cancellation ownership; engine-independent approval and policy authorities; source/evidence freshness offline; audit retention/integrity; encryption/key custody; local SSO/session recovery; local-model data boundaries; offline license behavior; reproducible air-gap artifact supply chain and upgrade/rollback compatibility.

**Risks and completion tracking:** Current hosted API, identity/commercial-access checks, provider integration calls, token brokerage, AI configuration, audit export and installer/update dependencies need a source-backed dependency inventory. Do not assume these are already offline-capable. Track each dependency's current source, owner, migration design, tests, operational recovery and explicit verification evidence. Real installation/provider hosts and independent human decisions remain separately required where applicable. Offline security must not be achieved by bypassing authentication, approval, encryption, update signatures or permission checks. State is **newly planned / unimplemented**, with no customer on-prem support claim.
