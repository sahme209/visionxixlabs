# Release regression controls

These controls apply to website appearance changes, functional changes and dependency upgrades. They preserve the owner's existing spending, production, database and genuine-review boundaries.

1. **Classify the complete release.** An appearance-only change preserves authentication, database, download, desktop protocol and dependency files. Any difference in those areas makes the release functional and requires an explicit change inventory and relevant regression evidence. A visual description does not cover an accompanying dependency upgrade. Compare the final source against the last proven deployed source; an unknown deployed SHA is an evidence gap, not equivalence.
2. **Keep design and function evidence separate.** Screenshots prove appearance. Unit tests prove their stated contracts. Build success proves compilation. Use compiled application/HTTP and owned database or protocol fixtures for affected sign-in, recovery, storage and download paths. Exercise the supported connection modes and failure paths. Isolated identities, providers and data never become production proof.
3. **Bind installer acceptance to the released files.** Keep exact source/tag/run/attempt, candidate hashes and actual installation/upgrade/cleanup results together. Rebuilding or replacing files invalidates earlier byte acceptance. Preserve honest unsigned-platform and unverified-rendering/account limits.
4. **Verify the deployed source and the live paths.** Record the actual production deployment, immutable Git SHA and domain assignment. Project-setting agreement does not prove the configuration captured by an existing deployment. Use value-free client/transport diagnostics when runtime behavior contradicts local evidence. Never expose connection URLs, credentials, hostnames or raw exception contents to resolve that gap.
5. **Run the public journey check after the owner deploys.** From the reviewed checkout, run `node scripts/check-production-product.mjs desktop-vX.Y.Z INSTALLER_SOURCE_SHA`. It checks only canonical GET endpoints and bounded public release metadata. Nonzero exit blocks a success claim. Quiet, disabled Governance activity is not a reason to activate it to make health checks green. The installer SHA does not establish the website SHA; the checker does not cryptographically verify installer bytes/signatures.
6. **Require visible authentication and desktop acceptance.** Complete real Google sign-in, any required email recovery, workspace loading and the browser-to-desktop return/session check with the owner. Provider enumeration, a Google button, a mock identity or an open native window does not prove this journey. The public checker intentionally keeps these gates UNVERIFIED and `releaseAccepted:false`, including after an automated pass.
7. **Keep release status truthful.** Green CI and published installers do not mean the complete product is working. Keep login, public website downloads and other unverified journeys open; do not move to Governance on the strength of build/test counters. On failure, preserve the exact result and first gather discriminating evidence. No automatic additional production build, setting change, database write, permission change or retry is authorized by a failed check.

The checker is an operational regression control, not a new approval authority. Existing owner publication review and owner-clicked production deployments remain genuine external actions.
