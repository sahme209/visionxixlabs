# Website deployment readiness and bounded reconciliation

Reviewed 2026-10-15. These changes concern existing legacy website preview/publish APIs, not production Axiom deployment routing or the AWS ECS adapter. No external deployment, production data write, infrastructure change, or live billing action was performed during development.

## Customer-visible contract

A successful Vercel create request is an accepted request, not evidence the site is serving. The adapter preserves reported `readyState`/`state`, defaults missing state to UNKNOWN, and never invents a URL from an ID. Only explicit READY with an actual HTTPS URL and receipt ID may replace a served preview URL or mark it ready. Publication additionally requires provider-confirmed `target: production`; preview/missing target cannot be marked published. The existing admin publish route alone uses an explicit `deployProduction` wrapper that sends `target: production` to Vercel. A project name starting with prod is not production evidence, and default preview calls never add production intent. ERROR/CANCELED results fail without replacing an existing working preview.

Both public trigger paths, admin preview, admin publish, and signed-token revisions share this decision. Pending receipts are stored separately in `previewDeployment` or `productionDeployment`, including candidate ID/state/URL. Candidate URLs are not served-preview links. Missing credentials remain managed-pending/package-ready and cause no provider request. A pending revision stores its candidate package in `pendingAiPackage`; the currently served package and URL remain intact. The revision counter still tracks the requested generation, not successful hosting.

Responses explicitly include `deploymentPending`. An existing working preview may remain available while a replacement is building; its historical lead status does not imply the new operation succeeded. The status API reports `deployReady: false` during any pending operation and reports both receipts separately. Ready email dispatch remains gated on explicit READY from the initial create response; reconciliation does not send email, avoiding duplicate notifications. Future exactly-once asynchronous notification delivery remains unimplemented.

## Existing polling path now completes the pending operation

`GET /api/leads/status?token=...` retains its signed lead-token authority. The same endpoint also accepts `?leadId=...` only after existing configured-admin authorization, before lookup. Explicit invalid/empty tokens never fall back to admin authority. The admin Leads page exposes a per-lead Refresh deployment action that invokes this observation GET and reloads current lead state. Pending provider operations disable duplicate regeneration/deploy/publish controls; existing working previews remain separate links. Refresh failures appear inline and release the refresh busy state for retry. Terminal deployment failures remain visible after observation. A `managed-pending` receipt explicitly records that no provider call occurred, so it shows a configuration-unavailable message and permits an explicit authorized deployment retry after configuration is restored. Accepted/unknown provider outcomes retain the conservative observation/review boundary. After looking up that lead, it observes at most one pending preview and one pending production receipt. Only a strict saved `dpl_...` identifier may be fetched from the fixed Vercel API origin with the existing server-side VERCEL_TOKEN/optional team. Each read is bounded to five seconds and disables response caching. Missing credentials, managed-pending placeholders, malformed IDs, provider failures, mismatched returned IDs, and unconfirmed states cannot create a success transition.

A confirmed READY result updates that exact receipt and served URL. A preview's pending package becomes the active package only at this point and only when its saved deployment ID matches the observed receipt. Terminal preview failure and every immediate READY replacement clear stale pending package/ID fields; a failed earlier revision cannot be resurrected by a later retry. A terminal failure records the failed receipt and retains existing working URL/package; a first failed build returns to package-ready. No provider mutation occurs during polling.

The local status update uses a compare-and-set against lead ID, prior status, and entire prior JSON payload. A delayed observation cannot overwrite a newer revision, receipt, or other payload change. If it loses the comparison, the response reloads the current lead rather than reporting stale READY. Settled receipts skip future provider reads. The same boundary completes pending production publication only for a receipt already created through the admin-authorized publish route and confirmed by the provider as production target; possession of a signed lead token does not authorize a new deployment.

## Verification and remaining limitations

Behavioral provider/route tests simulate create responses, signed-token polling, exact-ID provider observations, READY completion, terminal failures, unavailable credentials, stale observations, public/admin authorization, and preservation of served previews. Fail-before comparison demonstrates the old code falsely promoted accepted states. These are simulated-provider regressions, not a live Vercel/customer acceptance claim.

No schema migration, queue, cron, new secrets, provider integration, or route was introduced. Completion depends on an authorized operator using the admin refresh action or a caller using the signed-token endpoint, and on the existing Vercel credential still having access. No public frontend auto-poller was found in the current product. There is no background notification worker or guaranteed completion if nobody polls. Historical submissions without saved receipts are not backfilled or invented. Direct concurrent submissions and provider-create crash reconciliation require a broader durable operation contract; this work does not claim to solve those existing limitations.

AWS/Azure/GCP website adapters remain unsupported and fail closed. Production Axiom login recovery and website release promotion retain their separate approval gates.
