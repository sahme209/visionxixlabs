# Airflow provider run identity

Reviewed 2026-10-16. The existing Airflow 3 client now checks run identity at its actual response boundary. The documented [Airflow 3 REST run response](https://airflow.apache.org/docs/apache-airflow/3.2.2/stable-rest-api-ref.html) carries `dag_id` and `dag_run_id`; list and trigger responses must identify the requested DAG. Lists must contain an actual `dag_runs` array with nonempty run identities. A malformed collection is refused rather than silently converted into an empty successful read. Null logical dates remain supported; this change adds no partition policy.

A successful trigger response must echo the exact submitted run ID, including manually generated IDs. Missing/mismatched identity or invalid JSON after a successful POST is an unknown outcome, not evidence that the trigger was rejected. The client neither fabricates a receipt nor automatically replays a manual trigger. The desktop route returns a provider error without a triggered-success audit. Operators must inspect an uncertain manual trigger before issuing another; durable manual-trigger reconciliation remains a separate missing capability.

Scheduled occurrences retain their existing deterministic identity. An unconfirmed response does not advance the schedule; a later scheduled attempt uses the same occurrence ID and existing 409/exact-run reconciliation. This preserves idempotency rather than introducing a new run or declaring the first attempt definitely failed. No executor or approval policy was changed.

Regression evidence composes the real client with desktop routes and the scheduler, using synthetic provider HTTP responses. Before the fix, another DAG's success produced a proposal and a mismatched trigger response produced a successful receipt; the new boundary regressions refuse both. A scheduled unknown-response/409 recovery regression confirms the same submitted identity and one modeled provider occurrence. These tests do not contact Airflow, GitHub or a cloud provider, and do not prove a real customer deployment.

The next provider acceptance gate remains an explicitly authorized nonproduction Airflow 3 endpoint: inspect the deployed response schema, validate returned DAG/run identity, exercise one governed fixture occurrence and capture its sanitized run/audit linkage. Strict business-partition correlation, immutable deployment artifacts and actual cloud execution still require their separately tracked engineering and acceptance work.
