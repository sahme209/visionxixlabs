# ECS v2 durable review core — execution disabled

This slice implements reusable packet, revisioned decision and review-checkpoint storage. It does not implement provenance verification, public routes, workflow authorization, signing, dispatch, AWS writes, execution claims or live quota consumption. `ECS_REVIEW_EXECUTION_ENABLED` is literally false and the only execution result is `execution_disabled`. A review-ready checkpoint is never an execution approval/token.

## Required independent boundary

Preparation parses an existing strict v2 structural candidate and requires accepted current management membership and the matching current selected policy before any independently verified provider boundary is invoked. It rechecks authority, policy and expiry inside the post-IO persistence transaction. Unauthorized or blocked callers cannot trigger future costly provider reads. The default boundary is absent: preparation fails unavailable and persists nothing. Caller JSON, source labels, hash equality, TypeScript interfaces and synthetic test facts do not verify provenance. No production adapter manufactures trusted facts from the submitted manifest. Real GitHub/Sigstore verification, task-definition/container completeness, current AWS target/baseline/ALB association, OIDC and provider permissions remain unimplemented dependencies.

The existing pure fact comparison is extracted as `matchTrustedReviewEvidence`; final `matchTrustedReleaseEvidence` still requires its independent approval match. Preparation stores a detached manifest and independently supplied evidence with canonical digests. Every later service read reparses and recomputes packet identities. This detects accidental or partial storage corruption, not a privileged database attacker rewriting all facts and hashes. No new cryptographic authority is claimed.

## Durable lifecycle and authority limits

Three new, separately reviewed tables store packets, append-only decision revisions and immutable review checkpoints. Packet operation identity is unique within the tenant. A same-operation/different-content request conflicts. The application exposes create/read methods only; there are no packet/decision overwrite or delete APIs, SQL triggers, cascaded deletion of review history, existing-table alterations or live deployment links. Restrictive foreign keys prevent cross-tenant decisions/checkpoints and deletion of referenced packets. Privileged operator retention/export/deletion requires a separately reviewed procedure; application append-only behavior does not prohibit an administrator's direct SQL updates.

The PostgreSQL adapter uses parameterized static SQL and Serializable transactions. It reads accepted current owner/admin membership and the environment's explicitly selected enabled `AxiomApprovalPolicy`, with current required approver roles/count and block state. Unsupported role requirements and missing policy fail unavailable. Self-approval is conservatively disabled in this first review-only adapter. Its canonical policy digest includes policy identity, update timestamp and these requirements. This is an explicit selected-policy review adapter, not a replacement for a complete multi-policy deployment authorization engine.

A voter supplies the expected prior revision. A fresh transaction reads that voter's latest decision and appends the next revision; unique revision keys and Serializable conflicts prevent concurrent overwrite. Later rejected/revoked revisions invalidate previous approval. A stale revision cannot silently replace the new decision. Current memberships, policy, packet integrity, expiry, latest voter decisions and quorum are recomputed when creating/retrieving a checkpoint. Old checkpoint identifiers are not trusted directly. Current eligible approvals produce a decision-set digest and idempotent checkpoint; rejection/revocation blocks it. The service never consumes a `DeploymentExecution` reservation or customer allowance.

Evidence records are captured at preparation. Checkpoints prove only the current review decision set against that stored evidence and current selected policy/membership. They do not refresh provider observations or establish current deployment readiness. Any future execution lane must independently reverify source/artifacts/target/baseline, durable approval policy/quorum and expiry at its actual claim boundary. Incomplete/missing provider observations cannot be repaired by this review snapshot.

A failed transaction/unknown commit returns `review_outcome_unknown`; there is no external action or automatic execution retry. Read-only reconciliation can identify the existing packet by tenant/operation, its latest decision revision and a recomputed checkpoint. Retrying the same preparation is idempotent; a decision retry must first learn the current revision. Expired packets cannot accept decisions/checkpoints. Revocation is append-only and checkpoint validity is recomputed, not a sticky ready flag.

## Source-only target snapshot compatibility

The existing release kernel now also parses `axiom.ecs.release.v3`. Its target replaces v2's integer `revision` with a strict `snapshot` containing schema `axiom.ecs.target-snapshot.v1`, persisted target id, canonical digest and selected connection id/credential version. V2 retains its exact field set, canonical bytes and meaning; mixed variants fail closed. A new variant is a new manifest digest and cannot reuse an old receipt or review packet.

The shared projector hashes explicit target configuration and ISO update time, scoped environment identity/update time, and safe connection identity/configuration/update time plus credential version. It excludes encrypted configuration and external IDs. The inactive AWS observation reader produces that identity from independently read rows after its existing IO fences. Digests prove equality only: they are not provenance, monotonic generations, historical ABA detection, management readiness or execution permission. The task-definition registration digest schema remains explicit; no adapter maps observations into trusted review facts in this slice.
