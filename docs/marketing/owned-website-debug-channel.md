# Fixture-only React debug channel compatibility

Pinned Next 16.3.8 defaults `experimental.reactDebugChannel` to true. The development client passes its debug readable stream into the Flight decoder. That stream receives data and EOF through HMR WebSocket messages. The owned website fixture intentionally denies WebSocket upgrades; an open debug stream can therefore leave unresolved debug references pending even when primary document and JavaScript deliveries succeed. This is a source-supported mechanism, not yet proof of the integrated CI stall's cause.

A pure regression executes the actual installed React Flight development decoder in a VM, with only actual React/ReactDOM dependency imports and a webpack loader that throws if used. It supplies a closed synthetic primary stream containing a debug reference and a root model. The root remains pending while the debug stream lacks the referenced data; providing the synthetic debug model and EOF resolves it. This proves the controlled decoder dependency, not an application, hydration or customer workflow. The test does not establish that EOF alone is required for root resolution. No network, process, listener, server, browser, Prisma or provider is used.

The fixture now sets `experimental.reactDebugChannel: false`, preserving all other actual experimental options. Both existing fixture paths apply it: the owned Next options and the supported config-file reload helper, which already validates exact private ownership, framework identity, source pins and development phase. Updating options alone would be ineffective because public custom-server preparation reloads `next.config.ts`. Ordinary configuration still returns the original object unchanged; no production config file bytes, global defaults, HMR permissions or request policy are changed. Fresh runtime manifests bind the changed helper sources.

The pure composition regression failed before correction because the actual pinned default was true, then passes with the fixture override. Existing private-context configuration tests verify preserved actual configuration and unmodified input. All original timing, ownership, cleanup, network and process safeguards remain. The fixture is explicitly not production-equivalent, and a fresh reviewed integrated CI result is still required before claiming that this correction restores actual playback acceptance.
