# Dashboard restart governance and durable claim

The legacy dashboard release action now uses the same tenant deployment allowance/reservation as desktop and Agent, with `source: dashboard` and server-derived `dashboard-release:<releaseId>` identity. The existing `{releaseId}` request requires no client header or new schema. It still requests the installed four-input workflow; neither workflow filename nor successful receipt verifies a source artifact, image rollback or application health.

Same-origin browser requests are required before cookie-session writes. Accepted replay receipts must match the dashboard source and current tenant-owned release repository/environment/tag/source binding; another API client cannot preoccupy the public idempotency namespace to fabricate an accepted dashboard receipt.

Before provider dispatch, the server checks current accepted owner/admin membership, tenant-owned release/repository/environment/AWS target, finalized scope and explicit tag/full source SHA. The shared deployment policy resolves the tag and compares it to the recorded source identity. Production requires the existing production controls and denies legacy artifact promotion; there is no emergency override on this route.

`ready` is not approval authority. Environments with an approvalPolicyId fail explicitly because the legacy release approval orchestrator has no durable decision bound to this operation. Configured environment/release windows fail explicitly until a reviewed verifier exists. A tenant/release-scoped zero-blocker readiness snapshot must postdate current release/repository/environment/target changes; current blocking policy violations also deny. This is conservative snapshot freshness, not a claim that its score proves immutable artifacts, complete provider readiness or durable approval. Snapshots lack a complete input manifest and cannot replace the future v2 evidence boundary. Actionable route hints explain these limitations rather than suggesting removal of governance.

After GitHub policy IO and quota reservation, a Serializable transaction rechecks current accepted management authority and the exact release/repository/environment/target/readiness snapshot, enabled branch-policy rows, current active GitHub installation identity and blocking policy state. It uses the existing pure lifecycle transition and a conditional ready→deploying update before any dispatch. This closes the old side-effect-first lifecycle failure. A failed claim releases only the undispatched allowance reservation after an authoritative read confirms the original ready state. An unknown transaction commit or unavailable cleanup remains held. This authority fence ends at the committed claim; it is not a promise to cancel a later external request after connection revocation.

Once provider invocation begins, exceptions, ambiguous provider failures, missing receipts and settlement failures preserve the claim and allowance. A definite nonacceptance may conditionally restore only the exact owned deploying claim and release its reservation; later operator transitions are preserved. Accepted durable receipts replay without another quota slot or dispatch. Reserved/uncertain operations require reconciliation rather than blind retry. A changed release does not generate a fresh operation identity that evades an unresolved hold. This initial contract permits one accepted dispatch per release; a deliberate later independent restart needs a separately reviewed operation identity contract, not a client-generated bypass.

No migration, cloud call, workflow dispatch, routing change or live billing occurred during implementation. Local composed service/route tests exercise fresh authority and snapshot denial, quota refusal, lifecycle claim ordering/CAS failure, exact four-input dispatch, definite rejection recovery, uncertain holds, receipt persistence failure and replay. Shared quota tests run separately. Mocked transactions do not prove database SSI or real AWS/GitHub permission and rollout acceptance. Full durable artifact approval, cryptographic provenance, target task/image health and verified rollback remain the separate ECS v2 milestone.
